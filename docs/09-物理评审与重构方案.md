> 本文是对 `renderer/rope.js` 物理层的一次完整体检，含**解析推导 + 30 余组 Node 探针实测**。

## 一、核心结论（只需读这一节）

### 1.1 结论一：现在看到的「倾斜」100% 是阻尼造成的伪影

匀速拖动时的稳态倾角有闭式解：

```
tan θ = (k·v + drag·v²) / g
其中  k = -ln(1 - velocityDamping) × fixedStepHz      [单位 1/s]
```

**24 组实测误差全部 ≤ 0.27°**。

这个式子里**没有质量、没有绳长、没有转动惯量、没有加速度** —— 只有速度、重力、阻尼。
换言之：真实的摆锤在支点匀速平移时**本来就不该偏**（惯性只体现为滞后，不体现为倾角）。
现在屏幕上的 20~33° 倾斜，是乘性阻尼把摆锤「拖」出来的假象。

实测对照（作弊全关，`monoDrop=0 && minDroopRatio=0`）：

| 速度 | g=8000 vd=.006 | g=8000 vd=0 | 闭式解 |
|---|---|---|---|
| 300 px/s | 9.2° | 2.7° | 9.0° |
| 600 | 16.3° | 4.5° | 16.1° |
| 1200 | 23.3° | 5.4° | 23.3° |

### 1.2 结论二：R13 与 R14 被同一个参数同向绑死

`k` 同时决定两件事：

| 量 | 关系 |
|---|---|
| 拖动时的倾斜角 | `tan θ ≈ k·v / g`（**正比**于 k） |
| 停手后的衰减时间常数 | `tau = 1/k`（**反比**于 k） |

| velocityDamping | k (1/s) | 1200px/s 倾角 | 自由摆 tau |
|---|---|---|---|
| 0.001 | 0.240 | 12.1° | 4.16 s |
| 0.002 | 0.480 | 16.1° | 2.08 s |
| 0.006 | 1.444 | 23.3° | 0.69 s |

**这就是 R13（左右要明显）与 R14（大摆幅慢衰减）结构性冲突的数学根源**，
也是历史上所有调参实验都在同一条曲线上滑来滑去的原因。

### 1.3 结论三：但它不是死结 —— 方向反了

真实人手移动鼠标是**走走停停**的，摆角本应由**加速度**驱动。

当前实现把加速度响应（真摆动）用三重手段抹平：

1. `minDroopRatio = 0.9` 的几何天花板 → 摆角硬上限 **acos(0.9) = 25.8°**
2. `angleDeadzone = 0.10` → 停手后 60~74% 的帧角度**严格为 0**
3. `0.06s` 低通 → 峰值再削 15~20%

然后只留下阻尼产生的**假倾斜**当观感来源。方向反了。

**把阻尼调小 + 删掉天花板**，加速度响应就会出来，而慢衰减正好也是 R14 要的 ——
**两个需求同时满足**。候选 R2 的实测印证了这点（见 第五节）。

## 二、P0 缺陷：数值底座（不修则一切调参无效）

### 2.1 【致命】`_lastH` 是死代码，`fixedStep` 被它绑架

```js
// renderer/rope.js:48   —— 全文件唯一赋值处
this._lastH = 1 / 240;

// renderer/rope.js:440-441
const dtPrev = this._lastH || h;
const ratio = Math.min(4, Math.max(0.25, h / dtPrev));

// renderer/rope.js:447-448   —— 每个子步都乘一次
const vx = (p.x - p.px) * ratio;
const vy = (p.y - p.px) * ratio;
```

`grep -n _lastH renderer/rope.js` 只有这两处，**没有任何地方更新它**。
于是 `ratio ≡ h × 240`：

| fixedStep | ratio | 后果 |
|---|---|---|
| 1/60 | **4.00** | 每子步速度 ×4 → 指数爆炸（实测 1.33e36 倍/秒） |
| 1/120 | 2.00 | 爆炸 |
| **1/240** | 1.00 | 唯一正常 |
| 1/480 | 0.50 | 每子步速度砍半 → 过阻尼 |
| 1/960 | 0.25 | 先被夹到 1/480，再砍半 |

**实测证据一**（纯自由落体 0.5s，解析值应为 v = 8000 × 0.5 = 4000 px/s）：

```
fixedStep 1/240 → v = 4000.0 px/s   ✅ 与解析一致
fixedStep 1/480 → v =   33.3 px/s   ❌ 慢了 120 倍
```

**实测证据二**（25° 自由释放、支点固定、无耗散，峰值序列）：

```
不打补丁：1/60 与 1/120 冲到 144°~178°（乱翻）
          1/240 正常衰减 22.5 → 24.6 → 22.8 → 20.7
          1/480 与 1/960 只出一个峰 25.6（过阻尼）

打补丁 _lastH = h 后：
          1/60 / 1/120 / 1/240 / 1/480 收敛到同一组
          ≈ 20.7, 18.2, 13.7, 10.3, 7.7, 5.8, 4.4
```

**这条 bug 完美解释了 `docs/06` 里那批「调参无用」的历史实验** ——
`fixedStep 1/2000 → 167.5°→169.5° 仍翻`、`gravity 40000 → 90° 仍翻`
全都是在 `ratio = 0.25` 的档位上跑的，物理被静默按死了。

> **修法（一行）**：`_step()` 末尾加 `this._lastH = h;`

### 2.2 【严重】`velocityDamping` 量纲错误

```js
// renderer/rope.js:442
const keep = 1 - Math.min(0.5, Math.max(0, c.velocityDamping ?? 0.004));
```

每**子步**乘性衰减。每秒速度留存 = `(1-vd)^(1/h)`：

| fixedStep | 1s 后速度留存 |
|---|---|
| 1/60 | 0.697 |
| 1/120 | 0.486 |
| 1/144 | 0.420 |
| 1/240 | 0.236 |
| 1/480 | **0.056** |

60Hz 与 480Hz 差 **1252%**。改 `fixedStep` 等于换了一台物理引擎。

自由摆看更直白（vd 固定 0.006）：

```
fixedStep 1/60  → tau 8.01 s
          1/120 → tau 0.67 s
          1/240 → tau 0.90 s
          1/480 → 无有效峰
```

> **修法**：改成物理量纲 `keep = Math.exp(-k * h)`，config 里用 `dampingPerSecond: 0.30`（单位 1/s）。
> 这样 `k` 直接等于 `1/tau`，可读、可算、与 fixedStep 解耦。
>
> 对照值：k = 10/s 时 `keep(1/240) = 0.959189`、`keep(1/60) = 0.846482`。

### 2.3 其它小缺陷

| 位置 | 问题 |
|---|---|
| `renderer/rope.js:313-314` | `accumulator += min(dt, maxAcc)` 紧接着又 `if (accumulator > maxAcc) accumulator = maxAcc` —— **限幅写了两遍** |
| `renderer/rope.js:319` | `_detectCentripetal(dt)` 用**帧** dt，而 `_step` 用**子步** h 积分，两个时间域混用 |
| `renderer/rope.js:417` | `_step(h, stepIndex)` 的 `stepIndex` 已弃用（死参数） |
| `renderer/config.js:111` | `cursorSmoothing` 死配置（渲染层已零延迟） |
| `renderer/config.js:130` | `cursor.bodyHeightRatio` 死配置 |
| `renderer/rope.js` 顶注释 | 仍写「4) 质点数 N 决定柔软度」，与现实现部分不符 |

## 三、物理模型：三道「几何作弊」把物理变成了姿态钳位

`renderer/rope.js` 每个子步除了正常 Verlet + PBD，还跑了一串**位置投影**：

| 步骤 | 代码位置 | 干了什么 |
|---|---|---|
| 5d `monoDrop` | `_step` 后段 | 强制每个节点比上一个低 `monoMaxFix`(6px) 以内（防 Z 折） |
| 5e `minDroopRatio` | `renderer/rope.js:582-599` | `wantDy = length × droopRatio`，不够就 `scaleY` 压缩 |
| 5e-2 | 紧随其后 | 按相对锚点 (dx,dy) 等比缩回总长 |
| 5f | 再兜一次 monoDrop | — |

全部带 `&& !this._centripetal` 旁路。

### 3.1 关键解析结论：`minDroopRatio` 就是摆角天花板

绳长恒定 + 5e 要求 `tipY - anchorY ≥ length × droopRatio` ⇒

```
θ_max = acos(minDroopRatio)
```

| minDroopRatio | 0.5 | 0.7 | 0.8 | 0.85 | **0.9** | 0.95 |
|---|---|---|---|---|---|---|
| 理论 θ_max | 60.0° | 45.6° | 36.9° | 31.8° | **25.8°** | 18.2° |

实测印证（2500px/s 往返甩动，最大摆角）：

```
droop 0    → 104.3°
droop 0.5  →  61.6°
droop 0.7  →  52.4°
droop 0.8  →  47.1°
droop 0.85 →  44.7°
droop 0.9  →  42.3°     ← 当前值
droop 0.95 →  39.5°
```

（实测高于解析上限，因为 5e 只在 `curDy > 1 && curDy < wantDy` 时生效，
且 `scaleY` 被 `droopMaxScale = 2.0` 钳住，是**逐步逼近而非一次性投影**。）

### 3.2 这就是 R13 达不成的量化根因

`_probe_aw.js`，body 角随拖动速度（200 → 4000 px/s）：

```
现状：20.2 / 24.9 / 29.9 / 32.0 / 33.0 / 27.7°
```

**速度翻了 20 倍，摆角只从 20° 到 33°，动态范围仅 1.63×。**

### 3.3 它不可通过其它参数绕过 —— `docs/04` D2 的处方已实测无效

按 D2 修复方向表执行（`angleDeadzone` 0.10→0.02 + `velocityDamping` 0.010）：

| 方案 | body max @200/400/800/1500/2500/4000 |
|---|---|
| 现状 | 22.6 / 26.1 / 30.7 / 33.7 / 36.3 / 36.7（1.62×） |
| D2 处方 | 22.2 / 26.0 / 30.3 / 33.3 / 36.3 / 37.0（**1.67×，等于没动**） |
| D2 + τ 0.12 | 17.0 / 22.2 / 26.6 / 30.5 / 31.2 / 27.2（更差） |
| `bodyRotateRatio` ×1.6 | 29.6 / 37.7 / 44.4 / 50.1 / 53.2 / 48.5（1.64×，仅等比放大） |

> **结论**：36.7° 天花板是 `minDroopRatio = 0.9` 的几何后果。
> 调死区 / 阻尼 / 放大系数**全部无效**，必须移除或替换 5e。
> `docs/04` D2 那张「修复方向表」应当撤销。

### 3.4 5e 不是能量源（纠正一个直觉）

释放 30°，总机械能 E0 = -831384：

```
一帧后：作弊开 -851715（1.02×，能量略降）   作弊关 -833270（1.00×）
4s 后： -960009                            -960133
```

⇒ 5e **不注入能量**，它做的是「每帧把姿态硬掰回下垂姿势」（姿态钳位 / 角度天花板）。
历史上的坐标爆炸（3.7e9 → 5.3e9 → 9.9e91）来自 `curDy ≤ 0` 的边界 bug 与绕圈旁路的组合，不是 5e 本身。

### 3.5 `monoDrop` 与 R15 直接冲突

`monoDrop = 1` 的语义是「每个节点必须比上一个低 1px」，也就是**禁止绳子翻到指针上方**。
而 R15 明确要求**允许翻上去**。二者语义直接矛盾。

实测（2500px/s 往返 1800 帧，fold = 相邻两段方向差 > 90°）：

| 配置 | folds | 绳端高于挂点帧占比 | 链长 min/max |
|---|---|---|---|
| 现状 g8000 droop.9 mono1 seg4 | 8 | **0%** | 54.6 / 60.0 |
| mono1 droop0 g1600 seg4 | 529 | 2% | 49.2 / 60.6 |
| mono0 droop0 g1600 seg4 | 211 | **51%** | 60.0 / 60.6 |
| mono1 droop0.5 g1600 seg4 | 686 | 8% | 46.2 / 60.0 |

⇒ `monoDrop` 是**防折叠的唯一有效手段**，但它同时是**禁止上翻的原因**。
⇒ **`segments = 2` 是唯一零折叠且零拉伸的拓扑**（seg2 → folds **0**，seg3 → 312，seg4 → 211，seg6 → 239）。

> ⚠️ **这条结论已在第 4 轮被推翻。** 当时的折叠数是 `_limitBend` 尚未修好
> （判反 + 会把锚点推开）时测出来的。修好之后所有拓扑的 folds 都是 0。
> 详见 [04](04-已知缺陷与待修.md) 的 D6。

### 3.6 `segments: 4` 是假柔性（第 4 轮已改用 3）

`stiffness = 1.0` + `iterations = 8` 下，900px/s 拖动时中间节点偏离首尾连线的最大距离
（下面是第 3 轮重构**之前**的 rope.js 数据；修好 `_limitBend` 后 3 段绳的 sag 能到 20.1px）：

```
tailMass 0.2 → 2.16px  1 → 0.83px  1.6 → 0.87px  5 → 0.43px  20 → 0.18px
```

绳长 60px 分 4 节（restLen 20），**弯曲量 < 1px，实际是一根刚性直杆**。
「4 节 = 更柔软」是注释里的假设，不是物理事实。
`tailMass` 从 1.6 改到 20 时摆角从 12.8° 掉到 4.7°，它实际在改变「摆锤 vs 绳」的质量分配。

### 3.7 `iterations` 完全空转

`stiffness = 1.0` 时，`iterations` 取 1 / 2 / 4 / 8 / 16：

```
最大摆角 42.5 / 42.4 / 42.3 / 42.3 / 42.2°   平均 36.6° 完全一致
```

每子步本质跑 8 + 2 = 10 轮全链求解，240 子步/秒 → 每秒约 2400 次，**纯烧 CPU**。

### 3.8 `_centripetal` 旁路是无效复杂度

`_probe_ai.js`，「绳端相对圆心**外向**方向平均偏差」（0° = 完美朝外）：

| 场景 | R100v1000 | R150v1500 | R200v2000 | R300v3000 |
|---|---|---|---|---|
| 作弊 ON（现状）g=8000 | 56.8° | 39.8° | 36.1° | 38.3° |
| 作弊 OFF g=8000 | **56.8°** | **39.8°** | **36.1°** | **38.3°** |
| 作弊 OFF g=2200 | 32.6° | 31.9° | 33.3° | 37.4° |
| g=2200 + vd 0.0015 | **24.1°** | **24.6°** | **26.7°** | **31.8°** |

**关掉作弊对绕圈毫无影响** —— 因为绕圈时 5d/5e 本来就被旁路。
改善「往外甩」观感的真正手段是**降低重力 + 降低阻尼**，不是那套判据。

另：线性往返（60px/300px/s、120/600、200/1000、300/1500、350/2000）的
`_centripetal` 触发率恒为 **0.0%** —— 判据本身是稳的，只是没必要存在。

## 四、调度层与表现层

### 4.1 子步量化抖动（高刷屏反而更抖）

`renderer/rope.js:330` 用 `willRun = min(maxSteps, floor(accumulator / h))` 取整。
600px/s 匀速拖动，每帧子步序列：

```
 60Hz → [4,4,4,4…]              帧间 tip 位移 stdev/mean  15.3%
120Hz → [2,2,2,2…]              15.1%
144Hz → [1,2,2,1,2,2…]          31.1%   ← 每三帧有一次单步
165Hz → [1,1,2,1,2…]            36.5%
240Hz → [1,1,1,1…]              15.1%
360Hz → [0,1,1,0,1,1…]          73.2%   ← 每三帧有一帧完全不推进物理
```

**144Hz 屏上相邻帧角度平均变化 1.434°，是 120Hz（0.348°）的 4 倍。**

现状之所以「看起来还行」，是因为 `droop = 0.9` 的硬钳把抖动也一起压扁了
（dt 敏感性实测 spread 只有 1.0°）。**一旦松开天花板，这个量化问题会立刻暴露**
（候选 R1 的 dt spread 就是 5.8°）。

另外主进程用 8ms 轮询 `screen.getCursorScreenPoint()`（125Hz），与 rAF（60/144Hz）不同源。

### 4.2 表现层：已有摆角被二次衰减

```js
// renderer/doll.js:288-299
let rawAngle = hasRope ? rope.tipAngle : 0;
if (Math.abs(rawAngle) < dz) rawAngle = 0;              // dz = 0.10 rad = 5.7°
const fk = 1 - Math.exp(-dtSec / 0.06);                 // 60ms 一阶低通
this._bodyAngle += (rawAngle - this._bodyAngle) * fk;
const bodyAngle = this._bodyAngle * cfg.doll.bodyRotateRatio;
```

实测可见角 vs 绳角：

| 拖动速度 | 绳最大角 | 熊最大角 | 停手后平均 | **<1° 帧占比** |
|---|---|---|---|---|
| 300 px/s | 26.4° | 21.4° | 1.06° | **74%** |
| 600 | 30.6° | 25.6° | 1.27° | **72%** |
| 1200 | 33.9° | 30.3° | 2.35° | **60%** |

峰值损失其实不大（死区对峰值影响小），但**停手后 60~74% 的帧角度严格为 0**，
「不动了」的观感全部来自这里。

### 4.3 更深的问题：熊没有自己的动力学自由度

`renderer/doll.js:301-313` 只是 `translate → rotate(bodyAngle) → drawImage`。
**没有转动惯量、没有重力力矩、没有角阻尼** —— 所谓「摆动」是把绳的弦角低通后画上去。

物理上熊是个有质量的刚体，挂在绳端，应该受重力力矩摆动。
`_probe_ay.js` 给它加了真实自由度（支点=绳端，Lc = 熊高/2 ≈ 43px，g=1600，ζ=0.45）：

```
amp 15 f1.0   ownDOF 37.3°  vs 弦角 36.3°
amp 40 f1.2   ownDOF 24.5°  vs 45.4°
amp 80 f1.5   ownDOF 173°   vs 152.7°    ← 倒挂
amp150 f1.8   ownDOF 179.8° vs 130.4°
amp250 f2.2   ownDOF 179.6° vs 139.1°
dt 不变性：60Hz 173° / 120Hz 179.8° / 144Hz 178.3° / 240Hz 180°
```

⇒ **熊的独立动力学必须自带角度软限幅**，否则比现状更糟。
绳子只有 60px，熊自己的摆摆动比绳快得多，两者频率不同就打架。

## 五、候选方案与验收矩阵

### 5.1 推荐配置（候选 R2）

| 参数 | 现值 | 建议 | 理由 |

### 5.3 软限幅的正确写法（踩坑记录）

**错误写法一：纯刚体旋转限幅**

```js
const d = -over * rotStiff;   // over = max(0, |angle| - limit)
```

实测：instant-reversal 下 body 冲到 112~137°，**因为旋转不耗能，熊会真的翻上去**。
纯旋转限幅会把角度「钳」在限幅附近，而不是「压回」。
（好处：纯旋转**精确保持所有段长**，不会像 `scaleY` 那样注入拉伸。）

**错误写法二：与未收敛的 PBD 交替**

在子步之间插软限幅 → 链长飞到 **997px / 726px**（rest 60）。

> **铁律：几何/姿态修正必须在 PBD 约束求解收敛之后，不能与未收敛的求解交替。**

**错误写法三：限幅点太紧**

试过 tanh 42° + 20°，结果是整段顶到限幅、丢掉动态范围：

```
amp15f1 52.5° / amp40f1.2 61.2° / amp80f1.5 61.4° / amp150f1.8 58.5° / amp250f2.2 56°
```

> **限幅点要留足够余量，让「能感觉到速度差异」发生在限幅以下。**

## 九、一句话总结

这次重构的核心不是"调参"，而是**把姿态钳位换回真正的动力学**：

- 数值底座：删掉 `_lastH`/`ratio` 死代码，`velocityDamping` 换成有物理量纲的 `dampingPerSecond`
  （`keep = exp(-k·h)`）——这一条不修，任何参数实验的结果都不可信。
- 物理模型：删掉 5d 单调下垂 / 5e 下垂下限 / 5e-2 等比缩回 / 5f 兜底这四道几何投影，
  换成**保长的 `_limitBend` 绕关节纯旋转**（3 轮与长度约束交替迭代），并删掉 `_centripetal` 整套旁路。
- 表现层：限幅从物理层挪到**渲染层 tanh**（45°+18°），这样绳能翻到指针上方（R15）而画出来的娃娃角不跟着翻（**第 29 轮已删除这道限幅**）；
  死区 0.10→0.02、低通 tau 硬编码 0.06→`bodyAngleTau: 0.08`。

结果是 R13 / R14 / R15 三项**同时**达成：
娃娃角动态范围 1.62×→**1.99×**、自由摆 tau 0.90s→**3.09~3.42s**、
周期 0.50s→**0.773~0.780s**（2 节时与简单摆 `2π√(L/g)` 误差 ≤0.9%；第 4 轮改 3 节后要用链式刚体摆做基准）、
绳端翻到挂点上方 **0%→30.3%** 帧、
帧率无关性 spread **0.07°**、fixedStep 无关性 spread **0.14°**、回归测试 **17 组全过**。

代价：`doll.angleLimit` 之后成为唯一的观感上限（peakV ≥ 302px/s 时全部封顶 63°），
要更"疯"就调它，见 8.4。

> **第 5 轮（m01516）补充：参数最终交给了用户自己。**
> 用户反馈「物理效果有点过快过强了，能否增加设置菜单」，于是新增了独立设置窗口
> （`Ctrl+Alt+S`）。这件事与本文的结论直接相关：
>

>    出厂 63° 封顶，而普通人手晃（正弦 40px@1.2Hz，峰值速度 302px/s）就已经顶到 62.9°，

> 2. **1.2 说的「R13/R14 被同一个 k 同向绑死」在面板上变成了两个滑块**。
>    `gravity`（周期）+ `dampingPerSecond`（tau）必须一起动才能「慢而不猛」，
>    所以预设里两者是按比例一起给的（柔和 g2400/k0.26、活泼 g4000/k0.20）。（第 6 轮已扩为 7 档，见下）
> 3. **数值安全阀不进面板**：`fixedStep` / `maxStepsPerFrame` / `maxAccumulator` /
>    `maxBend` / `bendIterations` 全部留在 `config.js`。理由见 2.1 与 2.2 ——
>    这几个参数的破坏力是「整个引擎手感变掉」，不是「难看一点」。
>
> 第 5 轮的验收数据（绳长 60.5px、3 段）：
>
> | 预设 | 周期 | tau | 匀速 500px/s 平均角 | 正弦 40@1.2 | 正弦 80@1.5 |
> |---|---|---|---|---|---|
> | 标准（出厂） | 0.789s | 3.44s | 2.75° | 62.9° | 63.0° |
> | 柔和 | 0.920s | 4.28s | 7.01° | 44.0° | 44.0° |
> | 活泼 | 0.714s | 3.69s | 1.74° | 72.7° | 73.0° |
>
> 注意「柔和」把匀速倾角从 2.75° 抬到了 7.01° —— 这是**符合预期**的：
> 闭式解 `tanθ = (k·v + drag·v²)/g` 里 g 降幅（2400/3300 = 0.73）大于 k 降幅
> （0.26/0.30 = 0.87），所以低速段的偏角变大。用户要的是「慢一点」，偏角变大反而更像真摆。
>
> 细节见 [04 D7](04-已知缺陷与待修.md) 与 [02 第八节](02-系统架构.md)。

> **第 6 轮（m02035）补充：3 档 → 7 档，并且档位需要「应用」确认。**
> 第 5 轮的 3 档被实测证明**区分度不够**：柔和/标准/活泼的周期只有 0.920 / 0.789 / 0.714s，
> 相邻档差 0.10~0.13s，人手感知不明显。第 6 轮扩到 7 档，关键改动是把低档的
> `gravity` 压到 1400~2100（第 5 轮最低只到 2400），周期拉开到 1.178 / 1.069 / 0.963s，
> 相邻差 0.11~0.16s，配合 `angleLimit` 从 17° 到 64° 的封顶差异，七档手感才真的不同。
>
> 这与本文 **1.2** 的结论完全一致：既然「慢」和「大」由同一个 g 的两头决定，
> 那就干脆把 g 的整个可用区间切成 7 段让用户自己挑，而不是替他选一个折中值。
> 七档的 `tau` 刻意压在 3.32~3.66s 不拉开（降 k 与降 g 的效应互相抵消），
> 因为用户抱怨的是「太快太强」，不是「停不下来」—— 要改 tau 请单独拖「晃动持续」。
>
> 另一处与本文 **8.4** 相关的设计：`angleLimit` 决定高速段的封顶（`limit + overshoot`），
> 七档把它从 17+18=35° 一直排到 64+18=82°，**正好覆盖「日常晃不撞顶」到「怎么甩都很夸张」**。
> 详见 [04 D7](04-已知缺陷与待修.md)。
