## D2 · 左右移动时小熊几乎不转 —— ✅ 已修复（第 3 轮重构）

**状态**：✅ 已修复，对应需求 R13 / R14。完整诊断与验收数据见
[09-物理评审与重构方案](09-物理评审与重构方案.md)。

### 为什么本条目原先的「修复方向」是错的

原条目建议「放开死区 0.10→0.02 + 减小 damping 0.030→0.010」。
第 3 轮实测（`_probe_bi` 系列）证明**这两条合计只把动态范围从 1.62× 提到 1.67×，
主客观都没有变化**；再叠加 0.12s 低通甚至更差。

真正的原因是两个：

1. **摆角有数学硬上限**。`minDroopRatio: 0.9` 的语义是
   「绳端竖直距离 ≥ 绳长 × 0.9」，绳长恒定时等价于
   **θ_max = acos(0.9) = 25.8°**。不论拖多快都撞不破这个天花板。
2. **阻尼参数没法只调一半**。闭式解 `tan(θ) = (k·v + drag·v²)/g` 里
   `k = -ln(1-velocityDamping) × fixedStepHz`，同一个 k 又决定
   自由摆的 `tau = 1/k`。R13（要偏角）和 R14（要慢衰减）被同一个旋钮同向绑死。

### 第 3 轮的做法

| 改动 | 从 | 到 | 理由 |
|---|---|---|---|
| 摆角天花板 | `minDroopRatio: 0.9` | **删除**（换 `maxBend: 1.50`） | 只限单关节弯曲、不限绝对朝向，天花板消失 |
| 重力 | 8000 | **4000**（第 4 轮再调至 3300） | 周期从 0.50s 变成 0.773s，接近真实摆 |
| 阻尼 | `velocityDamping: 0.006` | `dampingPerSecond: 0.30` | 换算成 1/s，与 fixedStep 解耦 |
| 空气阻力 | 0.0012 | 0.00015 | 高速时不再把绳子拖成杆 |
| 死区 | 0.10 | 0.02 | 同上 |
| 限幅方式 | 硬钳位（几何投影） | **渲染层 tanh 软限幅 45°+18°** | 物理层完全不限幅，只限制画出来的角度 |

### 验收数据（`verify.cjs`，屏高 864 / 绳长 60.5px）

| 指标 | 旧版 | 第 3 轮 |
|---|---|---|
| 匀速 500px/s 娃娃平均角 | ≈2°（被死区吃掉） | **2.21°** |

## D6 · 绳子变成硬性钢棍直棍 —— ✅ 已修复（第 4 轮，m01090）

**现象**：用户 m01090「连接线成硬性钢体直棍了，更改为 3~5 个节点的软绳」。

**根因（两个，叠加）**：

1. **段数/节点数语义搞错（主因）**。`renderer/rope.js:76` 的 `rebuild(len, count)`
   第二个参数是**质点个数**，而 `renderer/config.js` 的第 3 轮值写的是 `segments: 2`，
   `renderer/main.js` 又直接 `rope.rebuild(len, segs)`。于是拿到的是「2 个质点 = 1 段」，
   **数学上永远是一条直线，没有任何弯曲自由度**。同源 bug 还有一处：
   `if (rope.count !== segs || ...)` 拿节点数比段数 → 条件恒真，每次 resize 白重建一次绳子。

2. **`_limitBend` 会把锚点推开**。原实现的修正是无条件的
   `this._rotateAbout(a, b, phi)` / `this._rotateAbout(c, b, -phi)`，
   而 `j = 1` 时 `a` 就是 `pts[0]`（锚点，`invMass = 0`）—— 每次调用都把锚点
   从鼠标位置推开 1.0~3.2px，等于绳子自己拽着指针跑。已改为按逆质量加权：
   `phi * (wa / wsum)` / `-phi * (wc / wsum)`，`wa = 0` 时锚点纹丝不动
   （超限帧从 4.4% → 0.0%）。

**第 4 轮的改动**：

| 改动 | 从 | 到 | 理由 |
|---|---|---|---|
| `chain.segments` | 2（= 1 段，直线） | **3**（= 4 质点 = 2 个可弯关节） | 1 段必然直线；2 段只有 1 个关节、弧很僵；3 段中间节点最多偏离首尾连线 **20.1px（占绳长 33%）** |
| `physics.gravity` | 4000 | **3300** | 质量沿绳分布后简单摆公式失效，按**链式刚体摆**重标定以保持 0.77s 周期 |
| `physics.bendIterations` | 3 | **10** | 关节越多越难收敛：4 段绳 3 轮只压到 69.2°（不合格），10 轮 93.6° |
| `_limitBend` 修正量 | 无条件对半分 | **按逆质量加权** | 否则会把 `invMass = 0` 的锚点推开 |
| `bendRounds` 循环收尾 | `_solveConstraints(1)` | **再补一次 `_limitBend`** | 否则刚压下去的角度会被拉回来一部分 |
| `renderer/main.js` 重建判断 | `rope.count !== segs` | `rope.count !== nodeCount` | 拿节点数比段数 → 条件恒真、每次 resize 白重建 |

**为什么不是 5 段**：折叠问题已被 `_limitBend` 彻底解决（实测所有拓扑 folds 都是 0），
现在的约束变成**长度稳定性**——60s 剧烈甩动实测：

| 段数 | 质点 | 链式理论周期 | 实测周期 | 误差 | folds | 链长范围 | 最小关节 |
|---|---|---|---|---|---|---|---|
| 1 | 2 | 0.8531s | 0.8512s | -0.2% | 0 | 60.50~60.50px | 180° |
| 2 | 3 | 0.8007s | 0.8043s | +0.4% | 0 | 60.50~60.51px | 113° |
| **3** | **4** | **0.7713s** | **0.7772s** | **+0.8%** | **0** | **60.49~60.84px** | **94°** |
| 4 | 5 | 0.7562s | 0.7631s | +0.9% | 0 | 60.19~63.05px（漂） | 93° |
| 5 | 6 | 0.7470s | 0.7546s | +1.0% | 6 | 59.79~67.72px（严重漂） | 89° |

⇒ **3 段是唯一「能弯出明显弧度 + 链长稳定」的配置**。

**软度实测**（sag = 中间节点偏离首尾连线最大距离，绳长 60.5px）：

## D7 · 物理效果过快过强，用户无法自己调 —— ✅ 已实现设置菜单（第 5 轮 m01516；第 6 轮补 7 档位 + 应用按钮 m02035）

**用户原话 (m01516)**：「物理效果有点过快过强了，能否增加设置菜单，可以进行手动的调整？」

**这句话里其实有两个独立的问题**：

### 问题 A：不是「物理调错了」，是「日常操作全撞天花板」

出厂 `doll.angleLimit: 45` + `angleLimitOvershoot: 18` ⇒ 画出来的旋转角最多 63°。
（第 12 轮起面板上限放到 180° = 不限制，见 R20；下面的标定数据仍是出厂 45° 时测的。）
但普通人手晃（正弦 40px@1.2Hz，峰值速度只有 302px/s）就已经顶到 62.9°。
于是**无论手快手慢，熊看起来都是同一个倾角**，没有层次感，主观上就是「永远甩那么大」。

单扫 `angleLimit`（其余全默认，绳长 60.5px、3 段）：

| `angleLimit` | 18 | 22 | 26 | 30 | 36 | 45 | 60 |
|---|---|---|---|---|---|---|---|
| 正弦 40px@1.2Hz 的娃娃封顶角 | 36.0° | 40.0° | 44.0° | 48.0° | 54.0° | 62.9° | 77.7° |
| 匀速 500px/s 的平均角 | 2.75° | 2.75° | 2.75° | 2.75° | 2.75° | 2.75° | 2.75° |

⇒ 这个参数**只影响高速段的封顶，不影响低速段**，是「过强」的最优旋钮。

### 问题 B：「过快」只能靠降重力，但降重力会让「偏角更大」

闭式解 `tanθ = (k·v + drag·v²)/g` 与 `T ∝ 1/√g` 是同一个 g 的两头：
降 g 摆动变慢（用户想要的），但拖动倾角变大（用户不想要的「更猛」）。
所以**降 g 必须同步按比例降 k**，两者同比例降才能「慢而不猛」。

### 做法

新增独立设置窗口（`Ctrl+Alt+S` / 托盘「设置…」），10 个可调项分 3 组 + 一键预设。
（第 11 轮追加「指针」组两项，现为 **12 项分 4 组**；第 13 轮在页面底部追加「诊断记录」区，
不算可调项 —— 那个按钮不改变任何物理参数。）
架构与数据流见 [02 第八节](02-系统架构.md)，参数边界见 [01 第四之二节](01-需求与约束.md)。

## D3 · 绳子不允许翻到指针上方 —— ✅ 已修复（第 3 轮重构）

**状态**：✅ 已修复，对应需求 R15。详见 [09-物理评审与重构方案](09-物理评审与重构方案.md)。

### 真正的拦路虎不是 maxAngle

原条目以为罪魁是 `chain.maxAngle: 0.55`。实际上 `maxAngle` 在第 2 轮就已经删掉了
（`330bd52 refactor: 移除摆角硬限幅 maxAngle`），但 R15 依然没达成 ——
因为**真正禁止翻转的是「单调下垂」几何投影** `monoDrop`（5d / 5f 段）：

```
每个节点必须严格比上一个节点低 monoDrop(=1) px
```

这在语义上就等于「绳端永远不许跑到挂点上方」。

### 实测证据（2500px/s 往返 1800 帧）

| 配置 | 折叠次数（相邻段方向差 >90°） | 绳端在挂点上方的帧占比 |
|---|---|---|
| 旧版（monoDrop 1 / droop 0.9） | 8 | **0%** |
| monoDrop 1 / droop 0 | 529 | 2% |
| **monoDrop 0 / droop 0** | 211 | **51%** |

关掉 `monoDrop` 后「翻上去」立刻出现（0% → 51%），代价是折叠次数暴涨 ——
这也是为什么不能简单删掉了事。

### 第 3 轮的做法

用**只限关节、不限朝向**的 `_limitBend(maxBend)` 替代：

```
对每个内部关节 j，取 v1 = a - b、v2 = c - b（都以关节为原点）
alpha = atan2(v1 × v2, v1 · v2)
注意：这个约定下 伸直时 |alpha| = pi、对折时 |alpha| = 0
弯曲角 bend = pi - |alpha|，超过 maxBend 时绕关节纯旋转修正
```

纯旋转**精确保段长**，不会像 `scaleY` 那样注入拉伸。
配合 `bendIterations: 10` 与长度约束交替迭代（第 4 轮从 3 提到 10，关节越多越难收敛）（单轮最差关节 77.9° / 总长 107px，
3 轮收敛到 154.4° / 91.8px）。

验收：300px @ 6rad/s 往返 → **30.3% 帧绳端高于挂点**（旧版恒 0%）；
60s 剧烈甩动链长恒为 60.48px（=rest）、最小关节夹角 180.0°、零 NaN。

## D1 · 系统鼠标箭头仍浮在自绘指针上 —— ✅ 第 11 轮结案（按设计不修）

**状态**：**已结案**。不是「还没攻克」，是**架构上不可达**，因此改为放弃自绘指针、直接用系统指针。

### 现象（历史）

程序自己画了一个白色箭头当鼠标，但 Windows 的原生箭头仍叠在上面，出现双指针。

### 结论：这条路走不通，原因有三条

1. **`ShowCursor(bool)` 改的是调用线程的显示计数**，只影响该线程拥有的窗口。
   覆盖层是 `setIgnoreMouseEvents(true, {forward:true})` + `focusable:false` 的穿透窗，
   **从不持有鼠标、从不获得焦点** —— 指针下方是**别的窗口**在处理 `WM_MOUSEMOVE`，
   显隐由那个窗口的线程决定。⇒ 从本进程调 `ShowCursor` 永远改不到它。

   实测证据（当时记录的）：

   ```
   ShowCursor(false) 返回 -1        （本进程计数确实减了）
   GetCursorInfo()   返回 flags: 1  （指针仍然可见）
   SetCursor(0)                     （也无效）
   ```

2. **系统指针不是窗口**，由 DWM 画在独立的硬件光标平面上，任何 `HWND_TOPMOST`
   都盖不住。所以程序画的任何东西（包括自绘指针）永远在系统指针**下面**一层。

3. **`SetSystemCursor` 换空白光标是全局副作用**，不能接受：
   只要有置顶窗口压在覆盖层上（右键菜单 `#32768`、设置面板本身、任务栏
   `Shell_TrayWnd`、独占全屏游戏），屏幕上就会**完全没有指针** ——
   而那恰恰是用户要点菜单的时刻。更糟的是进程被强杀后会留下全系统无指针。

### 决策（m03147 / m03155）

**放弃自绘指针，改用 Windows 系统指针 + 手动偏移。**

- 删掉 `system-cursor.js`（71 行）、`renderer/cursor.js`（152 行）、
  `main.js` 里 `applySystemCursor*` / `foreignWindowAtCursor` / koffi `win32` 整段、
  `ui:flag` 广播链路、`renderer/doll.js` 的 `cursorBox()` 与自绘指针绘制。
- `renderer/doll.js` 的挂点简化为：
  ```js
  attachPoint(cursorX, cursorY) {
    const c = this.cfg.cursor;
    return { x: cursorX + (c.attachOffsetX || 0),
             y: cursorY + (c.attachOffsetY || 0) };
  }
  ```
- 默认偏移 `(7, 19)`（100% 缩放下系统箭头约 12.3 × 18.6，正好落在下边缘尖角下方）。
  **程序读不到系统指针的尺寸**（辅助功能 1~15 档缩放、第三方主题都会改），
  所以设置面板加了一组「指针」两个滑块（`-40 ~ +90`），按自己的指针调一次即可。
- 净效果：`main.js` 19924 → 14168 B，原生依赖 koffi 归零，`package.json` 的
  `dependencies` 整个消失。

### 代价（明确接受）

- 失去视觉统一性（自绘指针原本是 `docs/00-索引.md` 的 ✅ 特性）。
- 指针永远在绳子/吊环上面。快速甩动时绳子只能表现为**从指针背后穿过**，
  不可能盖住指针（R15 仍成立，只是表现形式变了）。
- 所有指针形状（arrow / hand / I-beam）共用一套偏移。
- 系统截图 / `BitBlt` / `PrintWindow` 抓不到系统指针 ⇒ 偏移量的验收
  必须用**数值断言**（给 `attachPoint` 装探针，检查 `attach − hotspot == offset`），
  不能靠截图。实测：`(7,19)→Δ(7,19)`、`(60,19)→Δ(60,19)`、`(7,70)→Δ(7,70)` 全部通过。

### 附带解除的约束

旧版 `Stop-Process -Force` 会绕过 `will-quit` 里的 `sysCursor.restore()`，
导致**系统指针永久消失**（这是约束 C4 的由来）。第 11 轮起程序对系统指针
**无任何全局副作用**，该风险消失；C4 保留只是为了不留 electron 残留进程。

## D4 · 测试环境无法可信地「钉住」指针

**状态**：✅ **已修复（P0）**。

见 `docs/03-测试方法论.md` 铁律 1。此前所有「钉住坐标再截图」的测试方法都不可信。

**修法**：`renderer/config.js` 的 `debug.lockPointer` 把指针控制权做成两种运行时模式：

- 快捷键 **`Ctrl+Alt+L`**
- `window.__doll.lock(true/false)`

`window.__doll.locked` 是 getter，永远反映实时值。

**测试纪律**：测前 `lock(true)` + `setPointer()`；**测完必须 `lock(false)` 把鼠标还回去**；

## D9 · 打开设置面板时娃娃会失去置顶 —— ✅ 已修复（第 10 轮 m02958）

用户 said (m02958): 「你把置顶设没了」。现象是打开设置面板调参的那段时间里，
娃娃会被浏览器、聊天窗口等其它窗口盖住；关掉面板后置顶自动恢复，所以初次很容易漏掉。

### 根因

`main.js` 的 `openSettings()` 在 `ready-to-show` 里执行了 `win.setAlwaysOnTop(false)`，
等面板 `closed` 再 `setAlwaysOnTop(true, "screen-saver")` 恢复；`toggleVisibility()` 里
还有一条 `if (!settingsOpen) win.setAlwaysOnTop(true, "screen-saver")` 的跳过逻辑。

降级再恢复这个**过程**本身没错 —— 面板是普通窗口，不把覆盖层降下来，
1536x864 的透明窗就会把面板压在下面（第 5 轮 b37 就是为修这个才加的）。
问题出在**持续时间**：面板开着的整段时间里覆盖层都留在非置顶层。

### 修法（比降级更简单，而且两边都不丢）

覆盖层**永远不离开置顶带**，把面板自己也提成置顶，再 `moveTop()` 压到覆盖层之上：

```js
// ready-to-show
win.setAlwaysOnTop(true, "screen-saver");          // 覆盖层保持
settingsWin.setAlwaysOnTop(true, "screen-saver");  // 面板也进置顶带
settingsWin.show();
settingsWin.moveTop();                              // 再压到覆盖层之上
settingsWin.focus();

// closed
win.setAlwaysOnTop(true, "screen-saver");
win.moveTop();                                      // 面板消失后回到置顶带最上面
```

关键点：覆盖层是 `setIgnoreMouseEvents(true, {forward:true})` 的鼠标穿透透明窗，
**即使被面板压住也不影响点击**，只需要保证面板在它之上。所以降级覆盖层从来不是必需的。

### 验收

用 koffi 读 `GetWindowLongPtrW(hwnd, -20) & 0x8`（`WS_EX_TOPMOST`）。
> 注：koffi 已于第 11 轮从依赖中删除，此命令要复现需临时 `npm i koffi`。

| 时机 | 覆盖层 topmost | 面板 topmost |
|---|---|---|
| 启动后 | true | — |
| `Ctrl+Alt+S` 打开面板 | **true**（旧版是 false） | true |
| 再按一次关闭 | true | — |

z 序验证：从覆盖层沿 `GetWindow(h, GW_HWNDPREV=3)` 往上走，第 1 步就遇到设置面板
⇒ 面板确实压在覆盖层之上，娃娃不会遮挡面板。

顺带把 `Ctrl+Alt+S` 改成**开关**（`toggleSettings()`：开着就关、没开就开），
避免面板被留在前台反复点。

### F9 · 固定步长一变，整个物理引擎的"手感"就变了
- 根因 A：`renderer/rope.js:440-441` 的变步长校正 `ratio = h / (this._lastH || h)`
  里，`this._lastH` **只在构造函数赋过一次初值 1/240，全仓库没有任何再赋值**。
  于是 `ratio ≡ h × 240`：`fixedStep = 1/60` 时每子步速度 ×4（指数爆炸），
  `1/480` 时每子步速度 ×0.5（过阻尼）。自由落体 0.5s：1/240 实测 4000.0px/s
  （解析值 8000×0.5 = 4000，正确），1/480 实测 **33.3px/s**。
- 根因 B：`velocityDamping` 是**每子步**乘性衰减 `keep = 1 - vd`，
  1 秒后速度留存率 60Hz 0.697 / 480Hz 0.056，跨帧率相差 1252%。
- 修法：删掉 `ratio` 与 `_lastH`；阻尼改为物理量纲 `dampingPerSecond`，
  实现为 `keep = Math.exp(-k * h)`（k 单位 1/s，与 h 完全解耦）。
- 验证：匀速 500px/s 的娃娃稳态角 @fixedStep 1/60~1/480 = 2.36 / 2.27 / 2.21 / 2.22°，
  **spread 0.14°**；@帧率 60/120/144/240Hz **spread 0.07°**。

### F10 · 弯曲上限 `_limitBend` 的公式把"伸直"和"对折"判反了
- 根因：`v1 = a - b`、`v2 = c - b` 都以关节 b 为原点，这个约定下
  **伸直时 |alpha| = π、对折时 |alpha| = 0**。原代码 `if (absA <= maxBend) continue;`
  等于放过了完全对折、反而去掰直正常伸直的绳子（实测最差关节 0.0°）。
- 修法：`const bend = Math.PI - absA;` 再比较 `maxBend`。
- 另一处：`willRun = Math.floor(accumulator / h)` 在 dt = 1/60、h = 1/240 时
  算出 3.9999999999999996 → floor 成 3，长期在 3/4 步之间抖动。加 `1e-9` 修正。
- 验证：`rope.test.cjs` 用例 [15] 最差关节 145.4°（下限 89.1°）。

### F11 · 自由摆的衰减时间常数只有 0.9s（"拽死"的手感）
- 根因：`velocityDamping: 0.006` 在 1/240 子步下等效 `k = -ln(1-0.006)×240 ≈ 1.44/s`，
  振幅衰减速率 `k/2 = 0.72/s` ⇒ `tau = 0.69s`。
- 另一个此前未被发现的耗散源：**PBD 距离投影本身**。
  实测 `b_num ≈ 47·h`，且 `b_num ∝ 1/L ∝ ω²`（ω = sqrt(gravity/绳长)），
  正确模型是 `b = k/2 + ω²·h/2`、`tau = 1/b`。
- 修法：`dampingPerSecond: 0.30`（k = 0.30/s）。`b = 0.15 + 0.0926 = 0.243` ⇒ 理论 tau 4.12s。
- 验证：实测 tau 3.09~3.42s（多节链） / 3.98s（2 节，理论 4.12s）。

### F12 · 设置面板的三处 bug（全部是 E2E 阶段才暴露的）
- **F12-a · `controls.length = 0`**：`controls` 是普通对象，这行会真的创建一个名为
  `"length"` 的键。之后 `Object.keys(controls)` 取到 `controls["length"] === 0`，
  `refreshReadouts()` 里读 `0.field.readout` 抛
  `Uncaught TypeError: Cannot read properties of undefined (reading 'readout')`。
  后果极隐蔽：**除被拖的那一项外，所有字段的显示值全空**，主进程收到的载荷变成 `{}`，
  预设和恢复默认都不刷新 —— 但面板本身不白屏，看上去「只是没反应」。
  修法：`for (const k of Object.keys(controls)) delete controls[k];` + 遍历时 `if (!c || !c.field) continue;`。
  **教训：JS 数组用 `length = 0` 清空；对象要用 `delete`，写错了不会报错。**
- **F12-b · `fmt()` 把最后一个字符吃掉**：原写法 `.replace(/.$/, "")` 是想去掉尾随小数点，
  但 PowerShell here-string 把正则里的 `\.` 吃成了 `.`，于是 `.$` 变成「任意一个字符 + 结尾」，
  `"0.300"` → `"0."`、`"0.000150"` → `"0.0001"`（末位的 `5` 和 `0` 被删）。
  修法：`out = out.replace(/0+$/, ""); if (out.endsWith(".")) out = out.slice(0, -1);`。
- **F12-c · 补丁脚本撞 CRLF**：`main.js` 是纯 CRLF，补丁脚本里的多行模板是 LF ⇒
  `split(old).length - 1 === 0`，**10 处替换全部命中 0 次**。
  好在脚本在写盘前 `throw`，文件没被破坏。修法：读入后先 `raw.replace(/\r\n/g, "\n")` 再匹配。

**共同教训**：这三个都不是「逻辑想错了」，而是**跨工具 / 跨编码的字面量失真**。
凡是在 PowerShell here-string 里写正则或跨行模板，都要先 `console.log` 出那几行对照，
或者改用 `endsWith` / `indexOf` 这类不含反斜杠的写法。

### F13 · 第 6 轮（7 档位 + 应用按钮）暴露的四处 bug

- **F13-a · `applied` 用了扁平形状却拿 `S.toFlat()` 去拍**：`toFlat()` 只认**嵌套**形状
  （`{physics:{gravity:1400}}`），传扁平对象进去恒返回 `{}`，于是「已生效档位」
  （实心蓝）**永远算不出来**，七个 chip 全是灰的。
  修法：`applied` 全程保持嵌套，`push()` / `get()` / `onChanged` 三处统一赋值，
  只在 `refreshChrome()` 里 `S.toFlat(applied)` 拍一次。
  **教训：同一个状态量不能有的地方存扁平、有的地方存嵌套，转换只能发生在比较的瞬间。**
- **F13-b · 页脚被顶出可视区**：`body { min-height: 100vh }` + `.groups { flex:1 }`
  时，flex 子项的 `min-height` 默认是 `auto`，它会被内容撑开、拒绝收缩，
  于是滚动条长在整页上、页脚（含最重要的「应用」按钮）被推到 1000px 以下。
  面板 620x800 时用户**必须滚到底才能看到「应用」**，等于按钮不存在。
  修法：`html, body { height: 100% }`、`body { height: 100vh; overflow: hidden }`、
  `.groups { min-height: 0; overflow-y: auto }`。
  **教训：`min-height: 0` 是 flex 滚动容器的必需项，缺了它 `flex:1` 不收缩。**
- **F13-c · 档位 chip 里两段文字粘在一起**：chip 内容是 `"1 档"` + `<span class="d">1.18 秒</span>`，
  靠 `.d { margin-left: 6px }` 分隔。`.chip` 是普通行内盒时 margin 会被基线对齐吃掉，
  渲染成 `"1 档1.18 秒"`。修法：`.chip { display: inline-flex; align-items: baseline; gap: 7px }`
  并删掉 margin。**教训：按钮里的多段文字用 flex + gap，不要用 margin。**
- **F13-d · 托盘 radio 的勾不跟着走**：`applyPresetById()` 改完 `currentOverrides` 后没重画菜单，
  radio 的勾停在旧档。修法：函数末尾补 `rebuildTrayMenu()`。
  注意这和「拖滑块时不要 rebuildTrayMenu」（会闪）不冲突 —— 换档是低频操作。

### F14 · 第 13 轮（诊断记录器）暴露的两个 bug

- **F14-a · `status` 写成 getter**：`Recorder` 内部三处都写 `this.status()`，
  但实现写成了 `get status() { ... }`，于是 `this.status()` 变成"调用一个对象"，
  直接 `TypeError: this.status is not a function`。
  修法：改回普通方法。**教训：内部调用写法先定（`this.x()` 还是 `this.x`），
  再决定实现用方法还是 getter —— 两者的调用语法不一样。**
- **F14-b · `_sample()` 里的配置兜底少一层，抛一次断整帧**：
  原写法 `(r && r.cfg && r.cfg.doll) ? r.cfg.doll : (window.CONFIG ? window.CONFIG.doll : {})`，
  当 `window.CONFIG` 存在但没有 `doll` 键时，`ternary` 的 false 分支拿到 `undefined`，
  抛 `TypeError: Cannot read properties of undefined (reading 'bodyRotateRatio')`。
  **真正致命的不是这个 TypeError，而是它抛在 rAF 主循环里** ——
  `frame()` 没有 try/catch，抛一次整个渲染循环就死了。
  修法：三层兜底 `(r && r.cfg && r.cfg.doll) ? ... : (window.CONFIG && window.CONFIG.doll) ? ... : {}`。
  **教训：主循环里调用的东西，每一个"可能没有"的输入都必须兜到底；
  兜底链的最后一级要保证是具体的 `{}`，不能是另一个可能 undefined 的表达式。**
