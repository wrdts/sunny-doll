## 零、这一段的历史：三项里只有 T1 活下来了（第 27 轮结论）

用户 (m07533) 提的三项需求，看起来是三个独立功能，当时判断为**同一个瓶颈的三个阶段**：

| 需求 | 表面上的样子 | 当时的判断 | 现在的状态 |
|---|---|---|---|
| T1 图片端线条锚点位置 | 「让绳子别老挂在图片正中间顶上」 | 娃娃的**旋转原点被写死在吊点** | ✅ 第 21~24 轮完成，演进成「吊环位置编辑器 + 拖拽」 |
| T2 图片中心 / 多重质点 | 「让图片有重心，别整块跟着绳子转」 | 娃娃**完全没有任何横向自由度** | ❌ **第 27 轮撤除**（用户 m10287「将挂件认定为刚体」） |
| T3 图片弹性形变 | 「动起来有点弹性」 | 现在的拉伸只是**整体缩放** | ❌ **第 27 轮撤除**（同上） |

当时的依赖链（现已作废，留作记录）：

```
T1 线条锚点（纯渲染层，可独立开工）
 └─→ T2 多重质点（锚点必须先能离开顶点，否则质点分布没有物理意义）
      └─→ T3 弹性形变（必须先有受力点，才能驱动网格变形）
```

**为什么 T2/T3 被撤除**：T2 在数学上有硬伤 —— `step()` 是围绕静止四角的固定解析解、
`centroidIndex()` 写死 `return 2`，**没有质量分布输入**；一旦真要引入不同质量，
必须解 4~8 自由度的耦合方程（见 [03-测试方法论](03-测试方法论.md) 里显式欧拉发散的记录）。
T3 则被实测否定：**皮肤层做不出剪切** —— 一阶滞后是线性算子，平行四边形进去还是平行四边形，
实测 `puppet 关 + skin 150ms` 剪切恒为 `0.000°`。
权衡后用户选择**把挂饰当作刚体**：它只会绕吊环整体旋转，不拉伸、不变形、不滞后。
这是一个明确的产品决策，不是技术妥协 —— 刚体的行为可预测、永不抖、零额外开销。

## 二、T1 · 图片端线条锚点可调（✅ 已完成，第 21~24 轮）

### 2.1 现状

```js
// renderer/doll.js:315-316
ctx.save();
ctx.translate(anchorX, anchorY);          // 平移量 = 绳子末端
// ...
// renderer/doll.js:318-328（图片分支）
ctx.rotate(bodyAngle);                     // ← 旋转原点就是「绳子末端」
ctx.transform(sx, 0, 0, sy, 0, 0);
ctx.drawImage(this.img, -w / 2, 0, w, height);   // ← 图片从 (0,0) 往下画
```

两个写死的假设：

1. **吊点在图片顶边中点**：`drawImage` 的 y 从 `0` 开始、x 从 `-w/2` 开始，
   所以图片矩形是 `[-w/2, w/2] × [0, height]`，而旋转原点 `(0, 0)` 正好是顶边中点。
2. **旋转原点 = 吊点**：`rotate` 在 `translate` 之后，所以一切都绕绳子末端转。
   这符合「挂在钩子上的挂饰」直觉，但用户想要的是**图片上任意位置都能挂绳子**。

另外吊环是单独画的（`renderer/doll.js:241 _drawLoop(x, y)`，由 `:258 draw(state)` 调用），
它画在绳子末端，不与图片锚点关联 —— 改锚点时必须一起改，否则会出现
「绳子从娃娃肩膀穿进去，但吊环还画在头顶」。

### 2.2 设计

**唯一的契约：锚点用图片自身的相对坐标表示，与像素尺寸无关。**

| 字段 | 类型 | 范围 | 默认 | 含义 |
|---|---|---|---|---|
| `doll.anchorX` | number | `0.0 ~ 1.0` | **`0.5`** | 0 = 图片左边缘，1 = 右边缘 |
| `doll.anchorY` | number | `0.0 ~ 1.0` | **`0.0`** | 0 = 图片顶边，1 = 底边 |

默认值 `(0.5, 0.0)` **就是当前行为**，所以：**不动面板时，画面必须逐像素不变。**
这一条是 T1 的验收底线。

像素量换算（在 `renderer/doll.js` 里算，不要写进 config）：

```js
const w = height * (this.img.naturalWidth / this.img.naturalHeight);
const oy0 = -Math.min(cfg.doll.heightMax, height, cfg.doll.anchorY * height);
const ox = -w * (cfg.doll.anchorX - 0.5);
const oy = oy0;   // 负值 = 在图片内部相对顶边往下
```

> **`Math.min(heightMax, ...)` 那一项不能省。** 理由：`get dollHeight()`
> （`renderer/doll.js:72`）会把高度夹在 `[heightMin 56, heightMax 128]`，
> 而 `anchorY` 是**相对图片**的。如果将来支持超大图片，`anchorY * height`
> 可能把锚点推出图片外，视觉上会变成「绳子插在娃娃脚底下的空气里」。
> 先夹一次，宁可锚点位置不精确，也不要出现悬空锚点。

渲染链改成**绕锚点旋转、图片矩形不动**：

```js
ctx.translate(anchorX, anchorY);   // 1. 到绳子末端
ctx.translate(ox, oy);             // 2. 再走到图片上的锚点
ctx.rotate(bodyAngle);             // 3. 绕「图片上的锚点」旋转
ctx.translate(-ox, -oy);           // 4. 撤回去，图片还在原位
ctx.transform(sx, 0, 0, sy, 0, 0);
ctx.drawImage(this.img, -w / 2, 0, w, height);
```

这是标准的「绕任意点旋转」三步式。**没有任何物理改动** ——
`rope.tipAngle` 依旧是首尾连线角，变的只是「画出来的图片怎么摆」。

### 2.3 为什么这是对的做法（而不是改物理）

有人会想：锚点变到图片侧边以后，力臂变短了，摆动是不是该变小？
**不用管，也不该管。** 原因：

- 现在的模型里，娃娃对绳子**没有反作用力**（`renderer/rope.js` 里 `p0.invMass = 0`，
  绳子的另一端是「指针」，娃娃是纯渲染）。所以「娃娃的重心在哪」在物理上根本不存在。
- 一旦真的去改力臂，就会掉进「给娃娃加独立钟摆自由度」那条已知死路 ——
  [06 第五版](06-路线图与决策日志.md) 记过一次：`Lc=43px, ζ=0.45` 的实验
  直接让娃娃冲到 **173~180° 倒挂**，比现状更糟。
- 用户要的是「看起来挂在那里」，「摆多大」由 `doll.angleLimit` 控（面板里有滑块）。
  **视觉锚点和力学力臂是两件事，这一版先只做视觉。**

T2 才是真正引入「重心」的地方，那时再讨论力臂。

### 2.6 已实现（记录当时的具体做法与踩过的坑）

落地时与上面的设计有两处偏差，记在这里，免得后来者以为文档没兑现。

**偏差一：emoji 分支不是「重算 baselineY」，而是给它一个假矩形。**
emoji 不是图片，没有 naturalWidth，宽度来自字体度量（`_dollWidth()` 里
`(m.left + m.right) * (h / m.h)`）。所以锚点偏移量是同一个公式，只是 `w` 换成度量宽度、
`h` 换成 `dollHeight`。绕锚点旋转的三步式两边完全一样。

**偏差二：`_drawLoop` 的调用点位置错了要修。**
一开始把吊环画在 `ctx.save()/restore()` **内部**，结果它跟着娃娃一起被
`ctx.transform(sx,0,0,sy,0,0)` 拉伸，锚点一挪吊环就变形。
正确做法是挪到 `ctx.restore()` **之后**，自己按 `bodyAngle` 算位置：

```js
// renderer/doll.js，ctx.restore() 之后
if (cfg.rope.show && cfg.rope.loop && rope && rope.path && rope.path.length >= 2) {
  this._drawLoop(anchorX, anchorY, bodyAngle, ao.ox, ao.oy);
}
// 内部：ax = x + ox*cos - oy*sin; ay = y + ox*sin + oy*cos
```

**踩过的坑：`heightMax` 夹取必须做，而且要在「像素量」这一侧做。**
文档里写的 `Math.min(cfg.doll.heightMax, height, anchorY * height)` 是对的，
但如果写成先算 `anchorY` 再夹 `height`，400px 大图 + `anchorY = 1` 会让
`oy` 变成 `-400`，锚点跑到图片外面。`verify.cjs` 验收 10 有一条专门测这个：
`400px 大图 + anchorY=1 时 oy 被 heightMax 夹住  (-128.0px, 上限 -128)`。

**验收 10 的五条断言（`verify.cjs`）**：

| # | 断言 | 实测 |
|---|---|---|
| 1 | 默认 `anchorX/anchorY` 的偏移必须精确为 `(0, 0)` | `(0.000, 0.000)` ✓ |
| 2 | `anchorX` 0/1 => `±43px`，`anchorY 0.5` => `-43px` | `43.0 / -43.0 / -43.0` ✓ |
| 3 | `anchorY=1` 时图片整体沉到吊环下方整幅高度 | `-400.0px`（400px 大图）✓ |
| 4 | 绕任意锚点旋转时锚点位移必须为 0 | `0.0e+0px` ✓ |
| 5 | `anchorX` 0/0.5/1.0 三档弦角序列逐位相同 | 最大差 `0.0e+0 rad` ✓ |

**回归结果**：`rope.test.cjs` 17 组、`verify.cjs` 验收 1~9 与改动前**逐位一致**，
只有 3 类耗时行浮动（性能段、记录时长），属于正常抖动。

### 2.6b 语义修正：吊环钉在绳端，参数动的是图片（第 21 轮，m08270）

**用户原话**：「1、挂饰挂点应始终位于绳索末端，调节挂点位置是调节图片和挂点的相对位置
2、挂饰挂点的位置应该在最后一段绳索的末尾处，而不是最后一段绳索的开头位置」

第一版（2.6）的做法是**反的**：吊环钉在图片上的 `anchorX/anchorY` 处，
绳子末端又钉在图片顶边中点，拖滑块时吊环和图片一起动。用户要的是反过来 ——
**吊环是绳子的零件，不是图片的零件**。

改法两条：

1. `renderer/doll.js` 的 `get anchorOffset()` 语义反演。原来返回「从绳端走到图片上的挂点」，
   现在返回「**从吊环走到图片静止矩形左上角**」：
   ```js
   const px = -w * (ax - 0.5);   // 挂点在图片坐标系里的 x
   const py = ay * h;            // 挂点在图片坐标系里的 y
   return { ox: -w / 2 - px, oy: -py };
   ```
   绘制时图片矩形直接画在 `[ox, ox+w] x [oy, oy+h]`，旋转支点就是原点（= 吊环），
   于是「摆」的力臂自然等于图片质心到吊环的距离。`oy` 去掉了旧的 `heightMax` 夹取 ——
   那道护栏原本保证「挂点必须在图片内部」，反演后夹取对象变成「图片相对吊环能沉多深」，
   语义已不同，保留会得到错误结果。

2. `renderer/rope.js` 新增 `get tailPoint()`：**最后一段绳的末端点**，
   即 `pts[n-1]` 沿 `pts[n-2] → pts[n-1]` 方向再延伸 `rope.overlap` 像素。
   它与 `tipX/tipY`（最后一个**质点**）不是同一个点：柔性弯曲允许末节方向与整绳连线角不同，
   而绘制绳子时末端本来就要延伸 overlap 穿进挂饰内部遮缝 —— `_drawRope` 一直是这么画的，
   只是挂饰之前挂在 `tip` 上，所以看起来"挂点在最后一段绳的开头"。

   实测（1/60 步长、±260px@2.2Hz + ±120px@1.3Hz 驱动 1200 帧）：
   尾端与最后质点的距离恒为 `10.000px`（= `rope.overlap`）。

配套：`rope.setOverlap(px)`（`renderer/main.js` 的 `applySize` 与 `applySettings` 都会同步），
`_drawLoop(x, y, 0, 0, 0)` —— 吊环不再跟着 `bodyAngle` 转、不再被 `anchorX/anchorY` 偏移。

**顺带修的一个隐患：绳子松弛**。距离约束只限制「每段不超过 `restLen * maxStretch`」，
从不把段推回 `restLen`，于是绳端被挂饰拽、又被弯曲约束折着，段长会永久停在略大于
`restLen` 的位置。挂饰挂在最后一个质点上时这点松弛只让绳子多长 0.4%，看不出来；
挂饰开始挂在**延伸后的尾端**上，它就会直接变成「娃娃离吊环越来越远」。
修法见 `renderer/rope.js` 的 `_limitLength`：把总松弛量记进 `this.slack`，
每个子步从**最后一节**收回 `SLACK_RATE = 0.25` 倍（一帧 4 个子步收回约 68%）。
实测 30s 自由摆后 `slack = 0.0029px`、60s 剧烈驱动下 `|折线长 - 绳长| <= 0.013px`。

**真机 E2E（CDP `Runtime.evaluate`，只读，不写配置）**：用 800x600 的假 canvas 构造
`new DollRenderer(canvas, CONFIG)`，喂假 rope（`tailPoint = (407, 219)`、`tipX/tipY = (400, 200)`、
`tipAngle = 0.3`、`overlap = 20`）跑一遍 `draw()`，把 `ctx` 的 `translate/rotate/transform`
累成矩阵，再看 `arc()`（吊环）和 `fillText()`（娃娃）的实际世界坐标：

| 量 | 实测 |
|---|---|
| `arc()` 圆心 | `(407, 219)` = `tailPoint`，**不是** `tipX/tipY = (400, 200)` ✓ |
| `arc()` 在 `restore()` 之后 | 是（`calls` 里第 4 个 `save` 之前已有 2 次 `restore`）✓ |
| 推 `anchorX` 0.5→0 时娃娃基线 x | `0` → `-10`（图宽 20，正好平移半个图宽）✓ |
| 推 `anchorX` 0.5→1 时娃娃基线 x | `0` → `+10` ✓ |
| 推 `anchorY` 0→1 时娃娃基线 y | `17` → `-43`（图高 60，正好上移一整幅）✓ |
| `bodyAngle` 变化时图片块整体是否旋转 | 是（矩阵里有 `rotate`，`arc` 的圆心不动）✓ |

### 2.8 第 22 轮：吊环位置编辑器 + 修「左右反向 / 坐标偏移」（m08776）

用户原话 (m08776)：「1、坐标位置与实际挂钩位置存在偏移。2、挂点的左右调节是反向的。」

2.6b 之后 `anchorX/anchorY` 仍是两个普通滑块，且**两个都是错的**：

| 现象 | 根因 | 修法 |
|---|---|---|
| 左右调节反向 | `renderer/doll.js` 的 `get anchorOffset()` 写成 `px = -w*(ax-0.5); return { ox: -w/2 - px, oy: -py }`，化简即 `ox = -w*(1-ax)` —— 把左右**镜像**了。只有 `ax=0.5` 碰巧对，所以整条链自洽却反直觉 | 改成 `px = w*ax; return { ox: -px, oy: -py }`。`ax=0 => ox=0`（图在吊环右侧）、`ax=1 => ox=-w`（图在左侧） |
| 坐标读数与线上不符 | 面板读数抄的是旧式 `-realW*(x-0.5)`，与线上差**半个图宽** | 改成 `offX = -realW * x`、`offY = -realH * y`，与 `anchorOffset` 逐字对应 |

**为什么不能只修面板**：`settings/settings.js` 的读数、`settings/anchor-editor.js` 的预览、
`verify.cjs` 的 `anchorOffsetOf` 内联副本与验收 10 的三条断言，全是照 `anchorOffset` 对齐的。
只改面板会让"预览"与"线上"分家；只改 `doll.js` 会让验收 10 变红（旧断言把错误方向钉死成"正确"）。
四者必须**同一次**改完。

**编辑器取代滑块**（拖拽仍按 m08506 搁置）：

- 左边 220×220 预览画布：**图片整体居中不动，吊环画在图片矩形上的 `(ax, ay)` 点**，
  虚线十字臂向画布边缘延伸。`fit()` 里 `PAD = 40` —— 吊环外圈半径 13 + 5 描边，
  不留边距时 `anchorX=0` / `anchorY=1` 的标记有一半被 `overflow:hidden` 裁掉。
- 右边：两行百分比读数 + 上下左右四个按钮（每档 1%）+ 「恢复居中」。
  **方向一律是直觉方向**：`右 => anchorX += 1档`。为迁就镜像公式而反转按钮是治标。
- 新控件**不注册进 `controls`** —— `refreshReadouts()` 遍历它并要求每个控件有 `input`/`valueEl`。
- `settings-schema.js` 里两个 `slider` 条目**从 `GROUPS` 删掉、但键必须留在 FIELDS**：
  单独一条 `ANCHOR_FIELDS` 再 `FIELDS.push(...)`。`sanitize()` 只认 FIELDS/CHOICES/STRINGS，
  键一旦从白名单消失，settings.json 里的位置会被**静默丢弃**，老用户升级后挂饰跳回正中。
- 预览要显示用户导入的自定义图，新增 IPC `settings:read-image`：主进程侧校验路径必须在
  `assets/dangles/` 内（同 `delete-dangle` 的护栏），返回 `{ok, dataUrl}`。
- `calibrateEmojiAspect()`：启动时用临时 canvas 以 100px 字号 `measureText` 量出
  `(left+right)/h` 写回 `EMOJI_ASPECT`（落在 0.2~5 才采纳）。原来写死 `1.0` 是猜的，
  与线上 `_dollWidth()` 的字体度量不一致时，"预览里的图"与"线上挂饰"宽高就不同。

### 2.11 第 29 轮：为什么记录里的 `angle` 不是挂饰的角度

记录器 `renderer/recorder.js` 的 `_sample()` 落盘字段里，`angle` 是 **`rope.tipAngle`**（鼠标到绳端整绳连线角），
而挂饰现在用的是 **`rope.tailAngle`**（p4→p5）。`doll` 子对象只有 `{raw, drawn, clamped, anchor}`。

诊断「挂饰朝向对不对」时要注意两点：

1. **`doll.raw` 是滤波器内部状态，不是弦角。** 第 29 轮前它会因为「展开」漂到 −1225°；
   现在它被 `wrapPi` 约束在 `(-180°, 180°]`，但仍然是**滤波后**的量，与大摆幅时的真实朝向有相位差。
2. **`tailAngle` 要从 `nodes[n-2]`、`nodes[n-1]` 反算**：`Math.atan2(p5.x - p4.x, p5.y - p4.y)`。
   记录里没有直接的 `tailAngle` 字段 —— 这是一个应当补上的字段（见下文）。

**建议补的记录字段**（尚未做）：`tailAngle`、`hangX/hangY`（= `hangPoint`）、`tailLen`（挂饰模拟段实测长度）。
后者能直接看出「模拟段有没有被拽回主体段长」这类约束漏改的 bug，比看角度直观得多。
