## 零、为什么是这三项，以及为什么必须按顺序做

用户 (m07533) 提的三项需求，看起来是三个独立功能，实际上是**同一个瓶颈的三个阶段**：

| 需求 | 表面上的样子 | 真正的拦路虎 |
|---|---|---|
| T1 图片端线条锚点位置 | 「让绳子别老挂在图片正中间顶上」 | 娃娃的**旋转原点被写死在吊点**（`renderer/doll.js:315-316` 先 `translate(anchorX, anchorY)`，再 `rotate`） |
| T2 图片中心 / 多重质点 | 「让图片有重心，别整块跟着绳子转」 | 娃娃**完全没有任何横向自由度**（见下方实测 A） |
| T3 图片弹性形变 | 「动起来有点弹性」 | 现在的拉伸只是**整体缩放**，图片本身是刚体（`renderer/doll.js:282-289` 的 `sx/sy`） |

三者的依赖关系是硬的：

```
T1 线条锚点（纯渲染层，可独立开工）
 └─→ T2 多重质点（锚点必须先能离开顶点，否则质点分布没有物理意义）
      └─→ T3 弹性形变（必须先有受力点，才能驱动网格变形）
```

**T3 不能先做。** 没有受力的质点位置，「弹性形变」只能靠伪随机拖尾或正弦抖动来充数 ——
那种东西看起来像弹性，但和鼠标怎么动完全无关，是属于**假装物理**的做法。
本项目在 [09-物理评审与重构方案](09-物理评审与重构方案.md) 里已经为这类事情付过一次代价，
这次提前写死：**不许用伪随机拖尾充数。**

## 一、现状证据（第 20 轮实测，全部可复现）

以下四个实验都只读真实的 `renderer/rope.js`（`node require`，不启动 Electron），
用 `rope.test.cjs` 同款配置（`segments 3` / 4 质点 / `ropeLen 90` / `gravity 3300` /
`dampingPerSecond 0.30` / `fixedStep 1/240` / `tailMass 1.6`）。

| # | 实验 | 结果 | 说明什么 |
|---|---|---|---|
| **A** | 挂点固定在 `(500, 300)`，跑 300 帧（5s）后打印 4 个质点的 `x` | `500.0000 / 500.0000 / 500.0000 / 500.0000`，**极差 0.000000** | 绳子永远是一条**竖直直线**。娃娃姿态完全由「整条绳相对竖直的夹角」决定，没有任何内部自由度 |
| **B** | 人为把第 2 个质点横移 20px（`p.x += 20; p.px += 20`），看多久被拉回 | **0.800s** 后回到距挂点 `x` 偏差小于 `0.5px`，末态偏 **0.4142px** | 想靠「让绳子自己弯」实现多重质点是行不通的：`_limitBend` + `_limitLength` 会在 1 秒内把横向偏移吃掉 |
| **C** | 以 600px/s 向右匀速拖 240 帧，打印各质点相对挂点的横向偏移 | `0.0 / -5.8 / -12.2 / -19.5` | 整条链是**刚性倾斜**，不是弯曲。首尾横向差 19.5px 全部来自「同一根直杆的倾角」 |
| **D** | 同一时刻比较首尾连线角与 `rope.tipAngle` | 两者都是 `-12.52°` | `get tipAngle()` 的定义（`renderer/rope.js:648`）本身就是首尾连线角，所以「娃娃角 = 绳子角」是恒等式，不是巧合 |

**结论**：现在的娃娃是一个**挂在绳子末端的刚体**，它所有的「物理感」都来自
`rope.tipAngle` 这一个标量。T2/T3 要的东西不在这个标量里，
所以**必须在渲染层新开一层自由度**，而不是继续调 `renderer/rope.js` 的参数。

## 二、T1 · 图片端线条锚点可调

### 2.1 现状

```js
// renderer/doll.js:315-316
ctx.save();
ctx.translate(anchorX, anchorY);          // 平移量 = 绳子末端
// ...
// renderer/doll.js:318-328（图片分支）
ctx.rotate(bodyAngle);                     // ← 旋转原点就是「绳子末端」
ctx.transform(sx, 0, 0, sy, 0, 0);
ctx.drawImage(this.img, -w / 2, 0, w, height);   // ← 图片从 (0,0) 往下画
```

两个写死的假设：

1. **吊点在图片顶边中点**：`drawImage` 的 y 从 `0` 开始、x 从 `-w/2` 开始，
   所以图片矩形是 `[-w/2, w/2] × [0, height]`，而旋转原点 `(0, 0)` 正好是顶边中点。
2. **旋转原点 = 吊点**：`rotate` 在 `translate` 之后，所以一切都绕绳子末端转。
   这符合「挂在钩子上的挂饰」直觉，但用户想要的是**图片上任意位置都能挂绳子**。

另外吊环是单独画的（`renderer/doll.js:241 _drawLoop(x, y)`，由 `:258 draw(state)` 调用），
它画在绳子末端，不与图片锚点关联 —— 改锚点时必须一起改，否则会出现
「绳子从娃娃肩膀穿进去，但吊环还画在头顶」。

### 2.2 设计

**唯一的契约：锚点用图片自身的相对坐标表示，与像素尺寸无关。**

| 字段 | 类型 | 范围 | 默认 | 含义 |
|---|---|---|---|---|
| `doll.anchorX` | number | `0.0 ~ 1.0` | **`0.5`** | 0 = 图片左边缘，1 = 右边缘 |
| `doll.anchorY` | number | `0.0 ~ 1.0` | **`0.0`** | 0 = 图片顶边，1 = 底边 |

默认值 `(0.5, 0.0)` **就是当前行为**，所以：**不动面板时，画面必须逐像素不变。**
这一条是 T1 的验收底线。

像素量换算（在 `renderer/doll.js` 里算，不要写进 config）：

```js
const w = height * (this.img.naturalWidth / this.img.naturalHeight);
const oy0 = -Math.min(cfg.doll.heightMax, height, cfg.doll.anchorY * height);
const ox = -w * (cfg.doll.anchorX - 0.5);
const oy = oy0;   // 负值 = 在图片内部相对顶边往下
```

> **`Math.min(heightMax, ...)` 那一项不能省。** 理由：`get dollHeight()`
> （`renderer/doll.js:72`）会把高度夹在 `[heightMin 56, heightMax 128]`，
> 而 `anchorY` 是**相对图片**的。如果将来支持超大图片，`anchorY * height`
> 可能把锚点推出图片外，视觉上会变成「绳子插在娃娃脚底下的空气里」。
> 先夹一次，宁可锚点位置不精确，也不要出现悬空锚点。

渲染链改成**绕锚点旋转、图片矩形不动**：

```js
ctx.translate(anchorX, anchorY);   // 1. 到绳子末端
ctx.translate(ox, oy);             // 2. 再走到图片上的锚点
ctx.rotate(bodyAngle);             // 3. 绕「图片上的锚点」旋转
ctx.translate(-ox, -oy);           // 4. 撤回去，图片还在原位
ctx.transform(sx, 0, 0, sy, 0, 0);
ctx.drawImage(this.img, -w / 2, 0, w, height);
```

这是标准的「绕任意点旋转」三步式。**没有任何物理改动** ——
`rope.tipAngle` 依旧是首尾连线角，变的只是「画出来的图片怎么摆」。

### 2.3 为什么这是对的做法（而不是改物理）

有人会想：锚点变到图片侧边以后，力臂变短了，摆动是不是该变小？
**不用管，也不该管。** 原因：

- 现在的模型里，娃娃对绳子**没有反作用力**（`renderer/rope.js` 里 `p0.invMass = 0`，
  绳子的另一端是「指针」，娃娃是纯渲染）。所以「娃娃的重心在哪」在物理上根本不存在。
- 一旦真的去改力臂，就会掉进「给娃娃加独立钟摆自由度」那条已知死路 ——
  [06 第五版](06-路线图与决策日志.md) 记过一次：`Lc=43px, ζ=0.45` 的实验
  直接让娃娃冲到 **173~180° 倒挂**，比现状更糟。
- 用户要的是「看起来挂在那里」，「摆多大」由 `doll.angleLimit` 控（面板里有滑块）。
  **视觉锚点和力学力臂是两件事，这一版先只做视觉。**

T2 才是真正引入「重心」的地方，那时再讨论力臂。

  `pointer-events`、DPR 三套坐标系，留到 T1 稳定之后作为体验增强。
- 不做「一行多个锚点」。一张图只有一个挂点。

## 三、T2 · 图片中心点 / 多重质点

### 3.1 问题

现在娃娃的姿态是**一个标量**：`bodyAngle`（来自 `rope.tipAngle`，经 `renderer/doll.js:302`
的死区 + 展开 + 低通 + 软限幅）。整张图片绕吊点刚性旋转。

真实挂饰不是这样的：挂点在顶边的一个点，而**重心在图片中间偏下**。
手一停，挂饰会自己转回「重心在吊点正下方」的姿态；快速拖动时，
上半部分和下半部分的滞后不一样。这就是「中心点」和「多重质点」要表达的东西。

### 3.2 三条路线（只推荐第二条）

| 方案 | 做法 | 优点 | 致命问题 | 判定 |
|---|---|---|---|---|
| ① 假质点 | 渲染层给图片装饰性地画 2~3 个点，跟着 `bodyAngle` 转 | 0 物理改动、1 小时能做完 | **受力是假的**：装饰点和图片的相对位置永远固定，用户拖动时看到的「惯性」依旧来自那一个标量 | ❌ 只许作为 T3 的临时占位 |
| **② 局部质点网（推荐）** | 新增 `renderer/puppet.js`，给娃娃一张 4 点局部网（左上/右上/左下/右下），每点是个 Verlet 点，由吊点位置 + 当前 `bodyAngle` 驱动 | 能表达「重心偏下」「拖动时上下滞后不同」；完全不碰 `renderer/rope.js`，绳子的 17 组回归不受影响 | 需要自己写一个小的约束求解器（但只有 4 个点，比绳子简单一个数量级） | ✅ **选它** |
| ③ 真扩展 rope | 把娃娃的质点并进 `renderer/rope.js` 的链里 | 物理最"真" | 会推翻 `rope.test.cjs` 的全部 17 组基线（`segment` 数、链长、周期全部要重测），而且 `p0.invMass = 0` 的「指针驱动」模型会被破坏 | ❌ 风险与收益不成比例 |

### 3.3 方案 ② 的落盘契约

```js
// renderer/puppet.js（新增）
class PuppetGrid {
  constructor(cfg, dollHeight)         // cfg = CONFIG.doll 的浅拷贝
  rebuild(w, h)                        // 图片尺寸变了才调（applySize 时）
  setAnchor(tipX, tipY, bodyAngle)     // 每帧：绳子末端 + 当前角度
  step(dtSec, vxPx, vyPx)              // 每帧：局部网做一次 Verlet + 长度约束
  get quad()                           // → [左上, 右上, 左下, 右下]，屏幕坐标
}
```

四条硬约束：

1. **画法只能是仿射**。Canvas2D 的 `drawImage` 只能做仿射变换，
   而四个点一般构成**任意四边形**（非平行四边形）。第一版**只允许仿射形变**
   —— 也就是四点由「平移 + 旋转 + 剪切 + 缩放」生成，不允许透视。
   实现方式：由四个角点反推 `a/b/c/d/e/f`（`ctx.setTransform(a,b,c,d,e,f)`），
   反推公式用「三条边取两条做基」的 2×2 逆矩阵，误差在 `0.1px` 内可接受。
2. **静止时必须精确回到矩形**。判据：`|Δcx - Δcy| < 1e-9` 且四角误差 `< 0.5px`
   （Verlet 在「无外力 + 约束收敛」下本来就该落回静止解，
   如果对不上，说明我的约束写漏了一项，不许靠"看起来还行"放过）。
3. **绳子的 17 组回归必须逐位不变**。`renderer/rope.js` 一行不改。
4. **质点数量写死 4 个**，不做「用户可调的细分数」——
   `rope.test.cjs` 的血泪教训：参数语义一多，测试就管不住。

### 3.4 判据

| # | 判据 | 怎么测 |
|---|---|---|
| T2-a | 静止时四角精确回矩形 | 单位测试：喂 300 帧静止输入，四角误差 `< 0.5px` |
| T2-b | 绳子回归不变 | `node rope.test.cjs` 17 组全过且数字不变 |
| T2-c | 重心偏下可观察 | 真机：`anchorY = 0.0` 时快速横向拖动，图片底部滞后大于顶部（截图量四角） |
| T2-d | 帧率无关 | 60/120/240fps 下同一驱动的四角轨迹极差 `< 2%` |
| T2-e | 无 NaN | 60s 剧烈甩动后 `quad` 全部有限 |

### 3.5 明确不做

- 不做自碰撞 / 图片扭曲到自交。挂饰是小图，自交看不出来，加了只会引入不稳定。
- 不做「质点可视化」开关。调试靠 `recorder.js` 的额外字段，不占用户界面。

## 四、T3 · 图片弹性形变

### 4.1 三条实现路径的取舍

| 路径 | 做法 | 每帧成本 | 判定 |
|---|---|---|---|
| ① 现有 `doll.stretch` | `renderer/doll.js:282-289` 的 `sx/sy` 只做**整体缩放**，图片本身是刚体 | ~0 | ❌ 不是形变，是「变胖变瘦」 |
| ② 网格分片贴图 | `drawImage` 的 9 参数版切 3×3 = 9 片，每片一个 `ctx.transform` | 9 次 drawImage + 9 次 transform，实测应 `< 2ms`（预算 16.67ms） | ⚠️ 效果最好，但**依赖 T2 的 4 点网扩成 3×3 = 9 点**，工作量最大 |
| **③ 皮肤式惯性（推荐先做）** | 给 T2 的 4 个角点各加一个「皮肤点」，位置 = 目标位置的一阶滞后，衰减复用 `dampingPerSecond` | ~0（就是 4 次指数插值） | ✅ 最便宜，视觉上已经能看出「图片被甩得有点变形」 |

**先做 ③，效果不够再考虑 ②**。理由是 ③ 完全复用 T2 的质点网，
不引入新的绘制机制；② 一旦上马，就要处理「9 片之间的接缝」
（`drawImage` 分片在 DPR 非整数时会出现 1px 白线，这是 Canvas2D 的经典坑）。

### 4.2 方案 ③ 的公式

```js
// 每个角点 i：目标是 T2 算出的 quad[i]，当前是 skin[i]
const follow = 1 - Math.exp(-dtSec / skinTau);   // skinTau 默认 0.045s
skin[i].x += (quad[i].x - skin[i].x) * follow;
skin[i].y += (quad[i].y - skin[i].y) * follow;
```

- `skinTau` 必须做成**与帧率无关**（用 `1 - exp(-dt/tau)`，不是固定比例），
  这是 `renderer/rope.js:189 _dampingPerSecond(h)` 已经验证过的写法。
- 拉伸量必须**钳制**：`skin` 与 `quad` 的最大偏离限制在 `maxPercent` 以内
  （复用 `doll.stretch.maxPercent = 0.10`），否则快速甩动时图片会被拉成一条线。
- **不做弹簧回弹**（不加二阶项）。理由：一阶滞后已经足够表达「软」，
  加了二阶就会出现过冲，而本项目在 R9「弹跳闸门」那一轮已经证明
  欠阻尼二阶系统的过冲（ζ=0.0185 时来回 14~20 次）比"不够软"难看得多。

### 4.3 判据

| # | 判据 | 怎么测 |
|---|---|---|
| T3-a | 拉伸不超过 `maxPercent` | 单位测试：喂 4000px/s 阶跃，最大形变 `< 10%` |
| T3-b | 停手后 2s 内回正 | 单位测试：偏离 `< 0.5px` 的时间 `< 2s` |
| T3-c | 帧率无关 | 60/120/240fps 的形变量极差 `< 2%` |
| T3-d | 不抖 | 真机截图：静止时四角位置逐帧标准差 `< 0.3px` |
| T3-e | 绳子回归不变 | `node rope.test.cjs` 17 组 + `verify.cjs` 1~9 组数字不变 |

## 五、顺手要修的事（不属于 T1~T3，但会挡路）

## 六、给后来者的三条提醒

1. **改渲染侧不需要动 `renderer/rope.js`。** T1/T2/T3 全部只碰 `renderer/doll.js`
   和新增的 `renderer/puppet.js`。一旦发现自己在改 `rope.js`，先停下来问：
   用户要的是"看起来"还是"算得对"？
2. **每一个 T 都必须在 `verify.cjs` 里留一条验收。** 现在的 9 组验收覆盖了
   周期、衰减、翻上、折叠、帧率无关、性能、记录器、环绕连续性。
   新增的机制如果没进 `verify.cjs`，下一轮重构一定会把它弄坏而没人发现。
3. **默认值必须等于当前行为。** `anchorX 0.5 / anchorY 0.0`、
   `skinTau` 关闭时 `skin === quad`。这样「用户不动设置 ⇔ 画面不变」，
   回归才有意义。
