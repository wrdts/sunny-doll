## 一、铁律

### 铁律 1：测试时必须断开真实鼠标

用户已经提了 **3 次**（m01467 第 3 条、m01563 第 3 条、m02010 前言）。

> m01563 原文：「之前多次判断指针效果可能存在失误，因为我的鼠标同时也在移动。
> 在你进行效果判断时应该断开鼠标的引导效果。」

原因见 `docs/02-系统架构.md` 第三节：指针有 ①②③ 三路输入，
手动改坐标会被 8ms 轮询覆盖，而真实鼠标也在同时产生 ①。

**正确做法**（按可靠性排序）：

1. **纯 Node 逻辑测试**（最可靠）：不起窗口、不碰鼠标，直接 `new RopeChain(cfg)` 跑物理。
   这是验证物理逻辑的唯一可信手段，`rope.test.cjs` 和临时 `_probe.cjs` 都走这条路。
2. **让用户把鼠标挪开** + 截图（次可靠）：只能验证静态外观，不能验证运动。
3. **CDP `Input.dispatchMouseEvent`**（有条件可用）：走真实事件路径，但和用户的手竞争。
4. ~~CDP 改 `__doll.cursor.x/y`~~（**不可用**）：不更新 `lastMouseEventAt`，被轮询覆盖回去。

**已实施（P0）**：`debug.lockPointer` 把指针控制权做成**两种运行时模式**：

| 模式 | `lockPointer` | 行为 |
| --- | --- | --- |
| 鼠标可控 | `false` | 正常使用。真实 `mousemove` 与主进程轮询都生效 |
| 鼠标不可控 | `true` | 调试。真实鼠标**完全失效**，指针只听脚本的 |

三个输入监听器**永远注册**，只由 `pointerLocked` 做运行时拦截，所以能随时切回来，
不必改配置、不必重启。切换方式（都不暴露给普通用户）：

- 快捷键 **`Ctrl+Alt+L`**（立即切换，控制台会打印当前模式）
- CDP：`window.__doll.lock(true)` / `window.__doll.lock(false)`
- 改 `renderer/config.js` 的 `debug.lockPointer`（下次启动生效）

`window.__doll.locked` 是 getter，读到的永远是实时值。`__doll.state().locked` 同。

**测试纪律**：
1. 开始测前先 `__doll.lock(true)`，再 `__doll.setPointer(x, y)` 钉住光标。
2. 测完**必须** `__doll.lock(false)` 把鼠标控制权还回去 —— 否则用户会觉得鼠标坏了。
3. 交付前把 `debug.exposeState` **和** `debug.lockPointer` 都改回 `false`。

### 铁律 2：不要用「接近水平占比」判断绳子是否异常

摆动穿过水平的瞬间会被误判成 bug。正确指标是 **droop**：

```
droop = (绳端y - 支点y) / 绳长
1 = 完全竖直下垂，0 = 水平，负 = 翘到支点上方
```

### 铁律 3：物理「对」不等于观感「对」

实测过：把支点固定后，被甩平的绳在 0.6s 内自己落回竖直，
1.0s 后 y 稳定在 400/417/433/449（长度 50 的竖直分布），并保持 ±13° 衰减摆动。
**物理本身是对的**，但画面上像一根硬杆横着 —— 这是观感问题，得靠渲染或限幅解决。

### 铁律 4：改完 JS 必须 `node --check`

PowerShell 用 `[System.IO.File]::ReadAllLines` + 按索引替换**极易错位**：
覆盖掉相邻行、丢闭合括号、把 `const` 定义删掉。
本项目已因此产生至少 5 次 `SyntaxError` 和 1 次「小熊整个消失」。

可靠流程：

```powershell
$c = [System.IO.File]::ReadAllLines($p)
# ... 替换 $c[$i] ...
[System.IO.File]::WriteAllLines($p, $c, (New-Object System.Text.UTF8Encoding($false)))
node --check $p; "EXIT=$LASTEXITCODE"
# 再用 for 循环回读打印确认
```

注意：`.Replace()` 改多行代码会因 CRLF 差异**静默失败**。

### 三条关键的方法论（第 3 轮踩出来的）

**① 驱动必须"平滑加速"，不能瞬时满速**

`sweep()` 每帧给 20px 位移（= 1200px/s）等于给摆锤一次 1200px/s 的**冲量**。
能量守恒 `½v² = gL(1-cosθ)` 代入 v=1200、g=3300、L=90 得 `cosθ = -1` ⇒
**θ = 180°，物理上就该翻过去**。翻顶之后是混沌轨迹，任何"帧率无关"断言都会失败。

旧版测试用 `nx = r.anchorX + (x - r.anchorX) * 0.75` 假装"渲染层平滑"，
把这个冲量削掉了 —— 但渲染层早已是零延迟，等于在测一个不存在的系统。
**现在用 `rampDrive(r, vx, rampSec, holdSec, dt)`**（smoothstep 加速 + 匀速段），
并且只取**匀速段**的平均角。

**② 不要用自由摆衰减去验证"帧率无关性"**

（另外，第 4 轮踩到一个相关的坑：**别拿段数当质点个数**。
`rope.rebuild(len, count)` 的 `count` 是质点个数 = 段数 + 1。
写成 `rebuild(90, cfg.segments)` 会少一个质点，测出来的"软绳"其实是更硬的拓扑。）

PBD 距离投影本身有数值耗散，且 `b_num ≈ 47·h`、`b_num ∝ 1/L ∝ ω²`。
所以 free-swing 的 tau 天然随 `fixedStep` 漂移（实测 2.6×），
测出来的差异是**算法特性，不是 bug**。
正确指标是「匀速拖动稳态平均角」，实测对 dt 与 h 的极差都 < 0.15°。

**③ 力矩/位置类断言的语义要先写清楚**

`minJointAngle` 约定 **180° = 伸直、0° = 对折**，
而 `maxBend` 限制的是"弯曲量" = `180° - 关节夹角`，
所以合格线是 `>= 180 - maxBendDeg - 5`（=89.1°），
写成 `>= maxBendDeg - 5`（=80.9°）等于**要求绳子必须折成 86°**。

### 其它测试本身的坑

- `[3]` 原第二条断言抓**末帧快照** `r.tipX < r.anchorX`：稳态滞后只有 2.2°（dx ≈ -3.5px），
  而残余摆动 ±3px ⇒ 随机假失败（实测 `tipX=1254.5 / anchorX=1254.2`）。
  改为累加整个匀速段的 `avgDX`。
- `[5]` 柔性断言曾经写成「4 节比 3 节更弯」，必然失败：段数只提供弯曲自由度，
  强重力下多段会一起被拉直。正确断言是「3/4 节都能弯出可见弧度」。
- `[6]` 拉长断言曾经要求 > 2%，太紧；软绳实测只拉长 0.6%。改为 > 0.1%。
- `[12]` **相邻过零间隔是半个周期**，必须 `T = 2 × 平均间隔`。

## 三之二、设置面板怎么测（第 5 轮新增）

设置面板横跨三个进程边界（面板渲染进程 → 主进程 → 覆盖层渲染进程），
单测任何一层都不够，下面是三层都要走的清单。

### 层 1 · 纯 Node：存储与清洗

```js
const store = require("./settings-store.js");
store.init(os.tmpdir() + "/sd-test");   // 别指向真实 userData
store.set({ "physics.gravity": 1800 }); // 内存立刻更新，磁盘还没写
store.flush();                          // 立即落盘
```

要验证的点：防抖生效（`set` 后文件不存在）、`flush` 后落盘、重新 `init` 读回一致、
坏 JSON 静默退回 `{}`、`clear` 后磁盘为 `{}`。

`settings-schema.js` 的 `sanitize` 要单独打：越界钳制、按 `step` 对齐、未知字段丢弃、
非有限值丢弃、扁平/嵌套两种形状都接受（**扁平优先**）。

### 层 2 · 纯 Node：应用后物理真的变了

不要靠截图判断"生效了没有"。正确做法是走真实链路再量物理：

```js
const clean = schema.sanitize(presetValues);        // 主进程做的清洗
const cfg = Object.assign({}, C.physics, C.chain);  // 再 deepAssign 覆盖值
const r = new RopeChain(cfg);
r.rebuild(60.5, cfg.segments + 1);
// 量周期 / tau / 匀速拖动稳态角，与出厂值对照
```

判据是**方向**不是绝对值：第 1 档必须周期最长、匀速拖动倾角最大；
第 7 档必须周期最短。实测七档周期 1.178 / 1.069 / 0.963 / 0.771 / 0.718 / 0.684 / 0.640s，
单调递减，任意两档之间至少差 3.2%。

### 层 3 · 真实 Electron：IPC 与界面

```powershell
Remove-Item Env:\ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
& node_modules\.bin\electron.cmd _t_e2e.js
```

`_t_e2e.js` 自己建一个 `BrowserWindow` 加载 `settings/settings.html`（用**真的** `settings-preload.js`），
然后在 `webContents.executeJavaScript` 里操作 DOM、在主进程侧记录 `ipcMain` 收到了什么。
这样可以一次性验证：字段是否渲染全、拖动后 IPC 载荷、档位整组替换、恢复默认下发 `{}`、落盘内容。

**第 6 轮（7 档位）必须额外验证的三条**：

1. **选中 ≠ 生效**：点 chip 后主进程必须**收不到** `settings:set`；
   此时 `#apply` 应该从 `disabled` 变为可用、文案变成「应用（第 N 档）」。
2. **应用后才下发**：点「应用」时主进程收到的必须是完整四条，且界面里
   `.chip.active` 从旧档移到新档、`.chip.selected` 清空、`#apply` 回到 `disabled`。
3. **手拖滑块会清选中态**：`selectedPresetId = null`，`.chip.selected` 应当消失，
   但 `.chip.active` 保持（因为该档位的值确实还在生效，只是用户又微调了别的字段）。

`_t_7tiers_e2e.js` 的实测输出（可作基线）：

```
[2] 初始 apply 按钮: { disabled: true, text: '应用' }
[3] 点第1档后: {"selected":["lv1"],"active":["lv4"],"apply":{"disabled":false,"text":"应用（第 1 档）"}}
[4] 主进程此刻还没收到 set: null          ← 关键：预览不落盘
[5] 点应用后主进程收到: {"physics":{"gravity":1400,...},"chain":{...},"doll":{...}}
[6] 点应用后界面: {"selected":[],"active":["lv1"],"apply":{"disabled":true,"text":"应用"}}
```

**不要用 `--remote-debugging-port` + CDP 去测面板** —— 面板是独立窗口，
CDP 连接要另开 target，比直接 `executeJavaScript` 麻烦得多。

### 层 4 · 覆盖层：下发能不能只改一项

`_t_overlay.js` 加载真实 `renderer/index.html`（真实 `preload.js`），从主进程侧
`win.webContents.send("settings:apply", { overrides })`，然后在渲染进程里读 `window.CONFIG`。

必须验证的是**整份替换语义**：先下发 `{gravity:1800}`、再下发 `{dampingPerSecond:0.9}`，
第二次之后 `gravity` 必须**回到出厂值 3300**（不是保留 1800）。
如果它保留了 1800，说明 `applySettings` 少了"先 `deepAssign` 回 `pristineDefaults`"这一步。

## 三之三、诊断记录器怎么测（第 13 轮新增）

记录器横跨「覆盖层采样 → 主进程写盘 → 面板显示」三层，但**采样本身是纯逻辑**，

### 层 1 · 纯 Node：采样语义（`verify.cjs` 验收 8）

用 `global.window` 假体 + 真 `RopeChain` + `require("renderer/recorder.js")`，
每帧 `rope.update(1/60)` 后 `recorder.tick(t)`，8 条断言：

| # | 断言 | 判据 | 实测 |
|---|------|------|------|
| 1 | 采样条数 | 3s @100ms 得 30±2 | 28 |
| 2 | 节拍偏差 | 最大 ≤ 3ms | 0.0ms |
| 3 | 字段完整性 | 缺字段的样本 = 0 | 0 |
| 4 | 首条 `ropeF` | 必须是 `null`（差分不出加速度） | null |
| 5 | 静止绳力 | 与 `m·g` 偏差 < 5% | 5357.9 vs 5280.0（1.48%） |
| 6 | `summary` 自洽 | `count` / `durationMs` 与样本一致 | PASS |
| 7 | 撞上限自动停 | `reason="auto"`、`onStop` 只调一次 | PASS |
| 8 | 兜底不抛 | `getRenderer()` 返回 null 时不抛 | PASS |

> 坑：`start()` 会把 `intervalMs` 钳到 **≥16**、`maxSamples` 钳到 **≥10**。
> 写断言时给 `maxSamples: 3` 是测不出来的 —— 实际生效是 10。

### 层 2 · 纯 Node：边界与幂等

- 重复 `stop()` 不得再触发 `onStop`（只有一条出口）。
- 没 `start()` 时 `tick()` 不得采到任何样本。
- `stop()` 之后 `status()` 的 `elapsedMs` 归零、`recording=false`。

### 层 3 · 真机：按钮、节拍、落盘

真机姿势与第 12 轮一致（见第二节），额外两条：

1. **改完 `renderer/recorder.js` 必须重启 electron**。页面跑的是启动那一刻加载的 JS，
   不重启会读到旧字段名 —— 本轮踩到：分析脚本按 `bear.force` 读，全变 `NaN`，
   误以为记录器坏了，其实文件里已经是 `bear.ropeF`。
2. **节拍用「平均 + 累计漂移」判，不要用「每条都必须是 100ms」**。
   60fps 下帧间隔 16.67ms，实际采样落在 97/103 交替，这是帧量化，不是 bug。
   判据：平均 100.00ms、理论条数 == 实际条数、最大累计漂移 < 1 个间隔。

实测（244 条 / 24301ms）：`97ms×117`、`103ms×116`、平均 **100.00ms**、累计漂移 68ms。

落盘验证清单：

```powershell

node -e "const d=require(process.argv[1]); console.log(d.samples.length, d.stopReason, d.summary)" $f
```

- `JSON.parse` 合法、`samples` 条数与面板显示一致；
- **样本行数 == 样本条数**（一条一行，`Select-String -Pattern '^\s+\{\"t\":' | Measure-Object`）；
- 所有数有限（没有 `NaN` / `Infinity`），`null` 只出现在首条样本的受力/加速度字段。

### 层 4 · 真机：动态场景的物理合理性

静止场景只能验"绳力 = m·g"，还得让熊真的动起来。用 koffi `SetCursorPos`
做正弦驱动（±220px @0.9Hz，6s），检查：

| 检查项 | 判据 | 实测 |
|---|---|---|
| 速度范围 | 随运动明显变化 | 0 ~ 3447 |
| 绳力范围 | 峰值应远大于 m·g | 2530 ~ 87934（**16.65×**） |
| 角度范围 | 应接近 ±180 | -179.3 ~ 179.5 |
| 链长守恒 | 各节长度偏离 < 1px | 最差 0.38px（restLen 21.6） |
| `doll.clamped` | 有样本为 true | 13 条（证明限幅在数据里可见） |

> ⚠️ koffi 用 struct 必须**先声明再写进函数签名**：
> `const POINT = koffi.struct("POINT", {x:"int32",y:"int32"});` 要写在
> `user32.func("bool __stdcall GetCursorPos(_Out_ POINT* p)")` **之前**，
> 否则 `Error: Unknown or invalid type name 'POINT'`。

## 三之五、图片挂点怎么测（第 21 轮 T1，第 27 轮更新）

> 背景见 [10-待办与改进方向](10-待办与改进方向.md)。T1 **完全不碰物理**，
> 所以测试的重点不是「物理对不对」，而是**「物理有没有被顺手改坏」**。
> **T2（网格）/ T3（甩尾延迟）已于第 27 轮撤除**，对应的验收 11/12 一并删除，
> 现在 `verify.cjs` 是 **11 组**。那两轮留下的通用教训见本文件「铁律」与 docs/07。

### 层 1：`verify.cjs` 验收 10（挂点，5 条）

| # | 断言 | 抓住什么 |
|---|---|---|
| 1 | 默认 `anchorX/anchorY = (0,0)` 时包围盒左上角精确落在吊环上 | 默认值必须等于改前行为，不是「看起来差不多」 |
| 2 | `anchorX` 0 => `0px`、1 => `-86px`；`anchorY 0.5` => `-43px` | 像素换算的**方向**和量级。第 22 轮曾把左右镜像了，旧断言还把这个错方向钉成「正确」 |
| 3 | 400px 大图 + `anchorY=1` 时 `oy = -400`（**不被 `heightMax` 夹住**） | 锚点跑到图片外面（第 21 轮删掉了 `Math.min(heightMax,…)`） |
| 4 | 绕任意锚点旋转时锚点位移必须为 0（`< 1e-12`） | 忘了 `translate(ox,oy) → rotate → translate(-ox,-oy)` |
| 5 | `anchorX` 0/0.5/1.0 三档弦角序列逐位相同（`0.0e+0 rad`） | 有人偷偷把锚点接进了物理力臂 |

第 2 条是最贵的一条：第 22 轮 m08776 报「左右反向」时，**测试之所以没拦住，是因为旧断言的期望值
是从被测代码自己推出来的**（写的是 `anchorX 0 => 左上 -W`，与错误实现一致）。
期望值必须来自物理语义（「挂点贴左边缘 ⇒ 图片在吊环右侧 ⇒ `ox = 0`」），不能来自实现。

### 层 2：真机必测三件事

1. **锚点可见**：`anchorX = 1.0` 时图片整体在绳子**左侧**；`anchorY = 1.0` 时图片在绳子**上方**。
2. **吊环跟手**：`anchorY = 0.5` 时吊环画在图片腰部，绳子与吊环之间没有断口。
3. **面板与线上同值**：面板读数里的像素偏移必须与覆盖层 `anchorOffset` **逐位一致**
   （真机实测 `ox=-59.184 / oy=-43.2` 两边相同）。这条曾在第 22 轮补失败过 ——
   面板用 `window.screen.height`、线上用 `innerHeight`，两者差几十像素。

### 三条教训（仍然适用）

- **同一概念的第二个副本必须当场对齐。** `verify.cjs` 里的 `anchorOffsetOf()` 是
  `renderer/doll.js` 的 `anchorOffset` 的手抄副本，改一处必须改两处，否则测试会替错实现背书。
- **删掉一个机制时要连它的断言一起删。** 第 27 轮删了 T2/T3，验收 11/12 也必须撤除；
  留着会让人以为功能还在。
- **「默认值必须等于改前行为」是唯一能保证老用户升级后视觉不变的判据。**
  出厂 `anchorX/anchorY = (0,0)`（左上角）是第 23 轮 m09384 定下的诊断基准点。
