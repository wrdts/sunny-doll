# 绕圈（离心）物理说明 —— ⚠️ 历史存档

> **本文描述的实现已在第 3 轮物理重构中整体删除。**
>
> 删除的东西：`_detectCentripetal()` 整套绕圈检测、`_centripetal` 旁路开关、
> 以及被它旁路的三道几何投影（5d `monoDrop` / 5e `minDroopRatio` / 5e-2 / 5f）。
> 对应的 9 个配置项（`centripetalRate` / `Tau` / `Jump` / `Sign` / `Hold`、
> `droopMaxScale`、`monoDrop`、`monoMaxFix`、`minDroopRatio`）已从 `renderer/config.js` 移除。
>
> **为什么删**：绕圈时那三道几何约束本来就被 `_centripetal` 全部旁路，
> 所以「开作弊」和「关作弊」在绕圈场景下的数值**完全相同**
> （实测 R100/R150/R200/R300 的外向偏差 56.8 / 39.8 / 36.1 / 38.3°，两套配置一模一样）。
> 也就是说这整套检测 + 旁路机制**对绕圈毫无作用**，纯属无效复杂度。
>
> 第 3 轮之后的替代方案：删掉全部几何投影，改用 `maxBend`（只限单关节弯曲角），
> 并降低重力（8000 → 4000 → 第 4 轮 3300）让离心力占比提高。
> 绕圈效果见 [09](09-物理评审与重构方案.md)。
>
> **本文保留的价值**：第 3~5 节记录的 6 个坑（尤其是"几何修正与 PBD 交替会把点甩飞"
> 和"数值爆炸真凶是 scaleY 除零"）是**任何**位置投影方案的通用教训，
> 写新的几何约束时仍然适用。**不要照本文的参数表调参，那些参数已经不存在了。**

## 1. 需求

用户 m02703 原文：

> 熊绕到外侧，可以绕鼠标转一圈，在此过程中，根据离心力效果，头部朝向鼠标，
> 屁股朝向外侧，鼠标和熊的头部连接着绳子，并不要求绳子必须向下，
> 而是根据两者位置和力的关系改变

m02820 明确选择**路线 1：纯物理 + 数值加固，不追求稳定效果，接受自然摆动**。

所以目标**不是**"绳子永远朝下"，而是：

- 鼠标快速画圈时，离心力把熊甩到圈外侧
- 绳子按两点位置自然弯曲连接，不强制朝下
- 熊头朝鼠标、屁股朝外（由绳子方向驱动娃娃旋转角实现）
- 一旦停止画圈，几何约束恢复，绳子重新朝下

## 2. 核心问题

正常状态下绳子上有三道**几何约束**，它们是为了防"上翻/拍平"：

| 编号 | 名称 | 作用 |
|---|---|---|
| 5b | `angleGuard` | 超过守角 72° 就加回正力 |
| 5d/5f | `monoDrop` | 保证每个质点比前一个更低（单调下垂） |
| 5e/5e-2 | `minDroopRatio` | 绳端必须垂到总长的 70% 以下 |

这三道约束**恰好也压制了离心外甩**。实测（R=150 v=1500，平均外甩）：

| 配置 | 平均外甩 |
|---|---|
| 全开（基线） | **-2px**（熊被压在圈内侧） |
| 单独关 `minDroopRatio` | +8px |
| 单独关 `monoDrop` | -2px |
| 关 5d + 5e | +39px |
| 只留重力 + 距离约束 | +52px |

→ **`minDroopRatio` 是主因**，`monoDrop`/`angleGuard` 有叠加放大效应。

所以方案是：**检测到"真的在绕圈"时，临时旁路这三道几何约束**，让离心力自由发挥。

## 3. 绕圈检测判据（三次迭代）

判断"鼠标在画圈"而不是"在来回甩"是这块的核心难点。

### 判据一：加速度方向变化率 `azRate`（必要，但不充分）

绕圈时加速度方向**持续旋转**，所以方向变化率很大。

| 运动 | azRate（deg/s） |
|---|---|
| 绕圈 R=30~300 | **641**（抖动 573~705） |
| 直线匀速 600~6000 | 0 |
| 锯齿往返 | 0 |
| 正弦往复 amp=60~300 | **1092** |

问题：**正弦往复也很大**，因为往复的加速度方向每半周期翻转 180°，
每一帧都算出巨大的变化率。只用 azRate 会误判（实测 10/60 帧）。

### 判据二：方向一致性 `azSign`（决定性）

方向变化 `d` 的**符号**累积：`this._azSign += (Math.sign(d) - this._azSign) * k`

- 绕圈：方向持续同向旋转，`d` 符号恒定 → 累积趋近 ±1
- 正弦往复：`d` 符号每半周期翻转 → 互相抵消 → 趋近 0

| 运动 | \|azSign\| |
|---|---|
| 绕圈 R=100/150/300 | **0.946** |
| 正弦横 / 正弦纵 | **0.011** |
| 直线 | NaN（加速度为 0，方向无意义） |

**相差近 90 倍，是比 azRate 可靠得多的判据。**

### 判据三：迟滞 `centripetalHold`（防起手瞬态）

`azSign` 是从 0 低通累积的，起手几帧还没爬起来。真实窗口实测
`sine1000` 仍有 5/120 帧误判（那 5 帧里最大角冲到 153°）。

所以加迟滞：原始条件成立后必须**连续保持 0.25s** 才真正置位。
**不设释放延迟**——出圈要立刻恢复几何约束，否则绳子会继续保持乱折叠。

### 最终判定

```js
const raw = this._azRate > thresh && Math.abs(this._azSign) > signMin;
if (raw) {
  this._centripetalHold += dt;
  this._centripetal = this._centripetalHold >= hold;
} else {
  this._centripetalHold = 0;
  this._centripetal = false;
}
```

## 4. 关键坑（都真实踩过）

### 坑 1：不能用 `_prevAnchorX/Y` 算速度

`update()` 末尾已经把 `_prevAnchorX/Y` 更新成本帧锚点了，
等到 `_detectCentripetal` 时两者相等，**速度恒为 0**，
`azRate` 恒为 NaN，绕圈检测 0/150 帧全不触发。

→ 必须用**独立记录**的 `_detAnchorX/_detAnchorY`。

### 坑 2：首帧加速度爆炸

指针首次定位/切屏时锚点一帧内跳变几百 px，
算出来的加速度是 **2747581 px/s²**（假值）。

→ 加 `centripetalJump`（默认 200px/帧）保护，超限就清空检测状态并跳过这帧。

### 坑 3：检测状态必须随 `rebuild()`/`resetVertically()` 清零

真实窗口里的 `rope` 一直活着，`_azSign` 可能已接近 ±1，
`_centripetalHold` 也带着旧值。重建之后条件立刻成立 → 起手被误判。

**同一段正弦在 Node 干净仿真里 0 帧误判，在窗口里却有 5 帧。**

→ `rebuild()` 和 `resetVertically()` 里都要把
`_detAnchorX/Y`、`_prevVX/VY`、`_accelAz`、`_accelMag`、`_azRate`、
`_azSign`、`_centripetalHold`、`_centripetal` 全部重置。

### 坑 4：数值爆炸的真凶是 5e 的 `scaleY` 除零

旁路几何约束后，绳子会翻到挂点上方，此时 `curDy` 变成**小负数**（实测 -3.5）：

```js
// 原始代码（有 bug）
const scaleY = wantDy / (curDy > 1e-6 ? curDy : 1e-6);
```

`curDy = -3.5` 走 else 分支，`scaleY = wantDy / 1e-6 ≈ 6e7`，
一子步把坐标轰到 1e8 → 两帧到 1e253 → 9.9e91。

→ 两重修复：

```js
const maxScaleY = c.droopMaxScale !== undefined ? c.droopMaxScale : 2.0;
if (curDy > 1 && curDy < wantDy) {       // 必须 >1，含负值时整段跳过
  let scaleY = wantDy / curDy;
  if (scaleY > maxScaleY) scaleY = maxScaleY;
  ...
}
```

**定位方法**：在 `_step` 各阶段插 `this.__probe(tag)` 打点，
看第一次越界出现在哪个 tag。实测越界首次出现在 `F-5g前`
（5e 之后、5g 之前），`E-5d后solve` 干净 → 锁定 5e。

### 坑 5：5c/5d 之后的约束求解会覆盖 5g 的长度钳制

5 段跑过一次 `_limitLength`，但 5c/5d 之后各跑一次 `_solveConstraints`，
会把节点间距重新拉向 `restLen`。实测绕圈旁路 5d 后绳段被拉到 **26.55**，
而 `elasticity:false` 时上限是 20。

→ 在 6) 数值安全阀之前补 **5g 收尾长度钳制**，再跑一次 `_limitLength(stretch)`。

### 坑 6：双驱动污染

CDP 脚本里同时调 `rope.setAnchor()` + `rope.update()`，
而主循环也在调 → 同一 dt 内 update 两次 → 绕圈外甩只剩 **5.9px**
（单驱动是 38px）。

→ `renderer/main.js` 里加 `window.__drivePaused` 开关，
脚本测试前置 `true`，测完置 `false`。

## 7. 已知局限（历史结论，第 3 轮后部分已失效）

- **绕圈转越快越接近稳定，但永远不会完美锁定**。纯物理下绳端与
  "理想朝外方向"的平均夹角：R=100 → 75°（范围 1~108°）、
  R=150 → 44°（2~62°）、R=200 → 39°、R=300 → 40°（20~53°）。
  这是用户 m02820 明确接受的（要物理，不要稳定）。
- **加阻尼救不了绕圈**：damp 0.12 时外甩从 43px 掉到 -6px（阻尼吃掉了甩出动能）。
- **绳长越长外甩越大**：几何约束全关时 R=150 绳 60 → 43px、绳 120 → 57px。
- **静止时绳子被熊遮住**：熊高 86px、绳长 60px，几乎完全遮住，只露吊环。

### 第 3 轮之后的补充（实测）

| 配置 | R100v1000 | R150 | R200 | R300 |
|---|---|---|---|---|
| 旧版（作弊 ON） | 56.8° | 39.8° | 36.1° | 38.3° |
| 旧版（作弊 OFF，g=8000） | 56.8° | 39.8° | 36.1° | 38.3°（**完全相同**） |
| 作弊 OFF，g=2200 | 32.6° | 31.9° | 33.3° | 37.4° |
| 作弊 OFF，g=2200 + k=0.0015 等效阻尼 | **24.1°** | **24.6°** | **26.7°** | **31.8°** |

⇒ **降低重力能明显改善「往外甩」的观感**（56.8° → 24.1°，偏差角越小越接近完美朝外），
而绕圈检测旁路机制毫无作用。这是第 3 轮把 gravity 从 8000 改成 4000 的另一个理由
（第 4 轮因 `segments` 2 → 3 质量分布变化，又按链式刚体摆重标定到 3300）。

> 上表最后一行的小阻尼（k=0.0015 等效）是当时为了对比而临时加的；
> 第 3 轮最终采用的是 `dampingPerSecond: 0.30`，绕圈效果需以 [09](09-物理评审与重构方案.md) 的验收为准。

> **第 5 轮补充**：`gravity` 现在是设置面板里的第一个滑块（"摆动快慢"，400~9000），
> 用户可以自己把它调到 1500~2400 —— 按上表，那会让绕圈外甩从 36° 降到 32° 左右（更好）。
> 换句话说，**「绕圈外甩不够」这个问题现在部分交给了用户自己权衡**：
> 降重力能改善绕圈观感，代价是拖动偏角变大、周期变长。

> **第 6 轮补充（m02035，7 档位）**：档位把「降重力」这件事固化成了 7 个可选项，
> 其中 **1~3 档（g=1400 / 1700 / 2100）全部低于上表最有效的 2200 附近**，
> 所以想让熊往外甩得更明显，直接选第 1 或第 2 档即可，不必再逐条拖滑块。
> 反过来 5~7 档（g=3800 / 4200 / 4800）会比出厂更容易出现「甩不出去」。
> 这是有意的取舍：**绕圈观感与拖动灵敏度是同一个 g 的两头**，
> 面板把它变成一个用户可以自己选的档位，而不是一个要写进代码的固定答案。
> （注：`_centripetal` 整套检测在第 3 轮已删除，现在绕圈完全靠纯物理 + 低重力表现。）
