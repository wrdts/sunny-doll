## 二、核心类与签名

### RopeChain（`renderer/rope.js:48`）

```js
class RopeChain {
  constructor(cfg)                    // 注意：只收一个 cfg，必须已合并 physics + chain 两段
  rebuild(len, count)                 // 重建链：len=总绳长, count=质点数
  _massAt(i, n)                       // 第 i 个质点的质量（从 1 线性升到 tailMass）
  _recomputeMass()                    // 重算逆质量；P0 的 invMass 恒为 0（钉死）
  setAnchor(x, y)                     // 设置支点（只记 anchorX/anchorY，不碰 points[0]）
  teleport(x, y)                      // 瞬移：整链搬到新位置，不产生冲量
  resetVertically()                   // 恢复竖直下垂
  _dampingPerSecond(h)                // 返回阻尼率 k（1/s）；兼容旧的 velocityDamping
  update(dt)                          // 每帧推进：分配子步 + 支点插值推进
  _step(h)                            // 单个固定子步（**签名已去掉 stepIndex 参数**）
  _solveConstraints(stiffness)        // PBD 距离约束迭代
  _limitLength(maxStretch)            // 单节长度上限，顺带算 tension
  _limitBend(maxBend)                 // 单关节最大弯曲角（绕关节纯旋转，精确保段长）
  _rotateAbout(q, o, phi)             // 绕 o 旋转 q，同时旋转 (x,y) 与 (px,py)
  get tailPoint()                     // 最后一段绳的末端 = pts[n-1] 沿末节方向再延伸 overlap 像素
  // ---- 第 29 轮：挂饰模拟段（p4 -> p5）----
  get tailAngle()                     // p4->p5 的方向：atan2(p5.x-p4.x, p5.y-p4.y)，竖直向下为 0
  get hangPoint()                     // 挂饰挂点 = p4（+ overlap 沿 p4->p5）；无模拟段时退回 tailPoint
  get hasTail()                       // 末点是否是模拟段末端质点（isTail）
  _tailLength()                       // 读 cfg.tail.length；enabled 为 false/"off"/0 时返回 0
  _tailMass()                         // 读 cfg.tail.mass（相对单段质量的倍率，默认 20）
  _restOf(i)                          // 第 i 段的静止长度：挂饰模拟段走 _tailRest()，其余 restLen
  _tailRest()                         // 读 cfg.tail.length
  setOverlap(px)                      // 同步 rope.overlap（applySize / applySettings 都调）
  _updateTip()                        // 更新 tipX/tipY/tipDirX/tipDirY/tension
  get tipAngle()                      // Math.atan2(b.x-a.x, b.y-a.y)，正=向右偏
  get polylineLength()                // 各段长度之和（测试用）
  get path()                          // this.points（画绳子用，**不可删**，删了整幅画不出来）
  get count()                         // this.points.length
}
```

**`_step` 每子步的执行顺序**（顺序本身是设计决策，改顺序会破坏物理）：

```
① 外力（gravity / drag / turbulence）
② Verlet 积分  x += (x-px) * exp(-k*h) + a*h²      ← keep 用 exp，不是 (1-vd)
③ 支点推进（按 r = _stepIndex/_stepTotal 线性插值，**绝不碰 px/py**）
④ iterations 次 _solveConstraints(stiffness)
⑤ _limitLength(stretch)
⑥ bendIterations 轮：_limitBend(maxBend) + _solveConstraints(1)   ← 必须交替，单轮收敛不足
⑦ _limitLength(stretch)
⑧ 速度安全阀（maxStepPerFrame，超限只改 px/py）
⑨ 非有限值兜底 → resetVertically()
```

**关键陷阱**：`constructor(cfg)` 是**单参数**。`renderer/main.js` 必须这样构造：

```js
function ropeCfg() {
  const C = window.CONFIG;
  // 第 29 轮补：C.tail 是顶层段（不在 chain 里），必须显式带上；
  // 否则 rope 读到的 cfg.tail 恒为 undefined，模拟段能工作只因兜底默认值撞对了 config。
  return Object.assign({}, C.physics, C.chain, C.tail ? { tail: C.tail } : {});
}
const rope = new RopeChain(ropeCfg());
```

直接把 `CONFIG.physics` 传进去会导致 `chain` 段全部读到 `undefined`。
这个坑最早是在 `angleSpring` 上发现的（当时调 0 / 8000 / 20000 / 40000 结果一模一样），
那个参数现已删除，但**合并两段的写法仍然是必须的** —— 现在 `segments` / `iterations` /
`dampingPerSecond` / `tailMass` 全在 `chain` 段里。

### 指针：直接用系统指针（第 11 轮起）

`renderer/cursor.js` 与 `system-cursor.js` 已整体删除，`renderer/doll.js` 里只剩：

```js
attachPoint(cursorX, cursorY) {
  const c = this.cfg.cursor;
  return { x: cursorX + (c.attachOffsetX || 0),
           y: cursorY + (c.attachOffsetY || 0) };
}
```

**为什么不能隐藏系统指针**（这条是架构级的，不是"还没做"）：

- `ShowCursor(bool)` 改的是**调用线程**的显示计数，只影响该线程拥有的窗口。
  覆盖层是 `setIgnoreMouseEvents(true,{forward:true})` + `focusable:false`，
  **从不持有鼠标、从不获得焦点** —— 指针下方是别的窗口在处理 `WM_MOUSEMOVE`，
  显隐由**那个窗口的线程**决定。⇒ `ShowCursor` 在这条架构里永远不可能生效。
- 系统指针**不是窗口**，由 DWM 画在独立的硬件光标平面上，任何 `HWND_TOPMOST` 都盖不住。
  所以程序画的任何东西（包括自绘指针）永远在系统指针**下面**一层。
- `SetSystemCursor` 能全局换形状，但那是全系统副作用：只要有置顶窗口（右键菜单 `#32768`、
  设置面板、任务栏）压在覆盖层上，屏幕上就会**完全没有指针**，而这恰恰是用户要点菜单的时刻。

⇒ 结论：**放弃自绘指针，用系统指针 + 手动偏移**。程序读不到系统指针的尺寸
（辅助功能里 1~15 档缩放、第三方主题都会改），所以 `attachOffsetX/Y` 只能是常量；
设置面板提供 -40~+90 的两个滑块，用户按自己的指针调一次即可。

## 四、挂点跟随模型（R10/R11/R12/R15 的实现方式）

这是本项目最重要的设计决策。第 3 轮重构后，模型是：

```
每帧：把「本帧锚点位移」线性摊到 willRun 个子步上，p0 的 px/py 保持为上一帧锚点
     → Verlet 速度 = 真实鼠标速度（离心力/加速度响应生效）
     → 子步数取整不改变总位移（帧率无关）
```

### 1. 挂点零延迟（`renderer/main.js:111-182`）

```js
const prevX = rope.anchorX;
const prevY = rope.anchorY;
const jump = Math.hypot(attach.x - prevX, attach.y - prevY);
if (jump > (ph.maxPivotStep || 400) * 4) {
  rope.teleport(attach.x, attach.y);   // 超大跳变（切屏）才吸附
} else {
  rope.setAnchor(attach.x, attach.y);  // 其余全部零延迟直给
}
rope.update(dt);
```

**没有任何平滑**。`cursorSmoothing` 字段已从代码中删除。

### 2. 两种 `followMode`（`physics.followMode`）

| 模式 | 行为 | 偏角与速度的关系 |
|---|---|---|
| **`"velocity"`（当前）** | 把本帧锚点位移**均摊到 willRun 个子步**，`p0.px = 上一帧锚点`，逐子步线性插值推进 | Verlet 速度 = 真实鼠标速度 ⇒ **离心力生效，偏角随速度增长** |
| `"translate"` | 整链刚性平移（`px/py` 同移） | 挂点相对速度恒为 0 ⇒ **无离心力，偏角与速度无关**（早年默认值） |

> **一次性注入第一个子步会毁掉帧率无关性**：实测 60fps 得到 1.44°、
> 240fps 得到 -23.54°。必须均摊到所有子步。

### 3. 为什么"支点只改 x/y 不改 px/py"是错的

Verlet 里速度 = 当前位置 − 上一子步位置。如果只改 `x/y` 不改 `px/py`，
整帧的锚点位移会被当成**一个子步内**的巨大速度注入，离心力 `ω²L` 压过重力，
绳子被甩成横杆甚至翻上去（这正是 F4 的历史缺陷）。

第 3 轮的做法是**把位移拆成 willRun 份、逐子步推进**，而不是"刚性平移 + 摆锤不跟随"。
后者虽然不爆炸，但完全没有惯性（实测最大角 0.2°）。

### 4. 子步数为 0 的帧必须什么都不做

高刷屏（如 360Hz）下 `floor(accumulator / h)` 会周期性算出 0。
旧实现即使在 0 子步的帧里也会把 `_prevAnchorX` 更新成新锚点 ——
等于**每三帧丢一次鼠标位移**（实测 360Hz 帧间抖动 73%）。
现在整个跟随/子步循环都包在 `if (willRun > 0) { ... }` 内。

## 五、物理公式

### Verlet 积分（`renderer/rope.js` `_step`）

```
x' = x + (x - x_prev) * keep + a * h²
keep = exp(-k * h)          // k = physics 阻尼率，单位 1/s
```

**`keep` 必须是 `exp(-k*h)`**。旧实现是每子步 `keep = 1 - velocityDamping`，
导致「1 秒后速度留存率」60Hz 0.697 / 240Hz 0.236 / 480Hz 0.056（跨帧率差 1252%），
改 `fixedStep` 等于换了一个物理引擎。

### PBD 距离约束（`_solveConstraints`）

```
e = |p_j - p_i| - restLen
按逆质量加权，两端各退一半：Δ = e * (w_i / (w_i + w_j))
```

`stiffness < 1` 就是弹性绳；`elasticity: false` 时强制 `stiffness = 1`（单次解到位）。

> **PBD 投影本身有数值耗散**，且不可消除。实测标度率：
> `b_num ≈ 47·h`、`b_num ∝ 1/L ∝ ω²`（ω = √(g/L)）。
> 所以「自由摆衰减多快」永远随 `fixedStep` 漂移，
> **不能用自由摆衰减去验证帧率无关性**，必须用「匀速拖动稳态平均角」。

### 弯曲约束（`_limitBend`，第 3 轮新增）

```
对每个内部关节 j：v1 = a - b、v2 = c - b（都以关节 b 为原点）
alpha = atan2(v1 × v2, v1 · v2)
注意这个约定下：伸直时 |alpha| = pi，对折时 |alpha| = 0
弯曲角 bend = pi - |alpha|
若 bend > maxBend：绕关节纯旋转
  按逆质量加权分配修正量（w = invMass，wsum = wa + wc）
  phi = -(alpha >= 0 ? 1 : -1) * (bend - maxBend)
  _rotateAbout(a, b, phi * (wa / wsum))
  _rotateAbout(c, b, -phi * (wc / wsum))
```

**纯旋转精确保段长**（同时旋转 x/y 与 px/py），不会像旧的 `scaleY` 那样注入拉伸。
它只限制"单个关节弯多少"，**不限制整根绳子的绝对朝向** —— 所以绳子依然能整体翻到挂点上方（R15）。

> **必须按逆质量加权**：`j = 1` 时 `a` 就是 `pts[0]`（锚点，`invMass = 0`）。
> 早期版本无条件 `_rotateAbout(a, b, phi)`，等于每次调用都把锚点从鼠标位置推开 1.0~3.2px
> —— 绳子自己拽着指针跑。加权后 `wa = 0`，锚点纹丝不动。

必须与长度约束**交替迭代**（`bendIterations: 10`）：掰直 j 号关节会把 j±1 号掰弯，
单轮实测最差关节 77.9°、总长冲到 107px。**循环收尾那一次必须是 `_limitBend`**，
不能是 `_solveConstraints`，否则刚压下去的角度会被拉回来一部分。

> 关节越多越难收敛。([15] 场景 300px 瞬变往返 600 帧，合格线 89.1°)：
> 3 段绳 bendIterations=3 就有 105.1° 通过；**4 段绳 3 轮只到 69.2°（不合格），10 轮才 93.6°**。
### 外力

| 力 | 公式 | 参数 |
|----|------|------|
| 重力 | `g` | `gravity: 3300` px/s² |
| 空气阻力 | `-drag * v * vx` | `drag: 0.00015` |
| 湍流 | 双正弦叠加 | `turbulence: 60`、`windFreq: 1.7` |

> 二次阻力项 `-drag·|v|·vx·h²` 的**等效减速度 `drag·v²` 与 h 无关**（h² 是位移换算），
> 这一点与速度型阻尼不同。

### 两个闭式解（第 3 轮推导，实测 24 组误差 ≤0.27°）

```
匀速拖动稳态倾角    tan(θ) = (k·v + drag·v²) / g
自由摆振幅时间常数  tau = 1 / (k/2 + omega²·h/2)      omega = sqrt(g / L)
```

**两个式子里的 k 是同一个 k** ⇒ 「拖动时的偏角」与「停手后晃多久」被同一个旋钮同向绑死。
这是 R13 与 R14 冲突的数学根源，也是为什么不能靠调阻尼解决。

## 六、娃娃旋转角（`renderer/doll.js`，第 29 轮重写）

挂饰的朝向**只有一处来源**：挂饰模拟段 p4→p5 的 `rope.tailAngle`。
拿到之后渲染层做四件事，**顺序不能换**：

```js
let rawAngle = hasRope ? rope.tailAngle : 0;                     // ① p4->p5 的方向
const dz = cfg.doll.angleDeadzone !== undefined ? cfg.doll.angleDeadzone : 0.02;
if (Math.abs(rawAngle) < dz) rawAngle = 0;                       // ② 死区 0.02（≈1.1°）
const tau = cfg.doll.bodyAngleTau !== undefined ? cfg.doll.bodyAngleTau : 0.08;
const fk = 1 - Math.exp(-dtSec / tau);                           // ③ 低通 tau=0.08s
if (this._bodyAnglePrev === null) {
  this._bodyAnglePrev = rawAngle;                                //    首帧直接吸附，不从 0 转过去
  this._bodyAngle = rawAngle * ratio;
} else {
  const d = wrapPi(rawAngle - this._bodyAnglePrev);              // ④ 帧间【最短路径】增量
  this._bodyAnglePrev = rawAngle;
  this._bodyAngle = wrapPi(this._bodyAngle + d * ratio * fk);    //    状态每帧折回 (-PI, PI]
}
const bodyAngle = this._bodyAngle;                               // 没有限幅，没有归位
```

### 为什么必须取「帧间最短路径增量」

`tailAngle` 的值域是 `(-PI, PI]`。挂饰翻过指针顶部时它从 `+179°` 直接跳到 `-179°` ——
**物理上只转了 2°，数值上跳了 358°**。如果直接 `body += (raw - body) * fk`，
滤波器会把 `-179` 当成新目标，一路倒着追，视觉上就是小熊原地反向转一圈（F15，
用户 m04468 / m04564 报的就是这个）。

`wrapPi(raw - prev)` 把 358° 折成 +2°，这是唯一正确的修法。

### 为什么状态必须每帧折回主值域

这是第 29 轮和第 16 轮（F15）的**本质区别**，也是修掉「小熊偏向一侧」的关键。

第 16 轮的写法是「展开」：

```js
// 旧写法（已删除）
this._bodyAngleCont += wrapPi(rawAngle - this._bodyAnglePrev);   // 无界累积
this._bodyAngle += (this._bodyAngleCont - this._bodyAngle) * fk;
```

`_bodyAngleCont` 会一路累加，甩几圈就漂到几百上千度。当时的补救是「归位」：
要求「鼠标静止 0.6s + 滤波器已收敛 + 累计偏离超过半圈」三条同时成立，
才把状态掰回主值域，而且不能硬跳（那本身就是一次视觉跳变），
所以还要记一个 `_bodyUnwindOffset` 让它指数衰减。

**结果是在真实使用中永久失效**。用户操作时鼠标一直在动（尤其甩圈），
`_bodyAngleStill` 永远攒不满 0.6s ⇒ 归位一次都不触发 ⇒ 状态漂到 `-1225°`
（用户记录 `record-20261022-150421.json` 实测）⇒ `softLimit` 永久饱和在 `-82°`
⇒ 小熊卡在一边、弦角已经回正了画面还歪着。

现在的写法**没有展开，只有折回**：`body = wrapPi(body + Δ * fk)`。
状态天然被约束在 `(-PI, PI]`，永远不会漂，也就不需要归位逻辑。
单帧最大转角被 `fk` 限住（60fps 下 `fk ≈ 0.19`，即 180° 阶跃最多转 34°/帧），
不会出现「突然跳过去」。

### ③ 低通为什么不能省

`tailAngle` 是每帧从两个质点坐标算出来的 `atan2`，源头抖动有三个：

1. **PBD 约束残差** —— `bendIterations: 10` 是上限不是精确解，相邻帧的残差方向不同；
2. **Verlet 速度项** `(x - px) / h` —— `fixedStep = 1/240`，末子步残差直接进坐标；
3. **模拟段只有 26px** —— 角度灵敏度 `dθ ≈ Δx / L`，**1px 坐标误差 = 2.2° 角度误差**。

实测记录（用户甩圈，`record-20261022-150421`）：21% 的 100ms 间隔里 `tailAngle`
变化超过 90°。硬赋值会让挂饰每几帧抽搐一下，低通把它摊成顺滑的一段弧。

### 没有软限幅了

第 27 轮之前的 `_softLimitAngle`（`limit + over * tanh((abs-limit)/over)`，
出厂 45°+18° ⇒ 可见封顶 63°）**已整块删除**。

第 29 轮按用户要求改为「直接跟随」，
所以 `doll.angleLimit` / `doll.angleLimitOvershoot` 现在**不作用于挂饰角度**：模拟段转到多少，挂饰就转到多少。

> 这两个参数仍留在 `renderer/config.js` 与 `settings-schema.js` 里（面板上还能调），
> 但当前代码没有任何地方读它们 —— 留着的唯一理由是「用户可能还想按旧习惯调回去」。
> 如果确认不要了，可以连同面板项一起删。

### 死区为什么必须小

死区 0.10（5.7°）时，停手后 **60~74% 的帧角度严格为 0**，
这是"摆动看起来停了"的直接原因之一。现在 0.02（≈1.1°），只用来吃掉
`atan2` 在 `dy` 剧烈变化时的数值抖动。

### emoji 分支也必须 `ctx.rotate`

`renderer/doll.js` 的绘制有两条分支（自定义图片 / 自带 emoji），
**两条都必须调用 `ctx.rotate(bodyAngle)`**。

第 29 轮之前只有图片分支有这一行，emoji 分支没有 —— 于是自带小熊（默认挂饰）
的位置会跟着 p4 走、角度却始终竖直，而自定义图片是正常的。
用户 m11343 的描述是「小熊方向并没有绑定成 p4-p5 朝向，依然竖直向下」，
m11388 进一步澄清「模拟段可见摇晃移动，是挂饰小熊没有角度旋转，但是挂饰小熊有跟随移动」。

真机 hook `ctx.rotate` 计数确认：修前一个 400 帧窗口里 **`frames: 0`**（一次都没调），
修后 `frames: 400 / uniqueAngles: 77 / min: -82° max: 82°`。

### 吊环与 `anchorOffset`（T1，第 21 轮经 m08270 修正）

**语义（m08270 定下的）**：吊环是**绳子的零件**，永远钉在绳端；`doll.anchorX/anchorY`
调的是「图片相对吊环摆在哪」，吊环本身一动不动。

| 字段 | 范围 | 出厂 | 含义 |
|---|---|---|---|
| `doll.anchorX` | 0 ~ 1 | **0.5** | 吊环对准图片的横向哪里：0 = 左边缘，1 = 右边缘 |
| `doll.anchorY` | 0 ~ 1 | **0.0** | 吊环对准图片的纵向哪里：0 = 顶边，1 = 底边 |

**吊环位置 = `rope.hangPoint`（第 29 轮起：有模拟段时是 p4，没有时退回最后一节末端）**，不是 `rope.tipX/tipY`：

```js
// renderer/rope.js
get tailPoint() {                  // 最后一段绳的**末端**
  const a = pts[n - 2], b = pts[n - 1];
  const len = Math.hypot(b.x - a.x, b.y - a.y) || 1;
  return { x: b.x + (b.x - a.x) / len * this.overlap,
           y: b.y + (b.y - a.y) / len * this.overlap };
}
```

`_drawRope` 末端本来就沿末节方向延伸 `overlap` 像素穿进挂饰内部遮缝；
挂饰之前挂在最后一个**质点**上，所以看起来「挂点在最后一段绳的开头」。改用 `tailPoint`
之后两者重合。实测尾端与最后质点的距离恒为 `10.000px`（= `rope.overlap`）。

`anchorOffset` 返回的是「**从吊环走到图片静止矩形左上角**」：

```js
// renderer/doll.js，get anchorOffset()
const w = this._dollWidth();      // 图片走 naturalWidth/naturalHeight；emoji 走字体度量
const h = this.dollHeight;        // 已在 [heightMin 56, heightMax 128] 内
const px = w * ax;                // 吊环在图片坐标系里的 x（左上角为原点）
const py = ay * h;                // 吊环在图片坐标系里的 y
return { ox: -px, oy: -py };
```

> **第 22 轮修（m08776「挂点的左右调节是反向的」）**：上面这两行原来是
> `const px = -w * (ax - 0.5); return { ox: -w / 2 - px, oy: -py };`，化简即
> `ox = -w * (1 - ax)` —— 把左右**镜像**了。三种取值下正确与错误的对比：
>
> | 字段 | 正确（现在） | 旧式（错） |
> |---|---|---|
> | `anchorX = 0` | `ox = 0`（挂点贴左边缘，图在吊环**右**侧） | `ox = -w`（图在左侧） |
> | `anchorX = 0.5` | `ox = -w/2` | `ox = -w/2`（只有中点碰巧对） |
> | `anchorX = 1` | `ox = -w`（挂点贴右边缘，图在吊环**左**侧） | `ox = 0`（图在右侧） |
>
> 面板上的「左/右」按钮、预览画布、读数、`verify.cjs` 的 `anchorOffsetOf` 内联副本
> 全是照这个式子对齐的，所以旧版**自洽但与直觉相反**，只修面板会改出更怪的结果。
> 只在 `renderer/doll.js` 一处改正、其余随之对齐，按钮方向才回到「右 = `anchorX` 增大」。
> 教训：**参数语义与绘制公式必须只写一次**，校验在 `verify.cjs` 验收 10 里钉死。

**这里故意没有 `Math.min(heightMax, ...)`**。第一版把它夹在「锚点必须落在图片内部」上，
语义反演后夹取对象变成「图片相对吊环能沉多深」，再夹就会让 `anchorY = 1` 的大图
沉不到位（400px 图只能沉 128px）。现在 `anchorY = 1` 就是老老实实沉一整幅。

绘制链因此退化成**绕原点纯旋转** —— 旋转支点就是吊环：

```js
ctx.translate(tailPoint.x, tailPoint.y);   // 到绳端 = 吊环
ctx.rotate(bodyAngle);                     // 绕吊环转
ctx.transform(sx, 0, 0, sy, 0, 0);
ctx.drawImage(img, off.ox, off.oy, w, height);   // 图片矩形画在偏移后的位置
```

**吊环必须在 `ctx.restore()` 之后画**（`_drawLoop(anchorX, anchorY, 0, 0, 0)`），
画在 `save/restore` 里面会跟着图片一起被 `ctx.transform(sx,sy)` 拉伸。
角度与偏移都传 0：吊环不跟 `bodyAngle` 转、不被 `anchorX/anchorY` 挪。

**零物理改动**：物理侧完全不知道吊环在哪 —— 变的只是「画出来的图片怎么摆」。挂饰的**位置**取 `rope.hangPoint`、**朝向**取 `rope.tailAngle`（第 29 轮起；没有模拟段时分别退回 `tailPoint` / `tipAngle`）。
锚点不参与力学 —— 这是刻意的，理由见 [10 第 2.3 节](10-待办与改进方向.md)。

**配套修的一个隐患：绳长松弛**。`_limitLength` 只限制「每段不超过
`restLen * maxStretch`」，从不把段推回 `restLen`，于是段长会永久停在略大于 `restLen`
的位置。挂饰挂在最后一个质点上时这点松弛只让绳子多长 0.4%；挂在**延伸后的尾端**上，
它就会变成「娃娃离吊环越来越远」。修法：把总松弛量记进 `this.slack`，每个子步从
**最后一节**收回 `SLACK_RATE = 0.25` 倍（60fps 下 4 个子步合计收回约 68%）。
实测 30s 自由摆后 `slack = 0.0029px`、60s 剧烈驱动下 `|折线长 - 绳长| <= 0.013px`。

### 为什么不给挂饰加质点网（第 27 轮结论）

T2 曾给娃娃一张 4 点局部网（左上/右上/左下/右下），`M = R(θ) ∘ N` 一次性映射到屏幕。
它被撤除的原因是**质心是假的**：`step()` 围绕静止四角做固定解析解，
`centroidIndex()` 写死 `return 2`（左下角），**没有任何质量分布输入**。

要让「重心偏下」真的影响姿态，必须解耦合方程（4~8 自由度、隐式线性解），
而显式欧拉在 `soft=120`、`dt=1/60` 下一帧就发散到 `1e232`。
代价远超收益，用户因此选择刚体。

### 开关语义

`doll.puppet.enabled` 在 schema 里是 `CHOICES` 的 `"on"/"off"` 字符串
（`sanitize()` 只放行 `number`/`string`，布尔会被整条丢掉）。
`renderer/main.js` 的 `applySettings` 归一成布尔：

```js
window.CONFIG.doll.puppet.enabled = window.CONFIG.doll.puppet.enabled === true ||
  window.CONFIG.doll.puppet.enabled === "on";
```

关掉时 `_puppetPose` 返回的矩阵等价于 `N = I`（即 T1 老路），
**不能用上一帧缓存的 `N` 续着走** —— 那样形变会被冻住、永远不回正。
关掉后第一帧与 T1 的最大偏差 `3.55e-15px`；从未开启过则返回 `null`，走原地 `translate/rotate`。

| 字段 | 范围 | 出厂 | 含义 |
|---|---|---|---|
| `doll.puppet.enabled` | `off` / `on` | `off` | 出厂关闭，画面与 T1 完全相同 |
| `doll.puppet.soft` | 4 ~ 120 | 26 | 固有频率 `√soft` rad/s。26 时 1.5Hz 摆动形变 `0.96px`、4Hz 时 `4.69px` |
| `doll.puppet.damping` | 0.2 ~ 2 | 0.85 | 0.6 回正 `0.267s`、0.85 回正 `0.183s`、1 以上不过冲 |

### 吊环拖拽（第 24 轮 m09645）

编辑器没有位置滑块，除右侧「上/左/右/下」四按钮（每档 1%）外，还能在左侧预览图上**按住吊环拖动**。

三条不变量（改之前先读）：

1. **吊环永远钉在画布中心 `(cw/2, ch/2)`**，移动的是图片。`ox = hx - boxW*ax`、`oy = hy - boxH*ay`，
   与 `renderer/doll.js` 的 `anchorOffset` 是同一组式子。
2. **拖动期间图片矩形冻结**（`pointerdown` 时把 `ox/oy/boxW/boxH` 缓存进 `dragRect`），指针位置决定
   「吊环落在图片上的哪一点」：`ax = (px - L.ox) / L.boxW`。若让图片跟着指针跑，图片会在吊环下面一直
   滑走，永远拖不出想要的相对位置。
3. **坐标只换算一次**：`rel = (clientX - rect.left) / rect.width` → `px = rel * canvas.width`。
   canvas 内部分辨率固定 440、CSS 220、DPR 1.25，走比例换算对三套都成立，不做 DPR 修正。

命中半径 `HIT_R = 34`（吊环视觉半径约 15.5，留一倍余量）；没点中就不 `preventDefault`，页面正常滚动。
提交时机：`pointermove` 只调 `opts.setBoth(x, y)`（只重绘、不下发），`pointerup` 再走两次 `opts.set()`
的 60ms 合并通道 —— 否则每帧一次 IPC。

### 吊环编辑器的预览坐标系（第 22 轮补，m09043）

`settings/anchor-editor.js` 的 `render()` 必须画出**与线上同一个矩形**，否则用户看到的「吊环在挂饰上的位置」
和线上实际的挂点位置对不上。目前的实现：

```
anchorSource()                         render()
  kind: "emoji"                         const box = fit(cw, ch, src.w, src.h);   // 等比 contain，PAD = 40
  w: m.right - m.left   ──────────────▶  const w = box.w, h = box.h;
  h: m.h                                 const ox = box.sx, oy = box.sy;
  metrics: {left,right,ascent,descent,h,size}
                                       // 绘制：让字模包围盒正好铺满 (ox, oy, w, h)
                                       const unit   = w / (m.right - m.left);
                                       const cx     = ox - m.left  * unit;
                                       const base   = oy + m.ascent * unit;
                                       ctx.font = (m.size * unit) + "px " + EMOJI_FONT;
                                       ctx.textAlign = "left"; ctx.textBaseline = "alphabetic";
                                       ctx.fillText(emoji, cx, base);

                                       // 吊环：与绘制共用同一个矩形
                                       const px = ox + w * anchorX;
                                       const py = oy + h * anchorY;
```

三个必须一起成立的等式：

1. `src.w / src.h` 必须等于字模包围盒的真实宽高比 `(right - left) / h`。传 `1:1` 会让 `fit()` 按正方形分配空间。
2. `unit = boxW / (right - left)` 是「1 个字号单位 = 多少 CSS 像素」，横向、纵向共用同一个 `unit`（字形不会各向异性缩放）。
3. 吊环的 `(px, py)` 必须用**绘制同一个** `w/h/ox/oy`。第 22 轮前半的错误就是这里又按 `m.h` 缩了一次。

﻿读数（右侧两行）与吊环无关，只跟 `renderer/doll.js` 的 `anchorOffset` 对应：
`offX = -realW * anchorX`、`offY = -realH * anchorY`，其中 `realW/realH` 是线上真实 CSS 像素尺寸，

两个点之间画一条白线，**这条白线的长度就是「挂饰模拟段」的长度**（`chain.tail.length`）。
所以第 37 轮起面板上不再有「挂饰模拟段长度」滑块 —— 用户只要拖两个点，长度自己算出来，
点右下「应用」才下发。留滑块就有两个真相源，必然对不上。

### 挂饰锁定在挂点，不绕质点转（第 37 轮补，m12743）

> 用户 said (m12743): "重新说明，挂饰应该锁定于挂点，而不是质点"

第 37 轮前半曾把旋转支点挪到质点（`translate(pivot) … rotate … translate(-pivot)`），
被用户当场纠正。**现在的绘制路径里没有任何 `translate(pivot)` 对**，挂饰就是绕原点（= 吊环 = p4）转：

```js
const off = this.anchorOffset;
// 支点永远是吊环（原点）。这里没有 translate(pivot) … translate(-pivot)。
ctx.rotate(bodyAngle);
ctx.drawImage(this.img, off.ox, off.oy, w, height);
```

真机实测（假 rope `hangPoint (300,300)`、`tailAngle` 取 0 / 30° / 90°、`mass` 取 (0.5,0.5) / (0,0) / (1,1) 三组共 9 次）：
**每一次 `drawImage` 的平移分量都是 `(300, 300)`**，只有旋转分量在变（`(1,0)` → `(0.866,-0.5)` → `(0,-1)`）。
质点位置对绘制**零影响** —— 这正是「锁定于挂点」的含义。

`renderer/doll.js` 的 `get massOffset()` 保留了下来，但只当「质量中心」描述用：

```js
return { mx: w * (mx - ax), my: h * (my - ay) };
```

`(ax, ay)` 是挂点、`(mx, my)` 是质点，都在 `[0,1]` 的图片归一化坐标里；`w/h` 是挂饰真实 CSS 尺寸。
结果的意义是「质心相对吊环的偏移量」，将来接弹簧网（T4）时由它算力臂。

`settings/anchor-editor.js` 那边的「应用」按钮：

```js
const dx = (mass.x - hook.x) * size.w;
const dy = (mass.y - hook.y) * size.h;
const len = Math.sqrt(dx * dx + dy * dy);
return Math.max(1, Math.min(200, Math.round(len * 10) / 10));
```

1px 下限是为了防止两点重合时 `chain.tail.length = 0` 让 `nodeCount` 从 5 掉回 4、链路重建、挂饰跳一下。
`chain.tail.length` 必须留在 `settings-schema.js` 的 `ANCHOR_FIELDS` 白名单里，否则 `sanitize()`
会把算出来的长度整条丢掉（白名单只认 `GROUPS` / `ANCHOR_FIELDS` / `CHOICES` / `STRINGS`）。

## 六之三、挂饰是刚体（第 27 轮 m10287）
### 旋转角链路：第 29 轮已换成「最短路径低通」

第 27 轮当时从 `archive/f15-ce706f8` 取回的是 **F15 那套「展开 + 归整圈」**：

```js
// 第 27 轮版本（已删除）
this._bodyAngleCont += wrapPi(rawAngle - this._bodyAnglePrev);   // 无界累积
this._bodyAngle += (this._bodyAngleCont - this._bodyAngle) * fk;
const bodyAngle = this._softLimitAngle(this._bodyAngle * ratio) + this._bodyUnwrapOffset;
```

这套在真实使用中**永久失效**：归位要求「鼠标静止 0.6s」，而用户甩圈时鼠标一直在动
⇒ `_bodyAngleStill` 永远攒不满 ⇒ 状态漂到 `-1225°`（`record-20261022-150421.json`）
⇒ 小熊卡在一边，也就是 m05077 报的「偏向一侧」。

第 29 轮改成了**每帧折回主值域的最短路径低通**（详见上文
[## 六、娃娃旋转角](#六娃娃旋转角rendererdolljs第-29-轮重写)）：

```js
const d = wrapPi(rawAngle - this._bodyAnglePrev);
this._bodyAngle = wrapPi(this._bodyAngle + d * ratio * fk);
```

没有展开、没有归位、没有软限幅。状态天然有界。`_softLimitAngle` 整块删除。

**仍然有效的教训**（`verify.cjs` 验收 9 用的就是这条）：判断「穿越 ±180° 有没有反向猛甩」，
**不能用「单帧跳变」当判据**。`fk = 1 - exp(-(1/60)/0.08) ≈ 0.188`，低通会把 358° 的阶跃
摊成 60 帧、每帧几度，**每一帧都不大，但累计走了整圈**：

| 实现 | ±180° 单帧阶跃后累计转过 | 判定 |
|---|---|---|
| 展开／最短路径（正确） | **0.0°** | PASS |
| 朴素 `body += (raw - body) * fk` | **359.9°** | FAIL |

判据要量「累计行程与真实连续角之差」，而且基准必须由测试侧自己算，
不能用被测对象自报的中间量（那样朴素实现会自洽、恒为 0°）。

> **旋转中心（第 37 轮 m12635 → m12743 修正）**：**永远是吊环（原点）**。
> 第 37 轮前半短暂改成「绕质点」，用户 m12743 当场纠正，现已删除那对

## 六之四、挂饰模拟段：挂饰挂在 p4，朝向由 p4→p5 给（第 29 轮，m11010 / m11012）

### 为什么加这一段

第 27 轮把挂饰认定成刚体之后，它的旋转角只能来自绳子本身。原来用的是 `tipAngle`（整绳首尾连线角），
问题有两个：

1. **那是「整根绳有多斜」，不是「挂饰该朝哪」**。绳子短（出厂 60.5px）、只有 3 段，
   整绳连线角和末节方向差不了多少，挂饰看起来永远是「被绳子整体拽歪」，而不是「自己有个朝向」。
2. **没有可以调的东西**。用户 m11007 的原话是「现在已经拥有多段绳索的物理效果，
   将其增长一段不定长绳段用于挂饰的物理模拟，并在之后可以设定这段额外绳段的重量」——
   他想要的是一个**独立的、有重量的**朝向参考，而不是让整根绳兼任。

### 拓扑

```
p1 ── p2 ── p3 ── p4 ┄┄ p5
↑                      ↑     ↑
挂点                 挂饰挂这  朝向看这条
(鼠标)              (hangPoint) (tailAngle)
└────── 主体 3 段 ─────┘└ 模拟 ┘
      restLen 各 20.16px      tail.length 26px
```

- **p1~p4 是主体**，`chain.segments = 3`（段数）⇒ `rebuild(len, 4)`（质点数）。
- **p5 是额外的**，`chain.tail.enabled` 为真且 `length > 0` 时追加。
- 主体的 `restLen` **恒等于 `length / (n - 1)`**，挂饰模拟段长度是在这个之外另加的。

### ★ 挂饰模拟段长度必须「额外加」，不能「从总长里切」

这是第一版踩的坑，数据在这里：`length = 60.5px`、主体 3 段。

| 做法 | 主体段长 | 结果 |
|---|---|---|
| `mainRest = (length - tailLen) / (n - 1)`（**从总长切**） | 只剩 11.5px（tail=26）~2.8px（tail=52） | 整链失稳，`polylineLength` 冲到 300+px，`hangPoint` 乱飞 |
| `mainRest = length / (n - 1)`（**额外加**） | 恒定 20.16px | 稳定，挂饰模拟段长偏差 0.000px |

原因很直白：PBD 的稳定性依赖「相邻质点间距与约束刚度匹配」。把每段压到 2.8px
而重力还是 3300px/s²，一个子步的自由落体位移就超过段长的好几倍，约束求解追不上。
**所以「挂饰模拟段」是额外的一段绳子，不是从原有绳子里分出来的。**

### 四个新 API

```js
get tailAngle()   // Math.atan2(p5.x - p4.x, p5.y - p4.y)
                  // 竖直向下 = 0，顺时针为正；值域 (-PI, PI]，纯几何量，无滤波无限幅
get hangPoint()   // 有模拟段：p4 沿 p4->p5 方向再延伸 overlap 像素（与 tailPoint 同口径）
                  // 无模拟段：退回 tailPoint（= pts[n-1] 沿末节延伸）
get hasTail()     // 末点是不是 isTail
_tailLength()     // cfg.tail.enabled 为 false / "off" / 0 时返回 0
```

`tailAngle` 的坐标系与 `tipAngle` 完全一致（都是 `atan2(dx, dy)`），
所以 `renderer/doll.js` 里换字段不用改任何坐标换算。

### 三处必须同步改的约束求解

挂饰模拟段的静止长度和主体不一样，但约束求解器原来假定「所有段一样长」：

| 位置 | 原来 | 现在 | 不改会怎样 |
|---|---|---|---|
| `_solveConstraints(stiffness)` | `const rest = this.restLen;` 在**循环外** | 循环内 `const rest = this._restOf(i);` | 挂饰模拟段被反复拽回 20.16px（实际 26px），每帧被强行拉短 5.8px |
| `_limitLength(maxStretch)` | `segLimit = restLen * maxStretch` | `segLimit = segRest * maxStretch`（按段） | 挂饰模拟段的最大拉伸量算错 |
| `_limitLength` 结尾的 slack | `polylineLength - restLen * (n-1)` | `polylineLength - Σ _restOf(i)` | slack 恒为正，`SLACK_RATE` 每帧多收一段的量，绳子看起来越甩越短 |
| `resetVertically()` | `p.y = anchorY + restLen * i` | 逐点累加 `_restOf(i)` | 竖直初值里 p5 落在 80.6px 而不是 86.5px，启动瞬间有个假位移 |

### `renderer/main.js` 的两个连带修复

1. **`ropeCfg()` 必须带 `C.tail`**。`tail` 是 `CONFIG` 的顶层段，不在 `chain` 里，
   原来 `Object.assign({}, C.physics, C.chain)` 根本没把它传进去 —— 模拟段之所以能工作，
   纯粹因为 `_tailLength()` / `_tailMass()` 的兜底默认值恰好等于 `config.js` 里的值。
   这种「靠默认值撞对」的状态最危险：面板一改值就失效。
2. **`nodeCount` 必须算上模拟段**。`applySize()` 与 `applySettings()` 都用
   `rope.count !== nodeCount` 判断要不要重建链，原来 `nodeCount = segs + 1`（= 4），
   开关模拟段后 `rope.count` 变成 5 而 `nodeCount` 还是 4 —— 判据成立、不重建，
   表现为「面板上开了模拟段，但绳子上什么都没有」。

### 面板与配置

`renderer/config.js`：

```js
chain: {
  ...
  tail: {
    enabled: true,
    length: 26,     // 像素。占绳长约 43%
    mass: 20.0      // 末端质点相对单个绳段的质量倍率，不是克数
  }
}
```

设置面板在「绳子」页，三个字段：`chain.tail.enabled`（下拉 启用/关闭）、
`chain.tail.length`（0~80px）、`chain.tail.mass`（1~50 倍）。

**`chain.tail.enabled` 的三种写法都要认**：`sanitize()` 只收 `number` / `string`，
布尔值会被整条丢掉，所以面板提交的是字符串 `"on"` / `"off"`。
`renderer/rope.js` 的 `_tailLength()` 早期只判断 `t.enabled === false`，
字符串 `"off"` 不等于 `false` ⇒ 关闭开关完全无效。
现在 `renderer/main.js` 的 `applySettings()` 里统一折成布尔，`rope.js` 那边也兼容三种形态。

### 挂点为什么必须严格是 p4（第 31 轮，m11899）

用户原话：「你挂错了，小熊挂在了 p5 上，而非挂饰模拟段的起始位置 p4，而且没有绑定挂饰模拟段方向（p4→p5）」。

**代码里有两个「末端点」，之前挂饰用错了其中一个：**

| 点 | 谁提供 | 位置 | 谁用它 |
|---|---|---|---|
| 挂点 | `rope.hangPoint` | 有模拟段 = **p4**；无模拟段 = `tailPoint` | ✅ `renderer/doll.js` 的 `anchorX/anchorY`、吊环 |
| 绳端 | `rope.tailPoint` | 最后一段再沿方向延伸 `overlap`（p5 + 10px） | `_drawRope` 的末端、记录器 |

第 29 轮 ~ 第 30 轮之间 `renderer/doll.js` 读的是 `rope.tailPoint`，且当时的 `hangPoint` 返回
「p4 + overlap 沿 p4→p5」。两个候选点离 p4 都差 10~26px，所以挂饰看起来永远挂在 p5 附近，
旋转支点也跟着落在模拟段末端 —— 视觉上就是「挂错了」。

现在（第 31 轮）：
- `rope.hangPoint` **严格返回 p4 的坐标本身**，不做任何 offset；
- `renderer/doll.js` 读 `rope.hangPoint || rope.tailPoint`（后者只在没有模拟段时兜底）；
- `rope.tailPoint` 的语义收窄成「绳子实际画到的末端」，只给绘制与记录器用。

**朝向这一条本来就对**：`renderer/doll.js` 的 `rawAngle = rope.tailAngle`，而
`rope.tailAngle = atan2(p5.x-p4.x, p5.y-p4.y)` —— 一直是 p4→p5。
用户看到的「没绑定」是**支点错了**造成的错觉：支点落在 p5、图片又绕 p5 转，
看起来像整只熊在原地打转；支点回到 p4 之后，p4→p5 的倾角才表现为「熊沿模拟段方向摆」。

`verify.cjs` 验收 11.7 把这条钉住：`overlap = 10` 时 `|hangPoint − p4| = 0`、
`|hangPoint − p5| = 52`（模拟段长度）。

### 挂饰模拟段质量为什么默认 20 倍（不是 2 倍）

用户 m11012 说「目前默认为于单绳索段的 2 倍重量」，但实测 2 倍太轻。扫描数据
（总长 60.5px、tail=26、出厂物理、稳态 i>300、±40px@1.2Hz 驱动）：

| `tail.mass` | `tailAngle` 平均 | 峰值 | 朝天帧占比 |
|---|---|---|---|
| 2 | 78.5° | 99.5° | 50% |
| 5 | 47.5° | 77.1° | — |
| 10 | 46.8° | 91.4° | — |
| **20（出厂）** | **37.4°** | **65.8°** | **0%** |
| 50 | 34.6° | 62.6° | — |

2 倍时平均 78.5°（一半时间朝天）。20 倍时平均 37.4%、朝天比例为 0，而 50 倍相比 20 倍
只再降 3°，边际收益消失。

## 七、渲染顺序与绘制细节

`renderer/doll.js` 的 `draw(state)` 顺序：

0. **指针不画** —— 由 Windows 画在独立光标平面，永远在本画布之上（见第二节）
1. `ctx.translate(hangPoint.x, hangPoint.y); ctx.rotate(bodyAngle)` —— 娃娃
2. `_drawRope(rope, attach)` —— 绳子（**第 30 轮 m11815 搬到娃娃之后**）
3. `_drawLoop(hangPoint.x, hangPoint.y, 0, 0, 0)` —— 吊环，永远最后画（它要盖住绳端）

所以肉眼看到的层级是「系统指针 > 吊环 > 绳子 > 娃娃」。
**第 30 轮（m11815）之前绳子是第 1 步、娃娃是第 2 步，绳子会被娃娃盖住；现在反过来了。**
绳子快速翻上去时仍然只能表现为**从指针背后穿过**，不可能盖住指针（指针在独立平面）。

验证方法（不需要真机盯着看）：用 vm 加载真实 `renderer/doll.js`，在假 ctx 上记录落笔顺序，
断言 `indexOf('fillText') < indexOf('stroke')` 且最后一次 `arc` 在两者之后。实测序列：
`… rotate → strokeText → fillText → restore → (绳子 beginPath…stroke ×2) → (节点 arc…fill) → (吊环 arc → stroke)`。
绳子快速翻上去时只能表现为**从指针背后穿过**，不可能盖住指针。

### `_drawRope` 的两个关键点

**中点法二次贝塞尔**（`renderer/doll.js:211-217`）：

```js
ctx.moveTo(drawPts[0].x, drawPts[0].y);
for (let i = 1; i < drawPts.length - 1; i++) {
  const midX = (drawPts[i].x + drawPts[i + 1].x) / 2;
  const midY = (drawPts[i].y + drawPts[i + 1].y) / 2;
  ctx.quadraticCurveTo(drawPts[i].x, drawPts[i].y, midX, midY);
}
```

**首点替换必须有距离保护**（`renderer/doll.js:171-185`）：

```js
const gapLive = Math.hypot(live.x - pts[0].x, live.y - pts[0].y);
const seg01 = pts.length >= 2 ? Math.hypot(pts[1].x - pts[0].x, pts[1].y - pts[0].y) : Infinity;
if (gapLive <= Math.max(seg01 * 1.5, 8)) {
  drawPts[0] = { x: live.x, y: live.y, px: live.x, py: live.y };
}
```

没有这个保护时，`pts[0]` 与指针差 383px（实测），把 `drawPts[0]` 换成指针位置
会凭空造出一根几百 px 的假线段，画面上是「一根长杆从指针斜穿出去」。

### `_measureEmoji`（`renderer/doll.js:91` 定义、`:344` 调用）

用 100px 字号量 `actualBoundingBoxAscent/Descent/Left/Right` 来精确对齐 emoji，
因为 emoji 字形自带透明边距，直接按字号画会偏。

**彩色 emoji 的 `fillStyle` 必须保留默认黑色** —— 曾误设 `ctx.fillStyle = "#fff"`，
导致 🧸 整个变白、在白底画布上凭空消失。

### 档位的三条入口与两条状态（第 6 轮）

档位定义只有一份：`settings-schema.js` 的 `PRESETS`（数组）与 `BY_PRESET`（按 id 索引）。
**面板和托盘都从这里读**，否则两边的"当前是哪一档"会打架。

| 入口 | 触发 | 是否立即生效 |
|---|---|---|
| 面板 chip | `selectPreset(p)` → 只写 `selectedPresetId` + `overrides` | ❌ 预览，等「应用」 |
| 面板「应用」 | `applyPending()` → `push(flat)` → `settings:set` | ✅ 同一链路 |
| 面板滑块 | `onSlide()` → `push()`（60ms 合并） | ✅ 立即 |
| 托盘「档位」 | `applyPresetById(id)` → 直接 sanitize + store + broadcast | ✅ 立即 |

两个高亮态必须分开：

- `.chip.active`（实心蓝）= **真正生效**的那个档。判定在 `refreshChrome()`：
  把 `applied` 拍平成 `{key: value}`，与每个档位的 `values` **逐键比对**（键数必须相同、每项差 ≤ 1e-9）。
  找不到就全灭（说明用户拖过滑块，已经不在任何档位上）。
- `.chip.selected`（描边蓝）= 用户点了但还没应用。同一时刻最多一个。

**主进程侧同一套判定**：`main.js` 的 `activePresetId()` 用 `settingsSchema.toFlat(currentOverrides)`
做同样的逐键比对，托盘 radio 的 `checked` 由它决定。换档后必须 `rebuildTrayMenu()` 才会移动勾。

### 覆盖层如何应用设置（`renderer/main.js:269` `applySettings`）

```js
function applySettings(payload) {
  latestOverrides = ...;
  deepAssign(window.CONFIG, JSON.parse(JSON.stringify(pristineDefaults)));  // 先回出厂
  deepAssign(window.CONFIG, overrides);                                     // 再盖覆盖值
  syncCfg();                       // 把 CONFIG 分发给 rope / renderer / cursor
  // 只有段数或绳长真的变了才重建绳子
  if (...) { rope.rebuild(len, nodeCount); rope.resetVertically(); }
}
```

两个关键点：

1. **是整份替换，不是增量合并**。每次收到 `{ overrides }` 都先回到 `pristineDefaults` 再盖一遍，
   否则"取消某项覆盖"就没法实现（用户点「恢复出厂」下发的是 `{}`）。
2. **绝对不能调 `applySize()`**。它结尾无条件 `rope.teleport(attach) + rope.resetVertically()`，
   拖重力滑块时 60ms 一次把绳子扳回竖直，摆臂被反复打断，看起来像"卡住"。

`pristineDefaults` 由 `captureDefaults()`（`renderer/main.js:260`）在启动时和
每次 `reloadConfig()` 后抓取。`reloadConfig()` 末尾必须重新 `applySettings({overrides: latestOverrides})`，
否则重载 `config.js` 会冲掉用户调过的手感。

## 八之二、诊断记录器（第 13 轮新增）

要解决的问题：手感出问题时，光看屏幕分不清「是绳子在拉，还是娃娃自己在飞」。
把当前状态每 0.1s 落一条到文件，事后对着数据找原因。

### 数据流（跨三个进程）

```
面板点「开始记录」            settings/settings.js
      ↓ window.settingsApi.record({cmd:"start"})
      ↓ ipcRenderer.invoke("record:cmd")
主进程                        main.js registerRecordIpc()
      ↓ win.webContents.send("record:cmd", {cmd:"start"})
渲染进程（覆盖层）            renderer/main.js 的 onRecordCmd
      ↓ recorder.start({intervalMs:100, maxSamples:18000})
      ↓ 每帧 frame() 末尾 recorder.tick(now)
采样 … 每 100ms 一条
      ↓ onStatus → window.api.sendRecordStatus(st) → "record:status" → 面板 + 托盘
停止（按钮 / 托盘 / 撞上限）
      ↓ onStop → window.api.saveRecord(data) → ipcRenderer.invoke("record:save")
主进程                         serializeRecord() 写盘 → 推 "record:saved" 给面板
```

**托盘也有同一个开关**（`main.js` `toggleRecording()`，标签在「开始诊断记录 / 停止诊断记录」之间切换）。
主进程的 `recording` 变量由渲染层回推的 `record:status` 维护，不自己猜。

### 三条纪律（写在 `renderer/recorder.js` 文件头）

1. **只读物理，绝不写回** —— 记录器不许改变手感。它不碰 `rope` 的任何字段。
2. **算不出来的量写 `null`，绝不用 0 冒充** —— 0 会被读成「真的没受力」。首条样本的
   `ropeF` 就是 `null`（没有上一条样本，差分不出加速度）。
3. **每条样本都带墙钟时间戳 `w`** —— 覆盖层被隐藏时 rAF 会停，从 `t` 与 `w` 的差值就能看出漏采。

### 采样节拍为什么不用 `setInterval`

`tick(now)` 由主循环 `frame(now)` 每帧调用，内部按 `intervalMs` 抽稀。
覆盖层隐藏时 rAF 会停 —— 用定时器只会在看不见的时候继续堆样本。

节拍推进用 `this._nextAt += this.intervalMs`（**理论节拍**），而不是 `t + interval`：
后者会把每帧的舍入误差一直累积下去，10 分钟能漂出好几条样本。
另有 `if (this._nextAt < t) this._nextAt = t + this.intervalMs;` 兜底，避免长时间卡顿后疯狂补采。

实测（244 条 / 24301ms）：`97ms×117`、`103ms×116`，平均 **100.00ms**，理论应采 244 = 实际 244，
最大累计漂移 68ms。97/103 交替是 60fps 帧量化（16.67ms）的抖动，不是 bug。

### 「熊受的力」到底是什么力 —— 推导

先看 Verlet 里每个质点受什么：`a = 绳力/m + 重力 + 风 + 空气阻力`。
反解得：

```
绳力 = m · (a + kDamp·vAvg − (重力 + 风 + 空气阻力))
```

- `a` 用相邻两条样本的 `vAvg` 差分算。
- **`kDamp·vAvg` 这一项必须补回去**：Verlet 每子步有 `keep = exp(-k*h)` 的乘性衰减，
  折合每秒 `-k·v` 的减速度。不补的话算出的绳力会系统性偏小
  （k=0.3、v=1000 时约差 300px/s²，接近重力的 1/10）。
- `kDamp` 取 `rope.dampingRate()`，`重力/风` 取 `rope.environmentAccel()` ——
  **这两个方法是第 13 轮从 `_step()` 里抽出来的，就是为了让记录器用同一份公式**，
  否则两处漂移。

校验意义：**静止竖直时 `ropeF` 精确等于 `m·g`**（`mass=1.6` × `gravity=3300` = 5280，
实测 31 条全部 5280.0、最大偏差 0.00%）。摆到最低点约 `m(g + v²/L)`（实测峰值 16.65×m·g）。

单位是 `px/s² × 相对质量`，**不是牛顿** —— 程序里没有真实的质量/长度换算，
绝对值只用于前后对比与量级核对。

### 采样字段

| 字段 | 含义 |
|------|------|
| `t` / `w` | 相对开始时刻的 ms / 墙钟 ms |
| `cx,cy` / `ax,ay` | 鼠标位置 / 挂点位置 |
| `len,restLen,tension` | 当前绳长 / 静止绳长 / 张力比（0~1） |
| `tipX,tipY,angle,angVel` | 绳端坐标 / 弦角（度）/ 角速度（度每秒，±180 折回后差分） |
| `nodes[{x,y,vx,vy}]` | 每个质点的位置与 Verlet 速度 `(x-px)/h` |
| `segs[]` | 每节长度（用来验链长守恒） |
| `bear{x,y,vx,vy,speed,ax,ay,acc,ropeFx,ropeFy,ropeF,mass}` | 娃娃（末节质点）的全部运动学与受力 |
| `doll{raw,drawn,clamped}` | 画出去的角度 / 没限幅前的角度 / 是否被 `angleLimit` 压住 |

速度取 `(p.x - p.px) / h`，`h` 用和 `_step` 一样的钳制
（`Math.min(1/60, Math.max(1/480, cfg.fixedStep || 1/240))`）——
否则 `fixedStep` 调到 1/60 或 1/480 时报出来的速度会整体偏大/偏小。

### 落盘格式

`%APPDATA%\sunny-doll\records\record-YYYYMMDD-HHMMSS.json`，**每条样本一行**：

```json
{
  "version": 1,
  "intervalMs": 100,
  "startedAt": 1758...,
  "stoppedAt": 1758...,
  "stopReason": "user",
  "meta": { "screen": {...}, "ropeLength": 64.8, "restLen": 21.6, "nodes": 4, "config": {...} },
  "summary": { "count": 244, "durationMs": 24301, "maxSpeed": 0, "maxAngle": 0, "maxForce": 5280 },
  "samples": [
    {"t":0,"w":...,...},
    {"t":100,"w":...,...},
    ...
  ]
}
```

一条一行是为了能直接 `grep` / `Select-String` 挑样本。
`meta.config` 是**开录那一刻**的 `CONFIG` 完整快照 —— 中途改设置会让曲线前后不可比，
分析时必须看这个而**不是**现在的面板值。

`stopReason` 是 `"user"`（点了按钮 / 托盘）或 `"auto"`（撞到 `maxSamples` 上限，
默认 18000 条 = 30 分钟）。两种都从 `onStop` 这一个出口出，调用方不用分别处理。

### 一个必须绕开的坑：`status` 不能写成 getter

`Recorder` 内部三处都写成 `this.status()`。做成 `get status()` 会变成"调用一个对象"，
直接 `TypeError: this.status is not a function`。

另一个：`_sample()` 里取 `doll` 配置必须三层兜底
`(r && r.cfg && r.cfg.doll) ? ... : (window.CONFIG && window.CONFIG.doll) ? ... : {}`。
少一层就会在"渲染器还没建好"的那一帧抛 `TypeError: Cannot read properties of undefined
(reading 'bodyRotateRatio')` —— 而 `tick()` 是在 rAF 主循环里调的，**主循环没有 try/catch，
抛一次整帧就断**。
