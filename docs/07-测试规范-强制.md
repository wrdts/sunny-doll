# 测试规范（强制）

> 本文件是**强制规范**，不是建议。每次做任何物理/渲染效果的测试前，必须逐条核对。
> 违反其中任意一条，得到的测试数据即为无效数据，不得用于判断效果，也不得写入 `docs/` 任何结论。

---

## 铁律 0：测试前必须断开真实鼠标

**这是第一铁律。** 历史事故：多次因为真实鼠标在被测窗口上移动，
导致判断"指针效果"时出现严重失误（用户 m01563 第 3 条明确指出）。

### 为什么必须断开

程序有两路指针输入（见 `docs/02-系统架构.md`）：

1. 渲染进程的 `mousemove` 事件（真实鼠标）
2. 主进程 `screen.getCursorScreenPoint()` 每 8ms 轮询，通过 IPC 推送

只要真实鼠标动一下，第 1 路就会触发；第 1 路停了 200ms 后第 2 路又接管。
所以脚本调用 `__doll.setPointer(x, y)` 根本钉不住坐标——
实测会出现光标在 `(768,400)` 与 `(885,459)` 之间来回跳、`speed` 冲到 8981、
`angle` 在 -134°~+102° 乱翻。**这是测试污染，不是程序缺陷。**

### 正确做法：用指针锁（指针控制权双模式）

程序内置两种模式，由 `renderer/config.js` 的 `debug.lockPointer` 控制初始值：

| 模式 | `pointerLocked` | 谁控制指针 | 用途 |
|---|---|---|---|
| 锁定（测试模式） | `true` | **只有脚本** `__doll.setPointer()` | 做物理/渲染测试 |
| 解锁（正常模式） | `false` | 真实鼠标 | 日常使用 |

**三种切换方式**（任选）：

1. 运行时调用：`window.__doll.lock(true)` / `window.__doll.lock(false)`
2. 按 `Ctrl + Alt + L` 切换
3. 改 `renderer/config.js` 的 `debug.lockPointer` 后重启

### 每次测试的标准流程（照抄）

```js
// 1. 锁定（断开真实鼠标）
await send("Runtime.evaluate", { expression: "__doll.lock(true)" });

// 2. 确认锁生效
const st = await send("Runtime.evaluate", { expression: "__doll.locked", returnByValue: true });
if (st.result.value !== true) throw new Error("指针锁未生效，测试中止");

// 3. 把指针钉到一个确定位置，并静止 300ms 以上让物理收敛（非常重要）
await send("Runtime.evaluate", { expression: "__doll.setPointer(768, 432)" });
await sleep(350);

// 4. 此时才开始采集数据
...

// 5. 【必须】测试结束后无论成功失败都交还鼠标
//    用 try/finally 保证异常也能执行到
try {
  ... 测试 ...
} finally {
  await send("Runtime.evaluate", { expression: "__doll.lock(false)" });
}
```

### 采集前的静止期（第二条常被忽略的坑）

`setPointer` 把指针钉到新位置，本身就是一次**位移**，会给物理注入冲量。
如果立刻开始采集，前若干帧是"复位冲击"的尾部，数据完全不可用。

实测反例：某个测试场景切换时，`setPointer` 跳回屏幕中心，
导致"慢拖 200px/s"场景测出 `max=61°` 的异常值——那个 61° 是复位冲击，不是慢拖。

**规则：每次改变测试场景（尤其是重置指针位置）后，必须静止 ≥ 300ms 再采集。**

## 铁律 1：必须走正式 API，不许手写物理循环

历史事故：多次手写 Verlet 子步循环、手动设置 `r.accumulator`、绕过 `update()` 直接调 `_step()`，
产出了互相矛盾的假数据：

- `dx=0.0` 却报告角度 76°
- `damp 0.030` 下 `v=1000` 只有 2.8°，而 `v=600` 却有 12.2°（速度越大偏角越小，物理上不可能）
- `_stab.cjs` 报告 1200px/s 折叠到 `dy=17.9`（换成正式 `update()` 后同一场景完全健康）

**原因**：`_step()` 依赖 `this._stepIndex / this._stepTotal`（支点在本帧内推进到哪个位置）
这类跨帧状态。绕过 `update()` 直接调 `_step()`，这两个量永远是上次 update 留下的残值，
支点插值会算错，产出的角度毫无意义。

> 第 3 轮重构删掉了 `_lastH` 与 `ratio`（详见 [04](04-已知缺陷与待修.md) F9），
> 但 `_stepIndex / _stepTotal` 仍然是必须由 `update()` 维护的状态，规矩不变。

**正确做法**：

```js
const r = new RopeChain(Object.assign({}, C.physics, C.chain, { turbulence: 0, followMode: "velocity" }));
r.rebuild(60, cfg.segments + 1);   // 绳长、【质点个数】= segments + 1
// 当前线上 segments = 3 ⇒ 4 个质点。
// 别写成 r.rebuild(60, cfg.segments) —— 那是「3 个质点 = 2 段」，
// 会让你以为在测软绳、其实测的是硬得多的东西（第 4 轮踩过这个坑）。
r.setAnchor(400, 300);     // 挂点
r.resetVertically();       // 竖直静止初始态
for (const x of xs) { r.setAnchor(x, 300); r.update(1 / 60); /* 此时读 r.tipAngle */ }
```

## 铁律 2：判断"是否正常"要用正确指标

历史事故：用"接近水平的占比"判断绳子是否被甩平，结果摆动穿过水平的那一瞬间被误判成缺陷。

**正确的指标**：

| 指标 | 定义 | 含义 |
|---|---|---|
| `dy` | `(绳端.y - 挂点.y) / 绳长` | 1 = 完全竖直下垂，0 = 水平，负 = 翘到挂点上方 |
| `tipAngle` | `atan2(绳端.x - 挂点.x, 绳端.y - 挂点.y)` | 0 = 正下方，正 = 向右偏 |
| 水平偏移 | `abs(绳端.x - 挂点.x)` | 用户肉眼看到的"向一侧偏移"是多少像素 |
| 链自折 | 相邻节点 `y` 不增（`pts[k].y - pts[k-1].y < 0.5`） | 绳子拧成 Z 字形，渲染成波浪乱线 |
| 拍平 | `abs(tipAngle) > 88°` | 绳子被甩到几乎水平 |

**注意**：`dy` 与偏角是**几何约束关系** `dy = cos(偏角)`（近似，软绳有小偏差），
所以"要大偏移"与"要垂得住"在绳长固定时互斥。判断时必须同时看 `dy` 和水平偏移像素，
只看偏角会得出错误结论。

## 铁律 3：速度驱动必须连续，不能阶跃

历史事故：直接给速度做阶跃（0 → 800px/s 一帧完成），等效加速度 `800 × 60 = 48000 px/s²`，
是重力（3300）的 **14.5 倍**，解析模型必然数值发散（实测 859°、1320°）。

**更隐蔽的一次**：`rope.test.cjs` 的旧 `sweep()` 每帧给 20px 位移（= 1200px/s 瞬时起速），
等于给摆锤一次 1200px/s 的冲量。能量守恒 `½v² = gL(1-cosθ)` 代入 v=1200、g=3300、L=90
得 `cosθ = -1` ⇒ **θ = 180°，物理上就该翻过去**。翻顶之后是混沌轨迹，
导致 `[4] 向左甩` `[9] 帧率无关` `[14] fixedStep 无关` 三项断言全部假失败。
现在测试统一用 `rampDrive()`。

**正确做法**：用 smoothstep 做加速/减速斜坡。

```js
function path(speed) {
  const xs = []; let x = 400;
  const ramp = (n, v0, v1) => {
    for (let i = 0; i < n; i++) {
      const u = (i + 1) / n;
      const w = u * u * (3 - 2 * u);        // smoothstep
      const v = v0 + (v1 - v0) * w;
      x += v * (1 / 60); xs.push(x);
    }
  };
  ramp(8, 0, speed);                        // 加速 8 帧
  for (let i = 0; i < 20; i++) { x += speed / 60; xs.push(x); }   // 匀速 20 帧
  ramp(8, speed, 0);                        // 减速 8 帧
  for (let i = 0; i < 50; i++) xs.push(x);  // 静止 50 帧
  return xs;
}
```

## 铁律 4：正弦往复 ≠ 真实鼠标

历史事故：用完美正弦往复测试，挂点加速度峰值达到重力的 0.94 倍（7540 / 8000），
摆角一路累加到 537° 绕圈。这是驱动本身的病态，不是程序缺陷。

**真实鼠标的速度是「加速 → 匀速 → 减速 → 停」的片段组合**，不是连续正弦。
凡是评估手感，必须用铁律 3 的 `path()` 生成路径，或绕圈/甩动等分段路径。

正弦往复只适合测试**单一频率下的稳定性极限**，不能用来判断手感。

## 铁律 5：截图与坐标的正确姿势

### 截图

- **不要**用整屏 `CopyFromScreen`——全屏透明置顶窗会被聊天窗口遮挡，截到的是聊天窗口。
- **要**用画布导出：`document.getElementById('stage').toDataURL('image/png')`
- 导出前必须垫底，否则白色指针在白底上看不见：
  ```js
  g.save();
  g.globalCompositeOperation = 'destination-over';
  g.fillStyle = '#dfe3ea';
  g.fillRect(0, 0, c.width, c.height);
  g.restore();
  ```

### 坐标

- `[System.Windows.Forms.Cursor]::Position = ...` 设置光标**无效**（被全屏透明窗拦掉，或被主进程轮询覆盖）。
- 必须用 `__doll.setPointer(x, y)`，且**配合铁律 0 的指针锁**。

### 局部放大

```powershell
Add-Type -AssemblyName System.Drawing
$src  = [System.Drawing.Image]::FromFile("$PWD\_z.png")
$crop = New-Object System.Drawing.Bitmap(400, 480)
$g    = [System.Drawing.Graphics]::FromImage($crop)
$g.DrawImage($src, (New-Object System.Drawing.Rectangle(0,0,400,480)), (New-Object System.Drawing.Rectangle(1280,480,400,480)), [System.Drawing.GraphicsUnit]::Pixel)
$g.Dispose()
$big = New-Object System.Drawing.Bitmap(800, 960)
$g2  = [System.Drawing.Graphics]::FromImage($big)
$g2.InterpolationMode = [System.Drawing.Drawing2D.InterpolationMode]::NearestNeighbor
$g2.DrawImage($crop, 0, 0, 800, 960)
$g2.Dispose(); $big.Save("$PWD\_z_zoom.png", [System.Drawing.Imaging.ImageFormat]::Png)
```

## 铁律 6：`__doll` 需要 `debug.exposeState`

`renderer/config.js` 的 `debug.exposeState` 为 `false` 时 `window.__doll` 不存在。
要 CDP 测试必须先改 `true` 并 `Page.reload({ ignoreCache: true })`。

**测试完必须改回 `false`**（交付态），否则每次启动都会暴露内部对象。

## 铁律 7：编辑代码的姿势

`[System.IO.File]::ReadAllLines` + 按行号替换，在这台机器上**极易错位**，
已造成多次事故：丢掉闭合大括号、覆盖相邻行、删掉 `const anchorX = ...` 导致小熊不显示。

**每次改完必须**：

```powershell
node --check <文件>          # 必须 EXIT=0
Get-Content <文件> | Select-Object -Skip <行号-3> -First 10   # 回读确认
```

插入代码后要**重新计算行号**再做下一次插入。

## 铁律 8：跨工具 / 跨编码写字面量，改完必须自检

第 5 轮（设置面板）踩了三个**纯字面量失真**的坑，都不是逻辑错：

| 现象 | 真凶 | 预防 |
|---|---|---|
| 除被拖的那一项外，所有字段显示值全空；主进程收到 `{}` | 用 `controls.length = 0` 清空一个**普通对象**（真的创建了 `"length"` 键），`refreshReadouts()` 读 `0.field.readout` 抛 `TypeError` | 数组用 `length = 0`，对象用 `for (k of Object.keys(o)) delete o[k];`，遍历时 `if (!c \|\| !c.field) continue;` |
| `"0.300"` 变成 `"0."`、`"0.000150"` 变成 `"0.0001"` | `.replace(/\.$/, "")` 被 PowerShell here-string 吃成 `.replace(/.$/, "")`（删最后一个字符） | 改用 `endsWith(".") + slice(0, -1)`，不用正则 |
| 补丁脚本 10 处替换全部命中 0 次 | `main.js` 是纯 CRLF，here-string 里是 LF | 读入后先 `raw.replace(/\r\n/g, "\n")` 再匹配 |

**规则**：
1. 在 here-string 里写正则或多行模板，先 `console.log` 出那几行和预期逐字对照。
2. 每个替换都要 `if (s.split(old).length - 1 !== 1) throw new Error(...)`，**在写盘之前断言**。
   这样命中失败时文件没被破坏，代价只是重跑一次脚本。
3. 能不用正则就不用 —— `endsWith` / `indexOf` / `slice` 不含反斜杠，不会被吃。

## 铁律 9：测设置面板必须跨三层，不能只看截图

设置面板横跨「面板渲染进程 → 主进程 → 覆盖层渲染进程」三个边界。详细做法见
[`docs/03-测试方法论.md`](03-测试方法论.md) 第三之二节。最少要覆盖：

1. **纯 Node 存储层**：防抖生效（`set` 后文件不存在）、`flush` 后落盘、
   重新 `init` 读回一致、坏 JSON 静默退回 `{}`。
2. **纯 Node 物理层**：走 `sanitize` → `deepAssign` → 真实 `RopeChain`，
   量周期 / tau / 匀速拖动稳态角。判据是**方向**（第 1 档必须周期最长、倾角最大）。
3. **真实 Electron IPC**：自己建 `BrowserWindow` 加载 `settings/settings.html`
   （用真的 `settings-preload.js`），`executeJavaScript` 操作 DOM，
   主进程侧记录 `ipcMain` 收到什么。**不要用 CDP 去测面板**，它是独立窗口，另开 target 很麻烦。
4. **覆盖层语义**：连续下发两个不同的单项覆盖，第二次之后第一项必须**回到出厂值**
   —— 验证 `applySettings` 是整份替换而不是增量合并。
5. **档位是预览不是提交**（第 6 轮 R19）：点 chip 后主进程必须**收不到** `settings:set`，
   `#apply` 从 `disabled` 变可用；点「应用」后才收到完整四条，且 `.chip.active`
   从旧档移到新档、`.chip.selected` 清空。手拖滑块要清掉 `.chip.selected`。

## 铁律 10：验证「看不见的按钮」要量布局，不能只看截图

第 6 轮踩到的真事：设置面板 620x800，七个档位 + 三组滑块把内容撑到 1328px，
`body { min-height: 100vh }` 让滚动条长在整页上，**页脚（含最重要的「应用」按钮）
被推到可视区外** —— 截图只截到上半屏时完全看不出问题，用户却必须滚到底才能点「应用」。

三条可复用的做法：

1. **量，不要看**：在 `executeJavaScript` 里取
   `({winH: innerHeight, docH: document.documentElement.scrollHeight, btn: document.getElementById("apply").getBoundingClientRect()})`。
   只有 `docH === winH` 且按钮 `rect.bottom <= innerHeight` 才算"真的可见"。
   实测修前 `{winH:738, docH:1328}`，修后 `{winH:738, docH:738}`。
2. **滚动容器必须是它自己，不是整页**：`html,body{height:100%}` + `body{height:100vh;overflow:hidden}`
   + `.groups{flex:1 1 auto; min-height:0; overflow-y:auto}`。
   **`min-height: 0` 不能省** —— flex 子项的 `min-height` 默认 `auto`，会被内容撑开、拒绝收缩。
3. **截图要覆盖首屏和末屏两张**：`capturePage()` 只拍视口。先 `window.scrollTo(0,0)` 拍一张，
   再 `window.scrollTo(0, scrollHeight)` 拍一张，两张都看过才算验完。

## 测试前检查清单（逐条打勾）

- [ ] 已调用 `__doll.lock(true)`，并确认 `__doll.locked === true`
- [ ] 已把指针钉到固定位置，并静止 ≥ 300ms
- [ ] 没有手写 Verlet 循环，全部走 `r.update(dt)`
- [ ] 速度驱动是连续斜坡，不是阶跃
- [ ] 判断用的指标是 `dy` + 水平偏移像素，不是"接近水平占比"
- [ ] 截图用 `toDataURL` 并垫了灰底
- [ ] 测试结束已调用 `__doll.lock(false)` 交还鼠标（try/finally）
- [ ] 所有改动过的 JS 文件 `node --check` 通过
- [ ] `renderer/config.js` 的 `debug.exposeState` 已恢复 `false`

涉及设置面板时的追加项：

- [ ] `settings-store` 的测试 `init` 指向临时目录，**不要污染真实的 `%APPDATA%\sunny-doll`**
- [ ] 测完把 `settings.json` 清回 `{}`（或直接删掉），否则下次启动手感不是出厂值
- [ ] 如果动过 `settings-schema.js` 的 `FIELDS`，确认主进程与面板同时生效（共用一份定义）
- [ ] 真实程序启动验证前执行 `Remove-Item Env:\ELECTRON_RUN_AS_NODE`

涉及诊断记录器（R21）时的追加项：

- [ ] **改完 `renderer/recorder.js` 必须重启 electron** —— 页面跑的是启动那一刻加载的 JS，
      不重启会读到旧字段名（本轮踩到：分析脚本按 `bear.force` 读，全变 `NaN`，
      误以为记录器坏了，其实文件里已经是 `bear.ropeF`）
- [ ] 节拍判据是「平均 100ms + 理论条数 == 实际条数 + 累计漂移 < 1 个间隔」，
      **不要**要求每条都严格 100ms（60fps 帧量化会导致 97/103 交替）
- [ ] 测完把 `%APPDATA%\sunny-doll\records\` 下的测试文件清掉
- [ ] `recorder.tick()` 是在 rAF 主循环里调的，**主循环没有 try/catch** ——
      任何可能 undefined 的输入都要兜到底（见 [04](04-已知缺陷与待修.md) F14-b）
