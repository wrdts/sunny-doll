## 一、接下来的改进方向（按优先级）

### P0 · 建立可信的测试环境 —— ✅ 已完成

**为什么最先做**：现在所有结论都不可靠。指针有 3 路输入源在竞争，
用户的手也在动，测出来的数据没法复现。

**落地形态**：`debug.lockPointer` 把指针控制权做成**两种运行时模式**：

| 模式 | 值 | 行为 |
| --- | --- | --- |
| 鼠标可控 | `false` | 正常使用，真实鼠标驱动指针 |
| 鼠标不可控 | `true` | 调试，真实鼠标完全失效，指针只听脚本的 |

实现要点：三个输入监听器**永远注册**，只由 `pointerLocked` 运行时拦截——
所以能随时切回鼠标可控，不必改配置、不必重启。这一点很关键：
早期版本用 `if (!LOCK_POINTER)` 在注册期就掐掉监听器，`lock(false)` 后鼠标不会恢复。

切换方式（都不暴露给普通用户）：
- 快捷键 **`Ctrl+Alt+L`**（立即切换，控制台打印当前模式）
- `window.__doll.lock(true/false)`
- 改 `debug.lockPointer`（下次启动生效）

`window.__doll.locked` / `__doll.state().locked` 都是实时值（getter）。

**验收**：✅ 脚本设定坐标后连续采样 20 次 × 500ms，坐标不变，`speed` 恒为 0。

**测试纪律**：测完**必须** `lock(false)` 把鼠标还回去；交付前 `exposeState` 与 `lockPointer` 都改 `false`。

### P1 · 让左右移动明显晃起来（R13 + R14）—— ✅ 第 3 轮完成

**本节原方案（放开死区 + 减小 velocityDamping + 放开 maxAngle）已被实测证伪**，
详细数据见 [09-物理评审与重构方案](09-物理评审与重构方案.md)。证伪结论：

| 原建议 | 实测结果 |
|---|---|
| `angleDeadzone` 0.10 → 0.02 | 动态范围 1.62× → **1.67×**，肉眼无差别 |
| `velocityDamping` 0.030 → 0.010 | 同上，且与 R14 方向冲突 |
| 再叠加 0.12s 低通 | **更差**（17/22.2/26.6° vs 29.6/37.7/44.4°） |
| 放大 `bodyRotateRatio` 到 1.6 | 只是整体等比放大，动态范围不变（1.64×） |

**真正的原因有两个**：

1. **摆角有数学硬上限**：`minDroopRatio: 0.9` ⇒ `θ_max = acos(0.9) = 25.8°`。
   绳长恒定时，不论拖多快都撞不破。
2. **阻尼这一个旋钮同时决定两件事**：闭式解
   `tan(θ) = (k·v + drag·v²)/g` 与 `tau = 1/k` 用的是同一个 k。
   R13 要偏角、R14 要慢衰减，被同向绑死。

**第 3 轮的做法**（不是调参，是换模型）：

| 动作 | 从 | 到 |
|---|---|---|
| 删掉摆角天花板 | `minDroopRatio: 0.9` | 删除（换 `maxBend: 1.50` 只限单关节） |
| 重力 | 8000 | **4000**（周期 0.50s → 0.773s；第 4 轮因改 3 段绳重标定到 **3300**） |
| 阻尼 | `velocityDamping: 0.006`（每子步） | `dampingPerSecond: 0.30`（1/s，与 h 解耦） |
| 空气阻力 | 0.0012 | 0.00015 |
| 死区 | 0.10 | 0.02 |
| 限幅位置 | 物理层几何投影 | **渲染层 tanh 软限幅 45°+18°** |

**验收**（`verify.cjs`，屏高 864 / 绳长 60.5px）：

| 指标 | 目标（原方案写的） | 实际达成 |
|---|---|---|
| 300px/s 横向拖动最大摆角 | ≥ 25° | 绳 3.33°，但**娃娃（含低通+限幅）3.02°** —— 匀速拖动本质上不产生大倾角 |
| 正弦 amp80/f1.5 娃娃最大角 | — | **63.0°** |
| 娃娃最大角动态范围 | — | **1.99×**（旧 1.63×） |
| 停手收敛时间 | 1.5~2.5s | tau **3.09~3.42s**（比目标更慢，符合 R14「停得慢」） |
| 自由摆周期 | — | **0.773~0.780s** vs 理论 0.773s（误差 ≤0.9%） |

> **遗留观察**：正弦驱动在 peakV ≥ 302px/s 后娃娃角**全部封顶在 63.0°**（= 45+18）。
> 也就是说高速段的"动态范围"是靠 tanh 压缩出来的，不是物理自然增长。
> 如果用户觉得高速段"看不出差别"，调 `doll.angleLimit`，不要动物理参数。

### P2 · 允许绳子翻到指针上方（R15）—— ✅ 第 3 轮完成

用户原话：「绳子可以翻转到指针上方，这一块参考正常的牵引效果」。

**原方案（把 `chain.maxAngle` 设为 0）也是错的**：`maxAngle` 在第 2 轮就已经删了
（提交 `330bd52`），但 R15 依然没达成 —— 真正拦路的是 `monoDrop` 单调下垂投影
（每个节点必须比上一个低 1px），语义上就是"禁止翻上去"。

**实测证据**（2500px/s 往返 1800 帧）：

| 配置 | 折叠次数 | 绳端在挂点上方的帧占比 |
|---|---|---|
| 旧版（monoDrop 1 / droop 0.9） | 8 | **0%** |
| monoDrop 1 / droop 0 | 529 | 2% |
| monoDrop 0 / droop 0 | 211 | **51%** |

**修法**：删掉 `monoDrop`，改用 `_limitBend(maxBend)` ——
只限**单个关节的弯曲角**（绕关节纯旋转，精确保段长）、**不限绝对朝向**，
所以整根绳子可以翻到挂点上方，但不会自交折叠。

**验收**：300px @ 6rad/s 往返 → **30.3% 帧绳端高于挂点**（旧版恒 0%）；
60s 剧烈甩动链长恒为 60.48px（=rest）、最小关节夹角 180.0°、零 NaN。

### P3 · 系统指针（D1） —— ✅ 第 11 轮结案：不隐藏，改用系统指针

用户 (m03147) 问「系统自带的是否难以移动到最上层，如右键菜单等特殊场景中，依然要使用原鼠标？」，
并自己实测 (m03111 / m03114)：「娃娃在菜单下方」「系统指针一直存在，从来没有隐藏，
程序指针和小熊在同一层级，即菜单下方」。

于是逐个评估后得到结论：**Win32 `ShowCursor` 在这条架构里不可能生效** ——
它改的是**调用线程**的显示计数，只影响该线程拥有的窗口；覆盖层是
`setIgnoreMouseEvents(true,{forward:true})` + `focusable:false` 的穿透窗，
从不持有鼠标、从不获得焦点，指针下方是**别的窗口**在处理 `WM_MOUSEMOVE`。

用户提出两条备选，选中第二条（m03147 原话：「我认为第二项更好，请你进行分析」）：

| 方案 | 结论 |
|---|---|
| A · `SetSystemCursor` 换空白指针 | ❌ 否决。全局替换；只要有置顶窗口压在覆盖层上（右键菜单 `#32768`、设置面板、任务栏、全屏游戏）屏幕就**完全没有指针**；崩溃/强杀会留下全系统无鼠标 |
| **B · 放弃自绘指针，用系统指针 + 手动偏移** | ✅ 采纳（m03155「okey!do it」）。删掉 `system-cursor.js` / `renderer/cursor.js` / koffi 依赖，挂点 = 指针热点 + `(7, 19)`，面板加一组「指针」两个滑块 |

**净效果**：`main.js` 19924 → 14168 B，原生依赖归零，`package.json` 的 `dependencies` 消失，
约束 C4（不许强杀）的技术风险解除。代价是指针永远在绳子/吊环上面（R15 只剩「绳子从指针背后穿过」）。

| 档位需「应用」确认 | ✅ | 第 6 轮：chip 只预览（描边高亮），点「应用」才下发；滑块仍即时生效 |
| 托盘「档位」子菜单 | ✅ | 第 6 轮：radio 勾当前档，可直接换档不用开面板 |

**为什么是这几个数**（两条洞察，都是从数据里读出来的，不是拍脑袋）：

1. 「**过强**」的主因不是物理参数，是 `doll.angleLimit: 45` 太低 —— 出厂封顶 63°，
   而普通人手晃（正弦 40px@1.2Hz，峰值速度仅 302px/s）就已经顶到 62.9°。
   日常操作全撞天花板 ⇒ 看起来「永远甩那么大、没层次」。
2. 「**过快**」只能靠降 `gravity`，但 `tanθ = (k·v + drag·v²)/g` 说明降 g 会让拖动倾角变大。
   所以降 g 必须同步降 `dampingPerSecond`，两者同比例降才能「慢而不猛」。

**踩到的三个真 bug**（全部只在 E2E 阶段暴露）记在 [04 F12](04-已知缺陷与待修.md)：
`controls.length = 0` 对普通对象无效、`fmt()` 的正则被 PowerShell 吃掉反斜杠、
补丁脚本的 LF 撞上 `main.js` 的 CRLF。

**没做的事**：不支持导入/导出配置文件、不支持自定义预设。
用户没提，属于过度设计。

#### 第 6 轮追加：7 档位 + 「应用」按钮（m02035）

用户原话 (m02035)：「设定 7 个档位，并在下方增加"应用"按钮，」。

| 低档怎么变"轻" | **同时压 g / k / angleLimit** | 只降 g | 只降 g 会让拖动倾角变大（`tanθ=(k·v+drag·v²)/g`），反而更"猛" |

不是「停不下来」，所以七档只拉开周期（1.18→0.64s）和倾角封顶（35°→82°），
不拉开衰减时间。要改 tau 请用「晃动持续」滑块单独调。

### 第三版 · 物理重写（m01770 → ）

用户否掉「缓慢偏移」方案后，逐帧定位到根因：

| 实验 | 结果 |
|------|------|
| 调小 `cursorSmoothing` 到 0.02 | 挂点不蹭了，但绳被甩到 **179°** |


### 第五版 · 第 3 轮物理重构

一句话：**不再调参，换掉产生参数的那个模型。**

| 决策 | 备选 | 理由 |
|---|---|---|
| 删 `monoDrop` / `minDroopRatio` 三道几何投影 | 调它们的参数 | 它们的语义本身与需求冲突（`minDroopRatio` → 摆角硬上限 25.8°；`monoDrop` → 禁止翻上去） |
| 用 `_limitBend` 只限单关节弯曲 | 保留 `monoDrop` | 纯旋转精确保段长，不限绝对朝向，R15 与防折叠可以同时满足 |
| 阻尼改物理量纲 `dampingPerSecond`（1/s） | 保留 `velocityDamping` | 旧的每子步乘性衰减使手感随 `fixedStep` 漂移 1252% |
| 删 `_lastH` / `ratio` | 补上 `this._lastH = h` | 变步长校正恒等于 `h×240`，`fixedStep ≠ 1/240` 时要么爆炸要么过阻尼，是纯 bug 不是设计 |
| `segments: 4 → 2` | 保持 4 | 4 节的中间节点偏离直线 < 1px（"柔性"是假的）。**第 4 轮已改为 3**：修好 `_limitBend` 后折叠全为 0，3 段才是最软的稳定拓扑 |
| 删整个 `_centripetal` 绕圈检测 | 修它 | 绕圈时那三道作弊约束本来就被它旁路，关掉作弊对绕圈数值**毫无影响** |
| 限幅挪到渲染层 tanh（45°+18°） | 物理层硬钳位 | 物理层完全不限幅才符合 R15；渲染层只限制"画出来的角度"，不写回物理 |
| 重力 8000 → 4000 | 保持 8000 | 周期从 0.50s（像抽搐）变成 0.773s（接近真实摆），且离心力占比更高 → R13 方向。第 4 轮改 3 段后又按链式刚体摆重标定到 3300 |
| `iterations: 8 → 2` | 保持 8 | 实测 1/2/4/8/16 结果完全一致，8 次是纯冗余 |

**自研最小核的失败教训（记录下来避免重犯）**：

| 尝试 | 结果 |
|---|---|
| 自建简化核 V2（子步把 p0 插值到中点） | 支点位移被均匀化、Verlet 速度减半 → 阻力倾角随 fixedStep 漂移（−19.76/−15.65/−12.61/+0.14° vs 理论 12.19°） |

### 第六版 · 第 4 轮物理重构 —— 软绳改造（m01090）

一句话：**上一轮把 `segments` 和「质点个数」搞混了，绳子的弯曲自由度被自己删没了。**

| 决策 | 备选 | 理由 |
|---|---|---|
| 认清 `rebuild(len, count)` 的 `count` 是**质点个数** | 原样保留 | `segments: 2` 直传给 rebuild = 2 个质点 = **1 段 = 数学上永远是直线**。这是「绳子变钢棍」的主因 |
| `segments: 2 → 3`（= 4 质点 = 2 个可弯关节） | 4 段 / 5 段 | 3 段是**能弯出明显弧度的最小配置**（sag 20.1px 占绳长 33%），且链长最稳（60.49~60.84px）。4 段漂到 63.05px、5 段 67.72px |
| `_limitBend` 的修正量**按逆质量加权** | 无条件对半分 | `j = 1` 时 `a` 就是锚点（`invMass = 0`），无条件旋转会把锚点从鼠标位置推开 1.0~3.2px —— 绳子自己拽着指针跑 |
| `bendRounds` 循环**以 `_limitBend` 收尾** | 以 `_solveConstraints(1)` 收尾 | 后者会把刚压下去的角度拉回一部分 |
| `bendIterations: 3 → 10` | 保持 3 | 关节越多越难收敛：4 段绳 3 轮只压到 69.2°（不合格），10 轮 93.6° |
| `gravity: 4000 → 3300` | 保持 4000 | 3 段绳质量沿绳分布，**简单摆公式失效**，必须用链式刚体摆 `T = 2π√(Σmᵢ(xᵢ²+yᵢ²)/(g·Σmᵢyᵢ))` 重标定，以保持 0.77s 手感 |
| `renderer/main.js` 重建判断改 `rope.count !== nodeCount` | 保持 `!== segs` | 拿节点数比段数 → 条件恒真，每次 resize 白重建一次绳子 |

**关键教训：参数名的语义必须唯一。** `segments` 是段数，`count` 是质点个数，
两者差 1，混淆后不会报错、只会静默地把物理自由度删掉 —— 而这次的症状
（"绳子变钢棍"）恰好与"柔性没做够"高度相似，很容易误判成调参问题。

**推翻的旧结论**：第 3 轮写的「`segments: 2` 是唯一零折叠 + 零拉伸的拓扑」不再成立。
那条结论是在 `_limitBend` 判反 + 会推锚点的版本下测出来的。修好之后
**所有拓扑 folds 都是 0**，选型约束从"防折叠"变成"长度稳定性"：

| 段数 | 质点 | 链式理论周期 | 实测周期 | 误差 | folds | 链长范围 | 最小关节 |
|---|---|---|---|---|---|---|---|
| 1 | 2 | 0.8531s | 0.8512s | -0.2% | 0 | 60.50~60.50px | 180° |
| 2 | 3 | 0.8007s | 0.8043s | +0.4% | 0 | 60.50~60.51px | 113° |
| **3** | **4** | **0.7713s** | **0.7772s** | **+0.8%** | **0** | **60.49~60.84px** | **94°** |
| 4 | 5 | 0.7562s | 0.7631s | +0.9% | 0 | 60.19~63.05px（漂） | 93° |
| 5 | 6 | 0.7470s | 0.7546s | +1.0% | 6 | 59.79~67.72px（严重漂） | 89° |

（60s @ 4000px/s 复合正弦压力测试，3600 帧，绳长 60.5px）

### 第七版 · 第 5 轮 —— 设置菜单（m01516）

一句话：**用户觉得手感不对，但我不该替他决定"对"是多少 —— 该给他一个能自己调的面板。**

| 决策 | 备选 | 理由 |
|---|---|---|
| 设置面板开**独立 BrowserWindow** | 在覆盖层里画 HTML 控件 | 覆盖层是 `setIgnoreMouseEvents(true,{forward:true})` + `focusable:false` 的全透明窗（约束 C1），**它的鼠标事件全部穿透到下面的窗口**，里面放不了任何可点的控件 |
| 用户设置存 `%APPDATA%/sunny-doll/settings.json` | 直接改 `renderer/config.js` | ① config.js 是出厂默认值，要能被 git 管、被 `rope.test.cjs`/`verify.cjs` 当基线读；② 打包成 asar 后 config.js 只读；③ 恢复默认只要清空这个文件 |
| 字段定义放 `settings-schema.js`，**主进程与面板共用** | 面板自己写一份、主进程自己写一份 | 两份会漂移，出现「面板有滑块但主进程不认」。共用一份后，加字段只改一处 |
| `sanitize` 放在**主进程** | 放在面板 | `settings.json` 是可以手改的，一个 `NaN` 就足以让整条 Verlet 链变 NaN。面板只能产生合法值，但文件不能信 |
| 应用设置走 `applySettings()`，**不调 `applySize()`** | 复用 `applySize()` | `applySize()` 结尾无条件 `rope.teleport() + resetVertically()`，拖重力滑块时每 60ms 把绳子扳回竖直，摆臂被打断，看起来像「卡住」 |
| 覆盖值是**整份替换**，不是增量合并 | 增量覆盖 | 否则「取消某一项」没法实现（点「恢复出厂默认」下发的是 `{}`），必须先回到 `pristineDefaults` 再盖一遍 |
| 只暴露手感项（第 11 轮起 **12 项**），**数值安全阀不给用户碰** | 全部暴露 | `fixedStep` / `maxBend` / `bendIterations` 调坏了只会更难用甚至数值爆炸；判断标准写在 `settings-schema.js` 文件头 |
| ~~面板打开时覆盖层 `setAlwaysOnTop(false)`~~ → **第 10 轮改成：覆盖层永远保持置顶，面板自己也置顶并 `moveTop()`** | 打开面板时降级覆盖层 | 降级再恢复的过程本身没问题，但面板开着的整段时间里娃娃会被别的窗口盖住，用户看到的就是「置顶没了」（m02958）。覆盖层是鼠标穿透的透明窗，被面板压住也不影响点击，只要保证面板在它之上即可 |
| 拖滑块 IPC 用 60ms 合并 + `ignoreEchoUntil` 400ms | 每次 input 都发 | 不合并会淹没主进程；不忽略回声会让拖动中的滑块被自己的广播赋回旧值，手感像被拽回 |

**教训：这次的三个 bug 全是「跨工具的字面量失真」，不是逻辑错。**
`controls.length = 0`（对象不是数组）、`/.$/` 被 PowerShell 吃成 `/.$/`、
LF 撞 CRLF 导致 `split().length - 1 === 0` —— 每一个都「写的时候看着没问题」。
因此：**凡是在 here-string 里写正则或多行模板，都要先打印出那一行自检；每个替换都要断言命中数为 1。**

### 第九版 · 第 12 轮 —— 最大倾斜角上限放到「无限制」（m03753）

| 决策 | 结论 | 理由 |
|---|---|---|
| 面板范围 | `doll.angleLimit` 上限 **85 → 180** | 用户 m03753：「把角度限制范围上限增加到无限制」。180° 是弦角的数学最大值，到 180 就等价于"不限制"，不需要写 999 之类的哨兵值 |
| "不限制"怎么实现 | `if (!(limit > 0) \|\| limit >= 180) return angle;` **显式 early return** | 不能只靠"limit 比实测角大就自然不触发"——`bodyRotateRatio > 1` 时传入角可能超过 180°，那时也得真的直通 |
| 出厂值 | **仍是 45°（可见封顶 63°）** | 用户要的是"能调到不限制"，不是"默认就不限制"。改默认会推翻第 5~6 轮为"过强"做的全部标定 |
| 七个档位 | **不动** | 7 档里最高的第 7 档只到 64°，仍在老语义内。想完全放开是用滑块，不是改档位 |
| `angleLimitOvershoot` | 保持不变，`limit = 180` 时自然失效 | 少一个需要用户理解的概念 |

**代价**：`angleLimit = 180` 时"熊永远不会倒挂"这条保证不再成立 —— 熊会被甩到倒过来。
这是用户明确要的（R20）。`verify.cjs` 的 `makeDoll()` 复刻了这条 early return，
所以验收脚本在 180° 下也会给出与真实渲染一致的角度。

**"无限制"到底有多不限**：`tipAngle = atan2(dx, dy)` 的值域是 `(-180°, 180°]`，
所以设 180 之后渲染层的角度就是**未经任何压缩的原始弦角**。实测（纯函数层面）：

| limit | 传入 90° | 传入 120° | 传入 179° | 传入 180° |
|---|---|---|---|---|
| 45（出厂） | 62.76° | 62.99° | 63.00° | 63.00° |
| 90 | 90.00° | 106.76° | 108.00° | 108.00° |
| 179 | 90.00° | 120.00° | 179.00° | 180.00° |
| **180** | **90.00°** | **120.00°** | **179.00°** | **180.00°** |

**真机端到端验证**（Electron 实跑 + CDP：`__doll.lock(true)` 断开真实鼠标、主循环单驱动、
拖动用 smoothstep 平滑加速；采样 = 每帧读 `__doll.state().dollAngle`，即真正画出去的角度）：

| 场景 | limit = 45°（出厂）娃娃角 | limit = 180° 娃娃角 | 绳端弦角（两档相同） |
|---|---|---|---|
| 40px @ 400px/s | [-63.0, 63.0]° | [-89.8, 60.7]° | [-97.1, 67.3]° |
| 120px @ 1200px/s | [-62.9, 63.0]° | [-139.0, 98.7]° | [-176.9, 179.5]° |
| 250px @ 2200px/s | [-62.9, 63.0]° | [-146.8, 104.1]° | [-179.5, 177.5]° |

关键结论：**45° 时娃娃角被死死钉在 ±63°**（三个场景一模一样，与 tanh 上限完全吻合）；
**180° 时娃娃角跟着绳端弦角走**，大甩时到 -147°，确实倒挂。
同一次测试里真实鼠标被移到 (1750, 980)，`cursor` 稳定停在 (480, 320) —— 证明单驱动有效，
上面这些角度不是被手抖污染出来的。

### 第十版 · 第 13 轮 —— 诊断记录器（m04081）

用户原话（m04081）：「git保存一下，然后增加一个按钮，用于每0.1s记录现在情况，线段位置，熊的受力和速度等」

| 决策 | 结论 | 理由 |
|---|---|---|
| 采样放在哪 | **在覆盖层渲染进程里采样**，主进程只转发命令 + 写盘 | 物理状态只存在于渲染进程的 `rope` 对象里。主进程拿不到质点坐标，除非让渲染层每帧 IPC 推 —— 那就等于每帧序列化一次，白白耗性能 |
| 采样节拍 | `frame(now)` 里 `recorder.tick(now)`，`_nextAt += intervalMs` **理论节拍推进** | 不用 `setInterval`：覆盖层隐藏时 rAF 会停，定时器只会在看不见的时候继续堆样本。用理论节拍推进可以避免每帧舍入误差累积（实测 244 条零漂移） |
| 「熊受的力」是什么 | **绳子合力**，`ropeF = m·(a + kDamp·vAvg − (重力 + 风 + 空气阻力))` | 净力恒等于 `m·a`，没有信息量。真正想知道的是"绳子在拉多大的力"。**静止竖直时它精确等于 `m·g`** —— 这一条同时是最好的正确性自检 |
| 阻尼为什么要补 | 必须补回 `kDamp·vAvg` | Verlet 每子步有 `keep = exp(-k*h)` 的乘性衰减，折合每秒 `-k·v`。差分出的加速度里含这一项，不补则绳力系统性偏小（k=0.3、v=1000 时约差 300px/s²，接近重力 1/10） |
| 公式从哪来 | **从 `rope.js` 里抽出来共用**：`environmentAccel()` / `dampingRate()` | 记录器不许抄一份重力/风公式 —— 两处只要有一处改动就会漂移，而漂移了还看不出来。抽成公开方法后，记录器永远和引擎用同一份 |
| 算不出来的量 | 写 **`null`，绝不写 0** | 0 会被读成"真的没受力"。首条样本 `ropeF` 就是 `null`（没有上一条，差分不出加速度） |
| 落盘格式 | **一条样本一行**的 JSON | 为了能直接 `grep` / `Select-String` 挑样本。整体仍是合法 JSON，`JSON.parse` 能读 |
| 存哪 | `%APPDATA%\sunny-doll\records\record-YYYYMMDD-HHMMSS.json` | 和 `settings.json` 同级，升级不丢 |
| 上限 | 18000 条 = **30 分钟**，撞上限自动停（`stopReason="auto"`） | 防止忘了关把内存吃光。`stop("user")` 和 `stop("auto")` 统一从 `onStop` 一个出口出 |
| 入口 | 面板底部按钮 **+ 托盘同名项** | 面板要 `Ctrl+Alt+S` 才能开；托盘一键可达。两处状态由同一条 `record:status` 回推维护 |

**代价**（明确接受）：

1. 记录时多一份 `samples` 数组在内存里（18000 条 × ~300 B ≈ 5 MB 上限）。
2. 落盘在主进程异步做，写完才推 `record:saved` —— 大文件（120 KB / 244 条，30 分钟约 5 MB）会有可感知的延迟，但按钮不会卡。
3. 记录器是**只读**的，它不改手感；反过来说，它也无法复现某一次的手感 —— 想复现仍要靠 `settings.json`。

**验证**（详见 [03 三之三](03-测试方法论.md)）：

| 层 | 断言 | 实测 |

| 纯 Node（`verify.cjs` 验收 8） | 条数 / 节拍 / 字段 / 首条 null / 静止绳力 / summary / 自动停 / 兜底不抛 | 8 条全 PASS |

### 第十三版 · 第 18 轮 —— 挂饰库：名称 + 图片存项目 + 下拉联动（m05728）

用户三项需求：①「物理」页中把档位放置在页面内（选项卡下方）；②导入图片要输入名称、保存在项目中；③挂饰下拉以「图片+名称」为条目，切换时下方细节项联动。

| 决策 | 理由 |
|---|---|
| 图片复制进项目 `v0\assets\dangles\`（时间戳文件名防重名） | 原图可能被移动/删除；settings.json 只存项目内路径 |
| `dangleName` / `dangleList`（JSON 数组字符串）走 schema 的 STRINGS 通道 | 复用现有字符串 sanitize（maxLen 钳制），不新开 IPC |
| 挂饰下拉动态构建：`bear` + dangleList 索引 + `raw:<path>`（旧版未入库图兼容） | 换下拉 ≠ 改 schema 枚举，库内容随时变 |
| 下拉 change 同步写 dangle / image.path / dangleName 三键 | 联动是原子提交，不是三处各自触发 |
| 名称输入行只在「刚导入尚未入库」时显示（dataUrl 存在） | 入库后名称由下拉联动展示，避免界面常驻多余控件 |
| 档位条挪进 `</nav>` 之后（DOM 顺序即视觉顺序） | 不引入新的显隐逻辑，switchTab 原样工作 |

验证：13 JS `node --check` 全过、rope.test 17 组 ✓、verify 9 组 ✓；真机 E2E：布局 docH 763===winH、档位条仅物理页显示、导入→命名→入库→下拉联动→切回小熊→再切回全链路 ✓、settings.json 持久化 ✓。

### 第十四版 · 第 19 轮 —— 挂饰库管理：列表 / 重命名 / 删除（m05855）

用户原话 (m05855)：「图片选项页增加对于自定义挂饰项的增删，使得项目内部可以存在多个自定义项」

| 决策 | 结论 | 理由 |
|---|---|---|
| 库列表的形态 | import-row 之下一个独立区块，每行 = 缩略图 + 名称输入框 + 「使用」+ 「删除」 | 用户要的是「增删」。重命名复用 `change` 事件直接落在输入框上，不弹编辑框 —— 少一层模态就少一个能被误触的界面状态 |
| 删除走新 IPC `settings:delete-dangle` | 不新增通道到覆盖层，只在设置面板的 preload 里加 | 删文件是危险动作，权限只给面板，覆盖层永远碰不到 |
| 主进程怎么防越权 | `path.resolve(p)` 的 `dirname` 必须**等于** `assets\dangles`（大小写不敏感），否则直接拒绝 | 面板是不可信渲染层。不加这条校验，面板就能被改成传任意路径删任意文件 |
| 删掉正在使用的挂饰 | 自动切回自带小熊，并清 `image.path` / `dangleName` | 不留悬挂引用。否则 `dangle="image"` 但 path 指向已删文件，会静默回退到 emoji —— 用户看到的是「熊变了」而不是「图没了」，属于隐式行为 |
| 重命名当前生效的条目 | 同步写 `doll.dangleName` | 下拉与细节行显示的都是 `dangleName`，不同步会出现「同一个挂饰两个名字」 |
| 库内容存哪 | 仍是 `doll.dangleList`（JSON 数组字符串，走 schema 的 `STRINGS` 通道，`maxLen 20000`） | 不新开数据结构、不新开 IPC。20000 字符够存约 200 条，超出由 `sanitize` 直接截断 |

**验证**：`rope.test.cjs` 17 组 ✓、`verify.cjs` 9 组 ✓；真机 E2E 全链路
「加 2 条 → 重命名 → 使用 → 删使用中 → 回退小熊 → 删普通」✓。
